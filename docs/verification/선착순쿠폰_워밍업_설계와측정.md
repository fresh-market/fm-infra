# 선착순 쿠폰 워밍업 설계와 측정

**차가운 JVM 으로 이벤트를 열면 p99 를 못 지킨다.** 발급 정확성은 지켜지지만 SLO 는 13배
차이로 벗어난다. 그리고 `coupon-event.sh` 가 이벤트 직전에 인스턴스를 띄우는 설계라
**실제 이벤트는 항상 차갑게 시작한다.**

이 문서는 그 문제의 측정과 해결 설계를 다룬다. 회차별 결과는
[선착순쿠폰_부하시험_기록.md](선착순쿠폰_부하시험_기록.md) 에, 타임아웃과 회로 값의 근거는
[선착순쿠폰_타임아웃과회로_설정근거.md](선착순쿠폰_타임아웃과회로_설정근거.md) 에 있다.

---

## 1. 문제

2026-08-31, 같은 커밋(`82daeb9`), 같은 사양(`t3.small` 3대), 같은 시나리오(VU 20,000 /
재고 10,000)로 두 번 쟀다. 차이는 **본 시험 전에 트래픽이 지나갔느냐** 하나다.

| | 차가움 | 데워짐 |
|---|---:|---:|
| 발급 / 소진 | 9,979 / 10,000 | **10,000 / 10,000** |
| 번호 유실 (`gap`) | 0 | 0 |
| 실패율 | 0.00% | 0.00% |
| 혼잡 503 | 21 | **0** |
| 504 / 502 / 연결 오류 | 0 / 0 / 0 | 0 / 0 / 0 |
| **p99** | **4.69초** | **0.247초** |
| p95 | 2.72초 | 0.090초 |

**발급 정확성은 차가워도 지켜진다.** 초과 발급 0, 인스턴스 유실 0, 서버 오류 0.
무너지지 않는다. 못 지키는 것은 p99 하나다.

### 그 시간은 앱 안에 있다

```
앱이 잰 요청 최대   5,638ms
k6 가 잰 최대       5,660ms
```

거의 같다. ALB 큐잉이나 네트워크가 아니라 앱이 그만큼 붙잡고 있었다.

| | 차가움 | 데워짐 |
|---|---:|---:|
| 동시에 앱 안에 머문 요청 최대 | **244** | 6 |
| 가장 오래 머문 요청 | **4,839ms** | 45ms |

`commit-wait` 이 800ms 라 확정 대기는 거기서 끊긴다. Redis 는 왕복 둘에 100ms 씩이다.
**합쳐도 1초인데 4.8초를 머물렀다.** 나머지 3.8초는 어느 타임아웃도 덮지 않는 구간,
즉 가상 스레드가 CPU 를 얻기까지 기다린 시간이다.

### 무엇이 CPU 를 먹었나

```
JIT 컴파일 증가분   차가움 49,676ms  /  데워짐 11,113ms      90초 회차 동안
node CPU steal      차가움 11.0%     /  데워짐 3.7%
```

**차가운 JVM 은 요청을 처리하면서 동시에 자기를 컴파일한다.** 90초 회차에서 49.7초어치를
컴파일했고 그만큼이 요청 처리에서 빠졌다. steal 은 `t3.small` 이 공유 하드웨어라 생기는
것으로 우리 통제 밖이다.

**값을 조여서 고칠 수 있는 문제가 아니다.** 타임아웃은 각자 제 구간을 지켰다.

## 2. 측정: 얼마나 흘려야 데워지나

차가운 인스턴스 3대에 트래픽을 단계적으로 흘리며 쟀다 (2026-08-31).

| 단계 | 누적 요청 | 인스턴스별 `jvm_compilation_time_ms_total` |
|---|---:|---|
| 기동 직후 | 0 | 41,607 / 44,730 / 49,149 |
| 저부하 뒤 | 200 | 45,135 / 48,377 / 54,521 |
| **3,000 뒤** | **3,200** | **52,931 / 57,609 / 66,216** |

효율이 앞쪽에 몰려 있다.

```
요청   0 -> 200      +4,000ms    건당 20ms
요청 200 -> 3,200    +8,000ms    건당 2.7ms
```

**초반 요청 하나가 후반 요청보다 7배 더 데운다.** 자주 도는 메서드부터 컴파일되기 때문이다.

### 응답이 먼저 좋아진다

| 워밍업 트래픽 | 그 트래픽의 최대 응답 | p95 |
|---|---:|---:|
| 200건 (초당 6건) | 1.72초 | 1.41초 |
| **3,000건 (초당 97건)** | **171ms** | **88ms** |

3,000건을 흘리는 동안 이미 응답이 웜 수준(어제 웜 회차 p95 90ms)에 닿았다.

### 그 상태로 본 시험을 돌렸다

| | 워밍업 없음 | **워밍업 3,200건** |
|---|---:|---:|
| 발급 / 소진 | 9,979 / 10,000 | **10,000 / 10,000** |
| 혼잡 503 | 21 | **0** |
| **p99** | **4.69초** | **0.356초** |
| p95 | 2.72초 | 0.124초 |
| 504 / 502 / 연결 오류 / Target 5xx | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 |

**p99 가 13배 개선됐고 SLO 를 통과한다.**

## 3. 판정 기준을 고쳤다

처음에는 `jvm_compilation_time_ms_total` **10만 이상**을 데워진 기준으로 잡았다.
2만 건을 처리한 인스턴스가 그쯤이었다는 관찰에서 나온 값이다.

**틀렸다.** 위 회차는 **53,000 ~ 66,000 에서 통과**했다.

```
잘못 잡은 기준   컴파일 누적 10만 이상
실제로 맞는 것   처리한 요청 3,000건 이상
```

컴파일 누적은 트래픽을 받는 내내 오르지만 **성능에 기여하는 컴파일은 앞쪽 몇천 건에서
대부분 끝난다.** 10만은 문턱이 아니라 "오래 돌린 인스턴스의 부산물" 이었다.

그대로 두면 다음 사람이 도달할 필요 없는 값을 쫓는다. **기준은 요청 수로 잡는다.**

### 가동 시간은 기준이 아니다

앞선 측정에서 5.5시간 놀고 있던 인스턴스보다 10분 동안 실제 발급을 받은 인스턴스가 더
데워져 있었다. **처리한 트래픽만이 기준이다.**

## 4. 설계

### 기존 대기를 워밍업 대기로 쓴다

`coupon-event.sh open 3` 이 이미 healthy 를 최대 600초 기다린다. **readiness 가 올라가는
시점을 워밍업 완료 뒤로 미루면** 스크립트도 운영 절차도 안 바꾸고 목적을 이룬다.

```
coupon-event.sh open 3
  -> 인스턴스 3대 부팅
  -> 각자 워밍업 (readiness 아직 DOWN)
  -> 다 데워지면 readiness UP
  -> 스크립트의 "healthy 대기" 가 곧 "warm 대기"
```

`ApplicationRunner` 는 `ApplicationReadyEvent` **앞**에 돈다. 스프링 부트가 그 이벤트에서
`ACCEPTING_TRAFFIC` 으로 올리므로, **러너 안에서 데우면 readiness 조작 없이 자연히 늦춰진다.**
`DefaultMemberGradeInitializer` 라는 전례가 이미 있다.

### 자기 자신에게 진짜 HTTP 를 보낸다

```
POST http://localhost:8080/v1/coupons/{워밍업쿠폰}/issues
Authorization: Bearer {JwtTokenProvider.createAccessToken 으로 자체 발급}
```

인프로세스로 서비스만 부르면 톰캣, 시큐리티 필터, JWT 검증, Jackson 직렬화가 안 데워진다.
요청 하나가 지나는 전부를 데우려면 HTTP 로 보내야 한다.

토큰은 앱이 스스로 만들 수 있다 (`JwtTokenProvider.createAccessToken(Long, TokenType, String)`).

### 워밍업 전용 쿠폰을 쓴다

본 쿠폰으로 데우면 재고가 줄어 시험과 이벤트가 망가진다.

```
워밍업 쿠폰   재고 200
  요청 1~200     200 발급   -> 큐, 플러시 스레드, 배치 INSERT, markCommitted 까지
  요청 201~N     409 소진   -> 읽기 경로와 응답 경로를 반복
```

**재고를 일부러 작게** 잡아 쓰기 경로와 읽기 경로를 둘 다 지나게 한다.

동시성은 20 을 둔다. 순차로 보내면 플러시 배치 크기가 1 이 되어 **배치 경로가 안 데워진다.**

### 값

| 설정 | 값 | 근거 |
|---|---|---|
| 요청 수 | **5,000** | 3,200 에서 통과. 마진을 산다 |
| 동시성 | 20 | 배치 경로를 데우려면 필요 |
| 워밍업 쿠폰 재고 | 200 | 쓰기와 읽기 경로를 둘 다 태운다 |
| 상한 | **60초** | 3,000건이 30초였으니 5,000건은 약 50초 |

3,000 이 아니라 5,000 인 것은 비용이 비대칭이라서다.

```
더 데우는 비용    요청 2,000건 = 약 20초의 기동 지연
덜 데운 비용      이벤트 하나가 p99 4.69초로 끝남
```

통과한 0.356초가 SLO 1초 대비 2.8배 여유인데, steal 이 나쁜 날(11%)이면 그 여유가 줄어든다.

### 반드시 지킬 것 둘

**상한이 있어야 한다.** 없으면 워밍업이 안 끝나 readiness 가 영영 안 올라가고 ASG 가
인스턴스를 계속 교체한다. `health_check_grace_period` 가 300초이므로 60초는 안전하다.

**실패해도 ready 가 돼야 한다.**

```java
try {
    warmUp();
} catch (Exception e) {
    log.warn("event=COUPON_WARMUP_FAILED ...", e);   // 삼킨다
}
```

Redis 가 죽었거나 워밍업 쿠폰이 없어도 인스턴스는 떠야 한다. 워밍업은 최적화이지 정합성
요건이 아니다.

### 범위

`@Profile("coupon")` 으로 전용 인스턴스에서만 돈다. 앱과 배치는 하지 않는다.

## 5. 검토했으나 안 고른 것

### 이벤트 열기를 전 인스턴스에 퍼뜨린다

`CouponEventService.open()` 은 ALB 가 라우팅한 **한 대에서만** 돈다.
`CouponEventOpenedEvent` 는 스프링 로컬 이벤트라 프로세스 밖으로 안 나간다. 그래서 거기서
데워 봐야 한 대만 데워진다.

Redis pub/sub 으로 퍼뜨리면 되지만 두 가지가 걸린다. 지금 `RedisMessageListenerContainer`
가 없어 새로 놓아야 하고, **이벤트를 여는 순간에 데우기 시작하면 이미 늦다.** 사람들이 이미
몰려오는 중이다.

### CRaC

데워진 JVM 을 체크포인트로 떠서 복원한다. JIT 상태까지 복원되므로 **워밍업 문제 자체가
사라진다.** Spring Boot 3.2+ 가 지원한다.

대신 CRaC 지원 JVM(Azul Zulu 등)으로 갈아타야 하고 체크포인트 생성이 빌드에 붙는다.
지금 규모에는 과하다고 봤다. 워밍업 트래픽으로 안 되는 것이 확인되면 그때 다시 본다.

### AppCDS / AOT

클래스 로딩만 줄인다. **JIT 은 그대로**라 이 문제를 안 고친다.

## 6. 확인하지 않은 것

### 경계를 모른다

200 은 부족하고 3,200 은 충분한데, 1,000 이나 2,000 이 어떤지는 안 쟀다. 5,000 은 안전한
쪽으로 넉넉히 잡은 값이지 계산 결과가 아니다.

경계를 좁히려면 두 회차가 더 필요한데, 20초를 아끼려고 그럴 값어치는 없어 보인다.

### 표본이 하나다

3,200건에서 통과한 회차가 한 번뿐이다. 그 회차의 steal 도 안 봤다.

### 부하대가 다르다

워밍업은 초당 97건이었고 본 이벤트는 초당 333건이다. **그 부하대에서만 도는 경로**가 있으면
워밍업으로 못 덮는다. 완전히 데운 상태(p99 0.247초)와 3,200건 워밍업(0.356초) 사이의 차이가
거기서 왔을 수 있다.

### 경로의 어디가 비싼지 안 갈랐다

요청당 비용이 HTTP/시큐리티/직렬화에 있는지 Lua 호출과 배치 INSERT 에 있는지 모른다.
앞쪽이면 아무 엔드포인트나 두드려도 되고, 그러면 **워밍업 전용 쿠폰이 필요 없어 훨씬
간단해진다.** 지금 설계는 "모르니 다 데운다" 쪽이다.

### 구현하지 않았다

이 문서는 측정과 설계까지다. 코드는 아직 없다.
