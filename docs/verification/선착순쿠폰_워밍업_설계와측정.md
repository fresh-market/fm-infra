# 선착순 쿠폰 워밍업 설계와 측정

**차가운 JVM 으로 이벤트를 열면 p99 를 못 지킨다.** 발급 정확성은 지켜지지만 SLO 는 13배
차이로 벗어난다. 그리고 `coupon-event.sh` 가 이벤트 직전에 인스턴스를 띄우는 설계라
**실제 이벤트는 항상 차갑게 시작한다.**

이 문서는 그 문제의 측정과 해결 설계를 다룬다. 회차별 결과는
[선착순쿠폰_부하시험_기록.md](선착순쿠폰_부하시험_기록.md) 에, 타임아웃과 회로 값의 근거는
[선착순쿠폰_타임아웃과회로_설정근거.md](선착순쿠폰_타임아웃과회로_설정근거.md) 에 있다.

## 1. 문제

2026-08-31, 같은 커밋(`82daeb9`), 같은 사양(`t3.small` 3대), 같은 시나리오(VU 20,000 /
재고 10,000)로 두 번 쟀다. 차이는 **본 시험 전에 트래픽이 지나갔느냐** 하나다.

| | 차가움 | 데워짐 |
|---|---:|---:|
| 발급 / 소진 | 9,979 / 10,000 | **10,000 / 10,000** |
| 번호 유실 (`gap`) | 0 | 0 |
| 실패율 | 0.00% | 0.00% |
| 혼잡 503 | 21 | **0** |
| 504 / 502 / 연결 오류 | 0 / 0 / 0 | 0 / 0 / 0 |
| **p99** | **4.69초** | **0.247초** |
| p95 | 2.72초 | 0.090초 |

**발급 정확성은 차가워도 지켜진다.** 초과 발급 0, 인스턴스 유실 0, 서버 오류 0.
무너지지 않는다. 못 지키는 것은 p99 하나다.

### 그 시간은 앱 안에 있다

```
앱이 잰 요청 최대   5,638ms
k6 가 잰 최대       5,660ms
```

거의 같다. ALB 큐잉이나 네트워크가 아니라 앱이 그만큼 붙잡고 있었다.

| | 차가움 | 데워짐 |
|---|---:|---:|
| 동시에 앱 안에 머문 요청 최대 | **244** | 6 |
| 가장 오래 머문 요청 | **4,839ms** | 45ms |

`commit-wait` 이 800ms 라 확정 대기는 거기서 끊긴다. Redis 는 왕복 둘에 100ms 씩이다.
**합쳐도 1초인데 4.8초를 머물렀다.** 나머지 3.8초는 어느 타임아웃도 덮지 않는 구간,
즉 가상 스레드가 CPU 를 얻기까지 기다린 시간이다.

### 무엇이 CPU 를 먹었나

```
JIT 컴파일 증가분   차가움 49,676ms  /  데워짐 11,113ms      90초 회차 동안
node CPU steal      차가움 11.0%     /  데워짐 3.7%
```

**차가운 JVM 은 요청을 처리하면서 동시에 자기를 컴파일한다.** 90초 회차에서 49.7초어치를
컴파일했고 그만큼이 요청 처리에서 빠졌다. steal 은 `t3.small` 이 공유 하드웨어라 생기는
것으로 우리 통제 밖이다.

**값을 조여서 고칠 수 있는 문제가 아니다.** 타임아웃은 각자 제 구간을 지켰다.

## 2. 측정: 얼마나 흘려야 데워지나

차가운 인스턴스 3대에 트래픽을 단계적으로 흘리며 쟀다 (2026-08-31).

| 단계 | 누적 요청 | 인스턴스별 `jvm_compilation_time_ms_total` |
|---|---:|---|
| 기동 직후 | 0 | 41,607 / 44,730 / 49,149 |
| 저부하 뒤 | 200 | 45,135 / 48,377 / 54,521 |
| **3,000 뒤** | **3,200** | **52,931 / 57,609 / 66,216** |

효율이 앞쪽에 몰려 있다.

```
요청   0 -> 200      +4,000ms    건당 20ms
요청 200 -> 3,200    +8,000ms    건당 2.7ms
```

**초반 요청 하나가 후반 요청보다 7배 더 데운다.** 자주 도는 메서드부터 컴파일되기 때문이다.

### 응답이 먼저 좋아진다

| 워밍업 트래픽 | 그 트래픽의 최대 응답 | p95 |
|---|---:|---:|
| 200건 (초당 6건) | 1.72초 | 1.41초 |
| **3,000건 (초당 97건)** | **171ms** | **88ms** |

3,000건을 흘리는 동안 이미 응답이 웜 수준(어제 웜 회차 p95 90ms)에 닿았다.

### 그 상태로 본 시험을 돌렸다

| | 워밍업 없음 | **워밍업 3,200건** |
|---|---:|---:|
| 발급 / 소진 | 9,979 / 10,000 | **10,000 / 10,000** |
| 혼잡 503 | 21 | **0** |
| **p99** | **4.69초** | **0.356초** |
| p95 | 2.72초 | 0.124초 |
| 504 / 502 / 연결 오류 / Target 5xx | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 |

**p99 가 13배 개선됐고 SLO 를 통과한다.**

## 3. 판정 기준을 고쳤다

처음에는 `jvm_compilation_time_ms_total` **10만 이상**을 데워진 기준으로 잡았다.
2만 건을 처리한 인스턴스가 그쯤이었다는 관찰에서 나온 값이다.

**틀렸다.** 위 회차는 **53,000 ~ 66,000 에서 통과**했다.

```
잘못 잡은 기준   컴파일 누적 10만 이상
실제로 맞는 것   처리한 요청 3,000건 이상
```

컴파일 누적은 트래픽을 받는 내내 오르지만 **성능에 기여하는 컴파일은 앞쪽 몇천 건에서
대부분 끝난다.** 10만은 문턱이 아니라 "오래 돌린 인스턴스의 부산물" 이었다.

그대로 두면 다음 사람이 도달할 필요 없는 값을 쫓는다. **기준은 요청 수로 잡는다.**

### 가동 시간은 기준이 아니다

앞선 측정에서 5.5시간 놀고 있던 인스턴스보다 10분 동안 실제 발급을 받은 인스턴스가 더
데워져 있었다. **처리한 트래픽만이 기준이다.**

## 4. 설계

### 기존 대기를 워밍업 대기로 쓴다

`coupon-event.sh open 3` 이 이미 healthy 를 최대 600초 기다린다. **readiness 가 올라가는
시점을 워밍업 완료 뒤로 미루면** 스크립트도 운영 절차도 안 바꾸고 목적을 이룬다.

```
coupon-event.sh open 3
  -> 인스턴스 3대 부팅
  -> 각자 워밍업 (readiness 아직 DOWN)
  -> 다 데워지면 readiness UP
  -> 스크립트의 "healthy 대기" 가 곧 "warm 대기"
```

`ApplicationRunner` 는 `ApplicationReadyEvent` **앞**에 돈다. 스프링 부트가 그 이벤트에서
`ACCEPTING_TRAFFIC` 으로 올리므로, **러너 안에서 데우면 readiness 조작 없이 자연히 늦춰진다.**
`DefaultMemberGradeInitializer` 라는 전례가 이미 있다.

### 자기 자신에게 진짜 HTTP 를 보낸다

```
POST http://localhost:8080/v1/coupons/{워밍업쿠폰}/issues
Authorization: Bearer {JwtTokenProvider.createAccessToken 으로 자체 발급}
```

인프로세스로 서비스만 부르면 톰캣, 시큐리티 필터, JWT 검증, Jackson 직렬화가 안 데워진다.
요청 하나가 지나는 전부를 데우려면 HTTP 로 보내야 한다.

토큰은 앱이 스스로 만들 수 있다 (`JwtTokenProvider.createAccessToken(Long, TokenType, String)`).

### 워밍업 전용 쿠폰을 쓴다

본 쿠폰으로 데우면 재고가 줄어 시험과 이벤트가 망가진다.

```
워밍업 쿠폰   재고 200
  요청 1~200     200 발급   -> 큐, 플러시 스레드, 배치 INSERT, markCommitted 까지
  요청 201~N     409 소진   -> 읽기 경로와 응답 경로를 반복
```

**재고를 일부러 작게** 잡아 쓰기 경로와 읽기 경로를 둘 다 지나게 한다.

동시성은 20 을 둔다. 순차로 보내면 플러시 배치 크기가 1 이 되어 **배치 경로가 안 데워진다.**

### 값

| 설정 | 값 | 근거 |
|---|---|---|
| 요청 수 | **5,000** | 3,200 에서 통과. 마진을 산다 |
| 동시성 | 20 | 배치 경로를 데우려면 필요 |
| 워밍업 쿠폰 재고 | 200 | 쓰기와 읽기 경로를 둘 다 태운다 |
| 상한 | **60초** | 3,000건이 30초였으니 5,000건은 약 50초 |

3,000 이 아니라 5,000 인 것은 비용이 비대칭이라서다.

```
더 데우는 비용    요청 2,000건 = 약 20초의 기동 지연
덜 데운 비용      이벤트 하나가 p99 4.69초로 끝남
```

통과한 0.356초가 SLO 1초 대비 2.8배 여유인데, steal 이 나쁜 날(11%)이면 그 여유가 줄어든다.

### 반드시 지킬 것 둘

**상한이 있어야 한다.** 없으면 워밍업이 안 끝나 readiness 가 영영 안 올라가고 ASG 가
인스턴스를 계속 교체한다. `health_check_grace_period` 가 300초이므로 60초는 안전하다.

**실패해도 ready 가 돼야 한다.**

```java
try {
    warmUp();
} catch (Exception e) {
    log.warn("event=COUPON_WARMUP_FAILED ...", e);   // 삼킨다
}
```

Redis 가 죽었거나 워밍업 쿠폰이 없어도 인스턴스는 떠야 한다. 워밍업은 최적화이지 정합성
요건이 아니다.

### 범위

`@Profile("coupon")` 으로 전용 인스턴스에서만 돈다. 앱과 배치는 하지 않는다.

## 5. 검토했으나 안 고른 것

### 이벤트 열기를 전 인스턴스에 퍼뜨린다

`CouponEventService.open()` 은 ALB 가 라우팅한 **한 대에서만** 돈다.
`CouponEventOpenedEvent` 는 스프링 로컬 이벤트라 프로세스 밖으로 안 나간다. 그래서 거기서
데워 봐야 한 대만 데워진다.

Redis pub/sub 으로 퍼뜨리면 되지만 두 가지가 걸린다. 지금 `RedisMessageListenerContainer`
가 없어 새로 놓아야 하고, **이벤트를 여는 순간에 데우기 시작하면 이미 늦다.** 사람들이 이미
몰려오는 중이다.

### CRaC

데워진 JVM 을 체크포인트로 떠서 복원한다. JIT 상태까지 복원되므로 **워밍업 문제 자체가
사라진다.** Spring Boot 3.2+ 가 지원한다.

대신 CRaC 지원 JVM(Azul Zulu 등)으로 갈아타야 하고 체크포인트 생성이 빌드에 붙는다.
지금 규모에는 과하다고 봤다. 워밍업 트래픽으로 안 되는 것이 확인되면 그때 다시 본다.

### AppCDS / AOT

클래스 로딩만 줄인다. **JIT 은 그대로**라 이 문제를 안 고친다.

## 6. 확인하지 않은 것

### 경계를 모른다

200 은 부족하고 3,200 은 충분한데, 1,000 이나 2,000 이 어떤지는 안 쟀다. 5,000 은 안전한
쪽으로 넉넉히 잡은 값이지 계산 결과가 아니다.

경계를 좁히려면 두 회차가 더 필요한데, 20초를 아끼려고 그럴 값어치는 없어 보인다.

### 표본이 하나다

3,200건에서 통과한 회차가 한 번뿐이다. 그 회차의 steal 도 안 봤다.

### 부하대가 다르다

워밍업은 초당 97건이었고 본 이벤트는 초당 333건이다. **그 부하대에서만 도는 경로**가 있으면
워밍업으로 못 덮는다. 완전히 데운 상태(p99 0.247초)와 3,200건 워밍업(0.356초) 사이의 차이가
거기서 왔을 수 있다.

### 경로의 어디가 비싼지 안 갈랐다

요청당 비용이 HTTP/시큐리티/직렬화에 있는지 Lua 호출과 배치 INSERT 에 있는지 모른다.
앞쪽이면 아무 엔드포인트나 두드려도 되고, 그러면 **워밍업 전용 쿠폰이 필요 없어 훨씬
간단해진다.** 지금 설계는 "모르니 다 데운다" 쪽이다.

### 구현하지 않았다

이 문서는 측정과 설계까지다. 코드는 아직 없다.

## 7. AWS 회차: 구현한 워밍업을 재다 (2026-09-04)

**6절이 "구현하지 않았다" 로 끝나 있던 것을 채우는 절이다.** 설계가 코드가 되어(fm-backend #154)
실제 AWS 에 올라갔고, 그것을 세 조건으로 갈라 잰다.

### 세 회차로 가른다

조건 하나만 바꾸고 나머지를 고정한다. 같은 날 같은 인스턴스 같은 시드에서 잰다.

| 회차 | 조건 | 무엇을 답하나 |
|---|---|---|
| **B** | 배포된 기본값. `enabled: true`, `write-rows: 5000` | 앱이 스스로 데운 것으로 p99 를 맞추나 |
| **C** | `COUPON_WARMUP_WRITEROWS=0` | #154 의 쓰기 워밍업이 실제로 기여하나 |
| **A** | `COUPON_WARMUP_ENABLED=false` | 워밍업이 없으면 얼마나 나쁜가 |

**B 와 C 의 차이가 #154 가 더한 값이다.** A 와 B 만 재면 "워밍업이 효과 있다" 까지만 알고,
그중 쓰기 워밍업 몫은 여전히 모른다.

**B 를 먼저 돌린다.** A 는 p99 가 크게 튀는 회차라 인스턴스에 부하가 가장 크고, 먼저 돌리면
그 여파가 다음 회차에 남을 수 있다.

### 회차를 어떻게 가르나

`compose.yaml` 의 `environment:` 블록에 없는 변수는 컨테이너에 안 들어간다. `.env` 는 보간용이라
거기 넣어도 안 닿는다. 대신 systemd 가 `/opt/freshmarket` 에서 `docker compose` 를 돌리므로
**override 파일이 자동으로 합쳐진다.**

```yaml
# /opt/freshmarket/compose.override.yaml
services:
  app:
    environment:
      COUPON_WARMUP_WRITEROWS: "0"
```

**`restart` 가 아니라 `stop` 후 `start` 다.** 컨테이너를 새로 만들어야 JVM 이 진짜로 다시
차가워진다. 재시작으로 때우면 앞 회차가 데워 놓은 것을 다음 회차가 물려받아 **세 회차가 사실은
같은 조건**이 된다. 이 시험에서 가장 틀리기 쉬운 자리다.

**조건을 걸었다고 믿지 않고 로그로 확인한다.** 회차마다 다른 줄이 남는다.

```
B   event=COUPON_WRITE_WARMUP_DONE rows=5000 chunk=500 elapsedMs=..
C   그 줄이 없다. 읽기 워밍업 완료 줄만 남는다
A   워밍업 로그가 아예 없다. CouponWarmupRunner:114 가 곧바로 반환한다
```

### 공통 조건

| | |
|---|---|
| 백엔드 커밋 | `c09f779a` (#154 포함) |
| k6 | v1.7.1 |
| 전용 | `t3.small` 3대 |
| 앱 / 배치 | `t3.small` 1대씩 |
| DB | `db.t4g.micro`, Multi-AZ, `max_connections` 60 |
| 캐시 | `cache.t4g.micro` 2노드, 자동 페일오버 |
| DB 커넥션 | 37 / 60 (앱 24 + 배치 4 + 관리 3 + 전용 6) |
| 시드 | 더미 회원 100만, 발급 이력 300만, 상태 이력 420만, 시험 회원 2만 |
| 시나리오 | 20,000 VU / ramp 60초 / hold 30초 / `MAX_ATTEMPTS` 5 |

**RDS 가 이 회차에 갓 만들어졌다.** 시험 6분 전에 300만 행을 부었고 버퍼 풀이 그것으로 차 있다.
아래에서 2026-08-31 회차와 숫자가 갈리는 이유를 여기서 찾아야 한다.

### 커넥션 예산이 실측으로 읽혔다

`coupon-event.sh open 3` 이 백엔드의 풀 크기를 상수로 베끼지 않고 돌고 있는 인스턴스에게
물어본다. #154 의 `529d8baf` 가 계약으로 고정한 자리이고, 실제로 그렇게 돌았다.

```
앱 최대 3대 x 8 (실측) + 배치 4 (실측) + 관리 3 = 31
전용에 남는 여유 29 / 60
전용 3대 x 2 (실측) = 6
합계 37 / 60
```

#### 2026-08-31 회차와 직접 견주지 않는다

행으로 차 있었다.

**그래서 이 시험의 결론은 회차 사이 비교에서만 나온다.** B, C, A 는 같은 날 같은 인스턴스
같은 DB 상태에서 조건 하나만 갈라 쟀으므로 서로 견줄 수 있다.

#### 이 회차에서 못 잰 것

**컴파일 증가분을 못 냈다.** 회차 뒤 누적만 받았고(90,378 / 88,291 / 105,092ms) 회차 전 값을
안 찍어 두어 차이를 못 구한다. `process_cpu_usage` 도 순간값이라 회차가 끝난 뒤에 읽어
0.4~1.6% 만 보였다. **C 와 A 는 회차 전후로 두 번 찍는다.**

#### 회차 순서가 결과를 오염시켰다

**B 를 먼저 돌린 것이 잘못이었다.** RDS 가 시험 6분 전에 만들어졌고 B 회차가 그 위에서
처음 돌았다. 버퍼 풀이 방금 부은 더미 300만 행으로 차 있었고, 발급 경로가 쓰는 인덱스가
디스크에 있었다.

**C 회차는 B 가 데워 놓은 DB 위에서 돌았다.** 같은 인덱스 페이지가 이미 버퍼 풀에 있다.

```
B   갓 만든 RDS. 버퍼 풀에 발급 경로가 없다        p99 1.38초
C   B 가 데운 RDS. 같은 페이지가 이미 올라 있다     p99 0.807초
```

**JVM 은 회차마다 새로 차갑게 만들었지만 DB 는 그러지 못했다.** 컨테이너를 새로 만들어 JIT 은
초기화했어도 RDS 버퍼 풀은 회차를 건너 남는다. 그래서 **뒤에 도는 회차일수록 유리하다.**

`t3.small` 세 대에 `db.t4g.micro` 라 버퍼 풀이 작고, 더미 300만 행이 그 작은 공간을 두고
발급 경로와 다툰다. 이 조건에서 순서 효과가 특히 크게 나온다.

**그래서 B 와 C 의 차이에서 #154 의 몫을 읽을 수 없다.** 바로잡으려면 A 를 돌린 뒤 B 를 한 번
더 돌려야 한다(B'). B' 가 C 와 비슷하게 나오면 B 의 1.38초는 DB 가 차가웠던 것이지 쓰기
워밍업 탓이 아니다.

#### k6 시나리오가 410 을 모른다

**`coupon_unexpected` 가 9,986건 나왔다.** 임계가 깨졌지만 서버 결함이 아니다.

```js
http.setResponseCallback(http.expectedStatuses(200, 409, 422, 503));
```

`feat/coupon-sold-out-final` 이 **회수 여지가 없는 소진을 410 으로 끊도록** 바꿨는데
(`fm-backend` `917cc30c`), 시나리오의 기대 목록에 410 이 없다. 그래서 정상 응답이
`http_req_failed` 로 세어졌다.

```
앱 지표   sold-out-final 18,986 - 워밍업 9,000 = 9,986      <- coupon_unexpected 와 정확히 같다
          sold-out(409) 14
```

**B 회차에서는 이것이 안 드러났다.** 그때는 요청이 느려 큐에 미결이 남아 있어 회수 여지가
있는 상태(409)로 답했고, C 는 재고가 깨끗하게 비어 최종 소진(410)에 닿았다. **같은 코드가
부하 조건에 따라 다른 코드로 답한 것이고, 그 갈림이 시나리오의 구멍을 드러냈다.**

고칠 곳은 `fm-backend` 의 `loadtest/issue.js` 다. 410 을 기대 목록에 넣고 "다시 안 쏨" 으로
분류해야 한다. 409 와 같은 뜻이고 오히려 더 확정적이다.

### 세 회차를 나란히 놓으면

| | 워밍업 | DB 버퍼 풀 | p99 | 혼잡 | 200 응답 발급 |
|---|---|---|---:|---|---:|
| **B** | 읽기 + 쓰기 | **차가움** (첫 회차) | 1.38초 | `budget` 16,418 | 5,996 |
| **C** | 읽기만 | 데워짐 (둘째) | **0.807초** | `budget` 160 | 9,837 |
| **A** | 없음 | 데워짐 (셋째) | 2.34초 | `seq-unavailable` 19 | 10,000 |

**정합성은 세 회차 모두 완벽하다.** 재고 10,000 정확히, 구멍 0, 1인 1매.

#### A 와 C 의 비교가 이 시험의 결론이다

둘 다 데워진 DB 위에서 돌았고 **워밍업 유무만 다르다.**

```
워밍업 없음   p99 2.34초    미달
읽기 워밍업   p99 0.807초   통과
```

**워밍업이 p99 를 2.9배 낮추고 SLO 안으로 들여놓는다.** 이 문서 1절이 제기한 문제에 대한
답이고, 설계가 코드가 되어 실제로 작동한다는 것이 여기서 확인됐다.

**막힌 자리가 서로 다르다는 것도 읽힌다.** A 는 혼잡이 거의 없이 느렸다. 큐가 밀린 것이 아니라
요청 하나하나가 느린 것이고, 그것이 정확히 JIT 이 안 된 상태의 모양이다.

#### 쓰기 워밍업의 몫은 아직 모른다

**B 만 차가운 DB 위에서 돌아 C 와 견줄 수 없다.** B 를 한 번 더 돌려야 한다(B'). 지금은
DB 가 세 회차를 거쳐 충분히 데워져 있으므로, B' 는 C 와 같은 DB 조건에서 잰다.

```
B' 가 C 와 비슷하다      쓰기 워밍업은 이 부하대에서 티가 안 난다. B 의 1.38초는 DB 탓이었다
B' 가 C 보다 좋다        쓰기 워밍업이 기여한다
B' 가 다시 1.38초쯤이다   쓰기 워밍업이 오히려 해가 된다. 그때는 이유를 따로 찾아야 한다
```

#### 토큰이 시험 도중에 만료됐다

A 회차 직전에 이벤트 열기가 401 로 돌아왔다. 토큰이 만료되어 있었다.

```
지금   1788533718
exp    1788530984      45분 전에 지났다
iat    1788509384      exp - iat = 21,600초 = 6시간
```

**그런데 생성기가 뜬 지 40분밖에 안 됐다.** 인스턴스 시계가 부팅 뒤 6시간 넘게 앞으로 뛴 것으로
보인다. 같은 명령 안에서 파일 mtime 은 `14:55 UTC` 인데 C 회차 k6 로그는 `08:23Z` 였다.

**회차마다 다시 찍는 것이 안전하다.** 지금 절차는 "시험 직전에 다시 찍어라" 로 되어 있는데,
그 "직전" 이 회차 하나가 아니라 세 회차를 통틀어서로 읽히기 쉽다. `refresh.sh` 는 몇 초면
끝나므로 회차마다 부르는 편이 낫다.
