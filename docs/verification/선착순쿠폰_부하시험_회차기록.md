# 선착순 쿠폰 부하 시험 회차 기록

요구 조건은 **재고 10,000장에 20,000명이 60초에 걸쳐 몰리는 것**이다.

2026-08-30 에 두 회차를 돌렸다. **두 번 다 요구 조건을 못 맞췄다.**
재고 1만 중 실제로 나간 것이 494장과 598장이다.

이 문서는 그 두 회차에서 나온 수치와, 거기서 확정한 원인을 남긴다.
지표 원본은 `loadtest-runs/` 에 있으나 gitignore 대상이라 이 문서가 유일한 기록이다.

---

## 1. 한눈에 보기

| | 1차 | 2차 | 목표 |
|---|---:|---:|---|
| 발급 성공 (사용자가 받은 200) | 199 | 598 | 10,000 |
| DB 실제 발급 | **494** | (미측정) | 10,000 |
| 혼잡 503 | 19,801 | 15,269 | - |
| 예상 밖 응답 | 0 | **4,133** | 0 |
| p95 응답 시간 | 10.41초 | **45.54초** | 2초 |
| 최대 응답 시간 | 14.45초 | 56.81초 | - |
| 연결 실패 | 0 | 0 | 0 |

**부하 생성기는 두 번 다 제 몫을 했다.** 2만 VU 에 정확히 도달했고, 요청 2만 건을 다 보냈고,
버려진 반복이 0 이었다. 그러니 위 숫자는 생성기의 한계가 아니라 시스템의 실제 응답이다.

## 2. 가장 중요한 발견: 죽은 재고

1차에서 DB 를 직접 세어 보니 이렇다.

```
DB 에 실제로 들어간 발급    494 건
사용자가 200 을 받은 것     199 건
                          ─────────
차이                       295 건
```

**295명이 "요청이 몰려 처리하지 못했습니다"(503)를 받았는데, 실제로는 발급됐다.**

사용자는 실패한 줄 알고 돌아오지 않는다. 그 쿠폰은 누구도 쓰지 않는 죽은 재고가 된다.
재고는 줄었는데 아무도 이득을 못 본다.

`application-coupon.yml` 이 이 상황을 미리 경고하고 있었다.

> 안쪽이 더 길면 요청 스레드가 먼저 포기해 혼잡으로 답한 뒤에 그 배치가 커밋된다.
> 실패했다고 답했는데 발급된 상태가 되고, 사용자가 안 돌아오면 그 슬롯은 죽은 재고가 된다.

요청 예산이 800ms 인데 실제 응답이 10초를 넘었으니, 예산 계층이 이미 무의미한 구간이었다.

**2차는 `verify` 를 안 돌려서 죽은 재고가 몇 건인지 모른다.** 다음 회차부터 반드시 잰다.

한편 정합성 자체는 지켜졌다. 순번에 구멍이 없었고(`gap = 0`), 한 사람이 두 장을 받은 경우도 없었다
(`members = issued_rows`). 재고를 넘겨 발급된 것도 없다.

## 3. 왜 494장에서 멈췄나

### 3.1 무죄가 증명된 것들

측정으로 하나씩 지웠다. 아래는 전부 한가했다.

| 후보 | 실측 | 판정 |
|---|---|---|
| 부하 생성기 | `blocked` 9ms, `connecting` 2ms, 버려진 반복 0 | 무죄 |
| 전용 서버 CPU | 3대 평균 **23.2%** | 무죄 |
| Redis 서버 | 189 명령/초, 명령 소요 0초대 | 무죄 |
| MySQL | 실행 스레드 2, 슬로우 쿼리 0, 잠금 대기 0 | 무죄 |
| DB 커넥션 풀 | 대기(pending) **0** | 무죄 |
| ALB 라우팅 | 일반 앱은 69건만 처리 | 정상 |

k6 의 응답 시간 분해가 결정적이었다.

```
blocked      0.009초   연결 대기
connecting   0.002초   TCP 핸드셰이크
sending      0.001초
waiting     12.913초   <- 전부 여기
receiving    0.000초
```

**네트워크도 클라이언트도 아니다. 서버가 요청을 12.9초 붙잡고 있었다.**
그러면서 CPU 도 DB 도 안 썼다.

### 3.2 진짜 원인: 순번 확보 회로가 열려 있었다

2차에서 앱이 내보내는 원인별 카운터를 받아 확정했다.

```
congested-seq-unavailable   14,989   <- 압도적
issued                         598
congested-budget               210
congested-db-failed              1
```

로그로 한 겹 더 들어가면 이렇게 갈린다.

```
회로 열림 (CallNotPermitted)   15,054
Redis 무응답 (DataAccess)           4
Lettuce 타임아웃                1,198
```

**일어난 일의 순서**

1. Redis 호출 일부가 100ms 안에 안 끝난다 (Lettuce 타임아웃 1,198건)
2. 순번 확보 회로가 이것을 실패로 세고, 실패율 50% 를 넘겨 **회로가 열린다**
3. 열린 동안(10초) 들어오는 요청은 **Redis 에 가보지도 않고 즉시 거절**된다
4. 반열림 상태에서 5건을 시험 삼아 보내지만 또 느리다 -> 다시 열린다
5. 이 진동이 반복되어 15,054건이 차단되고, 틈새로 빠져나간 598건만 발급된다

1차에서 Redis 의 `evalsha` 명령이 494번만 실행된 것이 이것으로 설명된다.
**회로가 대부분의 시간 열려 있어 순번 확보가 Redis 까지 도달하지 못했다.**

### 3.3 그런데 Redis 는 한가했다

여기가 이 시험의 핵심이다.

```
Redis 명령 처리     189 건/초
Redis 명령 소요     0초대
연결된 클라이언트    11
```

**Redis 서버는 놀고 있었는데 클라이언트는 타임아웃을 겪었다.**

2만 개 요청이 인스턴스당 하나의 Lettuce 연결로 몰리면 명령이 클라이언트 큐에 줄을 선다.
Redis 는 각 명령을 마이크로초에 처리하지만, 큐에서 기다린 시간까지 합치면 왕복이 50ms 를 넘는다.

회로의 `slow-call-duration` 이 50ms 다. 그래서 회로는 **Redis 장애가 아니라 자기 쪽 큐 대기를
장애로 판정했다.** 보호하려던 대상과 실제로 잡은 것이 달랐다.

## 4. 회차별로 무엇이 달랐나

### 1차 (18:30 UTC)

첫 실행. 전용 서버의 앱 지표를 **하나도 못 받았다.**

Prometheus 의 `app`/`batch` 스크랩 설정이 `tag:Role` 에 값을 박아 두어 `coupon` 이 어디에도
들어가지 않았다. `node` 와 `cadvisor` 는 Role 을 값으로 안 걸러서 잡혔기 때문에 호스트 지표는
보였고, **그래서 빠진 줄도 몰랐다.**

원인 분석을 못 하고 추측만 남았다. 이후 `coupon` job 을 추가했다.

### 2차 (19:30 UTC)

`rewriteBatchedStatements` 를 켜고 전용 서버를 교체한 뒤 실행했다.

발급이 199 -> 598 로 늘었지만 **지연은 오히려 나빠졌다** (p95 10.4초 -> 45.5초).
`coupon_unexpected` 4,133건이 새로 생겼다. 전용 서버 로그에 없으니 ALB 가 낸 응답이고,
최대 응답이 56.8초까지 늘어 ALB 유휴 타임아웃(기본 60초)에 근접한 것과 맞물린다.

통과량이 늘면서 회로의 열림/닫힘 진동이 심해진 것으로 보이나, **확정하지 못했다.**

## 5. 시험 중에 고친 것들

부하를 거는 과정에서 드러난 문제들이다. 시험 자체보다 이쪽 수확이 컸다.

| 문제 | 어떻게 드러났나 | 조치 |
|---|---|---|
| 전용 서버가 기동조차 못 함 | `connectionTimeout cannot be less than 250ms`. HikariCP 하한에 걸려 있었다 | 백엔드가 타임아웃 계층을 다시 세움 (요청 예산 800ms) |
| 전용 서버 앱 지표 미수집 | 1차에서 시험 대상의 지표가 전무 | `prometheus.yml` 에 `coupon` job 추가 |
| `rewriteBatchedStatements` 미적용 | 494행이 495개의 INSERT 문으로 나감 | 드라이버 옵션을 `data-source-properties` 로 이관 |
| 배치 서버 메모리 고갈 | 여유 103 MiB. SSM 에이전트와 익스포터가 죽었는데 **JVM 만 살아 `up=1` 로 보였다** | t3.micro -> t3.small |
| 여러 대가 한 이름으로 겹침 | 전용 3대가 모두 `freshmarket-coupon` 으로 표시 | 모든 EC2 job 에 `instance_id` 라벨 추가 |

### `rewriteBatchedStatements` 의 효과

| | 1차 (적용 전) | 2차 (적용 후) |
|---|---:|---:|
| 발급 행수 | 494 | 598 |
| INSERT 문장 수 | **495** | **121** |
| 플러시 횟수 (COMMIT) | 14 | 21 |
| 문장당 행수 | **1.0** | **약 4.9** |

발급은 21% 늘었는데 INSERT 문장은 4분의 1로 줄었다. **옵션이 실제로 물렸다.**

다만 이상적으로는 플러시 1회당 INSERT 1문장이어야 하는데 5.8문장이다.
`flushOneByOne` 폴백, 드라이버의 재작성 크기 한도, 3대 분산 중 무엇인지는 아직 모른다.

**그리고 이것은 병목이 아니었다.** 같은 구간 DB 질의가 1,153회뿐이라 DB 는 거의 놀았다.
494건만 큐에 들어온 것이 결과이지 원인이다. 통과량이 늘었을 때를 대비한 조치다.

### 배치 서버 사건이 남긴 교훈

`up = 1` 이 정상을 뜻하지 않았다. JVM 만 살아남아 Prometheus 는 계속 정상으로 보고했고,
죽은 것은 SSM 에이전트와 익스포터였다. **SSM 명령이 `Undeliverable` 로 떨어지고 나서야 드러났다.**

관측 도구 자신의 실명(失明)은 그 도구가 못 잡는다.
`node` 와 `cadvisor` job 의 `up=0` 에 알람을 걸면 이런 것을 바로 잡는다. (미조치)

## 6. 다음 회차에서 할 일

### 백엔드가 정해야 할 것

병목이 인프라가 아니라 **Redis 클라이언트 설정과 회로 임계값**에 있다.

- `slow-call-duration: 50ms` 가 클라이언트 큐 대기까지 장애로 센다. 이 값이 맞는가
- Lettuce 연결 하나로 2만 동시 요청을 받는 구조가 맞는가 (풀 또는 다중 연결)
- `redis.timeout: 100ms` 를 유지할 것인가
- 회로가 열렸을 때 10초 전면 차단이 이 이벤트에 맞는 대응인가

### 측정에서 보완할 것

- **`verify` 를 매 회차 돌린다.** 2차는 죽은 재고를 모른다
- **k6 요약 출력을 파일로 남긴다.** 지금은 화면에만 나오고 사라진다
- `coupon_unexpected` 의 실제 상태 코드를 잡는다 (ALB 접근 로그 또는 k6 쪽 기록)

### 부하 수준

2만 VU 는 회로를 즉시 열어 버려서 **한 대의 용량을 재는 데 쓸 수 없다.**
낮은 부하(예: 500 -> 2,000 -> 5,000 VU)부터 올려 회로가 열리기 시작하는 지점을 먼저 찾는 편이 낫다.
그 지점이 곧 현재 구조의 실제 상한이다.

## 7. 시험 환경

두 회차 모두 같은 환경이다.

| | |
|---|---|
| 백엔드 커밋 | `4924810` |
| 앱 | t3.small 1대 (오토스케일링 min 1 / max 3) |
| 선착순 전용 | t3.small **3대** |
| 배치 | t3.small 1대 |
| DB | db.t4g.micro, Multi-AZ, `max_connections` 60 (실측) |
| 캐시 | cache.t4g.micro 2노드, 자동 페일오버 |
| 부하 생성기 | m7i-flex.large (2 vCPU / 8 GB), k6 1.7.1 |
| DB 커넥션 사용 | 37 / 60 |

**부하 생성기가 확정값과 다르다.** 원래 m7i.xlarge (4 vCPU / 16 GB) 였으나 이 계정이 프리 티어라
`RunInstances` 가 거부한다. 띄울 수 있는 여섯 중 메모리가 가장 큰 것이 m7i-flex.large 8 GB 다.

2만 VU 에 5.0 GB 를 쓰므로 8 GB 의 63% 다. 이번 두 회차에서는 버려진 반복이 0 이라 문제되지 않았다.
