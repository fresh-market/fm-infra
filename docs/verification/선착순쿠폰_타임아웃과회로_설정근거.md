# 선착순 쿠폰 타임아웃과 회로 설정 근거

**차가운 JVM 을 기준으로 값을 정한다.** 실제 이벤트는 늘 차가운 상태로 시작하기 때문이다.
`coupon-event.sh` 가 이벤트 직전에 전용 인스턴스를 띄우는 설계라, 데워진 상태를 기준으로
잡은 값은 정작 이벤트가 열리는 그 순간에 맞지 않는다.

회차별 결과는 [선착순쿠폰_부하시험_기록.md](선착순쿠폰_부하시험_기록.md) 에 있다.
이 문서는 그 회차들에서 나온 값으로 무엇을 어떻게 정할지를 다룬다.

---

## 1. 측정값

2026-08-30 부하 시험(VU 20,000 / 재고 10,000 / `t3.small` 3대)에서 잰 값이다.
**둘 다 정상 회차다.** 10,000건을 다 발급했고 실패가 0건이었다.

여기 적힌 값들이 아래 모든 판단의 근거다. 확정한 설정으로 다시 잰 회차는 6절에 있다.

| | 차가움 | 데워짐 |
|---|---:|---:|
| `couponSeq` 느린 호출 비율 (기준 50ms) | **69%** | 0% |
| `couponSeq` 실패 비율 | **0%** | 0% |
| `couponSeq` 호출 평균 | 17.7ms | 3.3ms |
| `couponSeq` 호출 최대 | **792ms** | 116ms |
| `couponWrite` 느린 호출 비율 (기준 150ms) | 0.9% | 0% |
| `couponWrite` 호출 최대 | 733ms | 77ms |
| 프로세스 CPU 최대 | **91%** | 30% |
| HikariCP 대기 스레드 최대 | 0 | 0 |
| HikariCP 커넥션 사용 최대 | 1 (풀 2) | 1 (풀 2) |

**느림 69% 에 실패 0%.** 임계가 50% 였으니 회로가 켜져 있었으면 열렸다. 그런데 그 회차는
아무 문제 없이 끝났다. 오판이 수치로 확정된 자리다.

## 2. 원칙: 느림 문턱은 그 호출의 타임아웃보다 뒤여야 한다

지금까지의 주석은 반대로 적고 있었다.

> Redis 타임아웃보다 앞이어야 한다. 같으면 실제로 끊긴 호출만 세게 되어, 느려지는 구간에서
> 회로가 안 열리고 요청마다 타임아웃을 그대로 문다.

의도는 맞는데 전제가 틀렸다. **회로가 재는 것은 Redis 왕복이 아니라 `executeCallable` 이
도는 시간 전체다.** 거기에는 가상 스레드가 CPU 를 얻기까지 기다린 시간이 들어간다.

그리고 대상의 왕복은 이미 타임아웃으로 묶여 있다.

```
측정값 <= 타임아웃    대상의 지연일 수 있다
측정값 >  타임아웃    대상은 이미 실패로 확정됐어야 한다.  이 초과분은 내 앱의 지연이다
```

**792ms 짜리 호출이 성공했다는 것이 증거다.** Redis 타임아웃이 그보다 짧은데 성공했으므로,
그 시간의 상당 부분은 Redis 밖에서 온 것이다. 같은 시각 ElastiCache `EngineCPUUtilization`
은 3.7% 였고 평균 호출은 17.7ms 였다.

느림 문턱을 타임아웃 아래에 두면, 회로는 **대상의 상태가 아니라 자기 CPU 여유를 보게 된다.**

### 이것이 실제로 장애를 만들었다

같은 차가운 JVM 에서 순번 회로만 껐다.

| | 회로 켜짐 | 회로 꺼짐 |
|---|---:|---:|
| 혼잡 503 | 27,382 | **3** |
| 재시도 | 25,202 | 3 |
| 총 요청 | 45,202 | **20,003** |
| 발급 (DB 확인) | 8,870 | **10,000** |
| 살아남은 인스턴스 | 3 -> 2 | 3 유지 |

재고가 멀쩡히 남은 상태로 27,382건을 거절하고 있었다.

```
차가운 JVM  ->  요청당 CPU 5배  ->  2 vCPU 포화
  ->  스케줄 대기가 측정에 섞임  ->  느린 호출 비율 100%  ->  회로 열림
    ->  재고가 남아 있는데 503  ->  재시도로 요청 2.26배
      ->  CPU 100%  ->  헬스체크 초과  ->  ALB 퇴출, ASG 종료
```

## 3. 회로 설정

### `couponSeq` (Redis) 는 느림으로 열지 않는다

```yaml
couponSeq:
  slidingWindowType: TIME_BASED
  slidingWindowSize: 10
  minimumNumberOfCalls: 100
  failureRateThreshold: 50
  slowCallRateThreshold: 100      # 사실상 끔
  slowCallDurationThreshold: 50ms # 지표용으로 남긴다
```

`slowCallRateThreshold: 100` 은 "모든 호출이 느려야 연다" 라 사실상 끈 것이다.

**느림 문턱 50ms 는 지우지 않고 남긴다.** 이 값으로 회로가 열리지는 않지만
`resilience4j_circuitbreaker_slow_call_rate` 지표가 계속 나온다. 그 값이 곧 **인스턴스가
데워졌는지 보는 계기판**이다 (데워지면 0%, 차가우면 69%). 지우면 항상 0 이 되어 수단을 잃는다.

Redis 가 진짜 죽으면 타임아웃에서 실패로 확정되므로 `failureRateThreshold` 가 잡는다.
느림 판정은 그 위에 아무것도 더해 주지 않으면서 오판만 만든다.

> 지금 `CouponSeqAllocator` 가 기동할 때 이 회로를 `transitionToMetricsOnlyState()` 로
> 넘긴다. 위 설정과 무관하게 **아예 열리지 않는다.** 실패 판정까지 되살릴지는 Redis 장애
> 주입 시험 뒤에 정한다 (6절).

### `couponWrite` (DB) 는 켜 두되 문턱을 올린다

```yaml
couponWrite:
  slidingWindowType: TIME_BASED
  slidingWindowSize: 10
  minimumNumberOfCalls: 20
  failureRateThreshold: 50
  slowCallRateThreshold: 50
  slowCallDurationThreshold: 400ms   # socketTimeout 300ms 뒤
```

같은 원칙이다. `socketTimeout` 이 300ms 이니 그보다 긴 측정값은 DB 가 아니라 앱 지연이다.
150ms 였을 때 차가운 정상 회차에서 느린 비율이 0.9% 라 아직 여유가 있었지만, 성공한 호출의
최대가 733ms 까지 갔다. 부하가 세지면 비율이 오른다.

`socketTimeout` 을 250 에서 300 으로 올릴 때 문턱이 300 이라 같아졌고, 기존 시험
`회로_느림_기준이_대상_타임아웃보다_뒤다` 가 그것을 잡아 400 으로 올렸다. 같으면 실패로
확정되는 것과 느림으로 잡히는 것이 동시에 일어나 구분이 없어진다.

**이 회로는 끄지 않는다.** DB 가 죽었는데 순번을 계속 내주면 커밋 못 할 번호가 쌓여 죽은
재고가 된다. 순번 회로와 달리 막는 값어치가 분명하다. 이번 시험에서 이 회로는 한 번도
열리지 않았다 (`congested-write-circuit` 0건, `congested-db-failed` 0건).

### 창을 시간 기준으로 두는 것

둘 다 `TIME_BASED` 10초다. 건수 기준이면 유입이 빠를수록 판정 근거의 시간 폭이 좁아진다.
초당 2천이면 100건이 50밀리초 어치라 **GC 정지 하나가 창을 통째로 덮는다.** 실제로 그렇게
열린 적이 있다 (최대 정지 330ms, 느린 호출 비율 100%). 10초 창이면 그 정지가 3% 로 묻힌다.

## 4. 타임아웃

### 어느 값이 요청 스레드에 물리나

이 설계의 요점은 **요청 스레드가 트랜잭션을 열지 않는 것**이다. 순번을 받아 큐에 넣고
future 를 기다릴 뿐이고, DB 에 쓰는 것은 플러시 스레드다. 그래서 값마다 물리는 자리가 다르다.

확정된 값이다 (`fm-backend` `82daeb9`).

| 설정 | 값 | 요청 스레드가 무나 |
|---|---|---|
| `spring.data.redis.timeout` | **100ms** | **문다.** 요청당 2회 (아래) |
| `coupon.issue.commit-wait` | **800ms** | **문다.** 확정을 기다리는 상한 |
| `socketTimeout` (JDBC) | **300ms** | 안 문다. 플러시 스레드만 |
| `hikari.connection-timeout` | **300ms** | 안 문다 |
| `hikari.validation-timeout` | (안 적음) | 안 문다 |
| `spring.data.redis.connect-timeout` | (안 적음) | 안 문다 |

세 검산이 함께 성립한다.

```
SLO    redis.timeout 100 x 2 + commit-wait 800 = 1,000ms  <=  8장의 p99 1초
계층   commit-wait 800  >  connection-timeout 300 + socketTimeout 300 = 600
회수   reclaim-after 60s  >  commit-wait 800ms
```

### Redis 왕복이 요청당 둘인 것

`x 2` 의 근거다. 하나는 쿠폰 로직이 아니라 인증 공통 경로에 있다.

```
JwtAuthenticationFilter  ->  AccessTokenValidAfterRepository.isValidAfter()   GET
CouponSeqAllocator       ->  allocate()                                        EVALSHA
```

앞의 것은 **JWT 를 만료 전에 무효화하는 장치**다. 로그아웃이나 탈퇴로 토큰을 끊으려면 서버
쪽 기록이 필요해서, `accessTokenValidAfter:{role}:{id}` 에 커트라인 시각을 두고 매 요청 비교한다.
쿠폰과 무관하게 인증된 요청이면 전부 탄다.

**대부분의 요청에서 이 키가 없다.** 로그아웃하지 않은 사용자에게는 커트라인이 없어 `nil` 을
받고 통과한다. 부하 시험의 2만 명은 방금 토큰을 찍었으니 전원이 그 경우다. 즉 2만 번의
왕복이 "없음" 을 확인하려고 돈다.

줄이려면 이 조회를 로컬 캐시로 덮으면 된다. 그러면 왕복이 하나가 되어 `redis.timeout` 을
200ms 까지 쓸 수 있다. 다만 인증 공통 경로라 전 도메인에 영향이 가므로 아직 하지 않았다.

### `request-budget` 을 `commit-wait` 으로 고친 것

이름이 재는 구간보다 넓은 것을 가리켜, 값의 근거를 틀리게 만들었다.

재는 구간은 큐에 넣은 뒤부터다. **순번 확보는 이 밖에 있다.**

```
queue.submit  ->  큐 대기  ->  INSERT + COMMIT  ->  markCommitted  ->  future 완료
```

`flush` 가 아니라 `commit` 인 것은 DB 커밋과 Redis 확정 표시가 **모두** 끝나야 요청 스레드를
깨우기 때문이다. 순서를 뒤집으면 응답을 받은 사용자의 재시도가 표시보다 먼저 도착해 DB 까지 간다.

옛 이름은 "요청 시간 = 예산 + Redis" 를 전제하게 만들었다. 빠진 항이 **CPU 스케줄 대기**다.
차가운 회차에서 HTTP p95 가 1.02초였는데 예산 초과는 0건이었다. 그 시간의 대부분이 이 구간
밖에 있었다는 뜻이다.

### 지금 안 물리는 셋

**`hikari.connection-timeout`** 은 실측으로 한 번도 발동하지 않았다.

```
대기 스레드 최대   0     모든 회차, 모든 인스턴스
타임아웃 누적      0
사용중 최대        1     풀에 2개 있는데 1개만 썼다
획득 시간 최대     108.7ms   차가울 때조차
```

커넥션 소비자가 플러시 스레드 1 + 캐시 적재 1 = 2 인데 풀도 2 라 **경합이 구조적으로
불가능하다.** 이 값이 발동하려면 DB 가 죽어 커넥션 생성이 안 돼야 하는데, 그건 드라이버의
`connectTimeout: 250` 이 먼저 끊는다.

**`hikari.validation-timeout`** 은 **적어도 뜻이 없어서 안 적는다.** HikariCP 가
`Connection.isValid(int seconds)` 에 넘기려고 값을 초로 바꾸는데, 그 과정에 하한이 있다.

```
Math.max(1000, validationTimeout) / 1000  ->  isValid(초)

300  ->  max(1000, 300)  = 1000  ->  isValid(1)   1초
1000 ->  max(1000,1000)  = 1000  ->  isValid(1)   1초
5000 ->  max(1000,5000)  = 5000  ->  isValid(5)   5초
```

**300 이라고 적어도 실제로는 1초로 돈다.** `connection-timeout` 이 250ms 하한에 걸려 적힌
값과 도는 값이 갈렸던 것과 같은 함정이다. 그래서 아예 안 적고 `application.yml` 의 1s 를
물려받는다. 양쪽 다 지우면 HikariCP 기본 5초가 되어 더 나빠진다.

그 1초를 `connection-timeout` 이 못 끊는다. `HikariPool.getConnection` 이 검증을 마친
**뒤에야** 남은 예산을 다시 계산하기 때문이다 (바이트코드에서 `isConnectionDead` 호출이
`elapsedMillis` 재계산보다 앞선다). 그래서 borrow 한 번이 `commit-wait` 을 넘길 수 있다.

다만 검증은 500ms 넘게 논 커넥션에만 돌고(`aliveBypassWindowMs`) 건강하면 1ms 에 끝난다.
1초를 다 쓰는 것은 DB 가 응답을 안 할 때뿐이고, 그때는 `commit-wait` 이 끊는 것이 맞다.

**`spring.data.redis.connect-timeout`** 은 부하 경로에 없다. Lettuce 가 커넥션 하나를
공유하고 명령을 그 위로 다중화하므로, 2만 명이 몰려도 TCP 연결은 인스턴스당 하나다.
기동할 때와 재접속할 때만 물린다.

**`connection-timeout` 은 그래도 지우지 않는다.** 안 물리는 이유가
`maximum-pool-size: 2` 와 `flush-threads: 1` 에 걸려 있다. 둘 중 하나를 올리는 순간 경합이
생기고, 그때 값이 없으면 `application.yml` 의 3000ms 를 물려받아 **`commit-wait` 보다 긴
대기**가 된다.

### 계층은 역전되면 안 된다

```
요청 예산
  ├ 커넥션 획득
  └ 소켓 응답 대기      합이 요청 예산보다 짧아야 한다
Redis 왕복              예산 밖이다. 요청당 두 번이라 최악 왕복의 2배
```

안쪽이 더 길면 요청 스레드가 먼저 포기해 혼잡으로 답한 뒤에 그 INSERT 가 커밋된다.
**실패했다고 답했는데 발급된 상태**가 되고, 사용자가 안 돌아오면 그 쿠폰은 아무도 안 쓴다.

`connection-timeout` 을 250 보다 작게 못 잡는다. HikariCP 가 하한 250ms 를 강제하고 그보다
작은 값은 경고와 함께 조용히 250 으로 덮어쓴다. 한때 100 으로 적어 두고 100 + 250 = 350 이라
계산했는데 실제로 도는 값은 250 + 250 = 500 이었다. **적힌 값과 도는 값이 갈리면 계산이
통째로 거짓이 된다.**

## 5. 헬스체크가 사실상 가장 중요한 타임아웃이다

회로보다 이쪽이 위험하다. 차가운 상태 CPU 가 91% 라 `/actuator/health/readiness` 가
문턱을 넘길 여지가 있고, 넘기면 **인스턴스가 죽는다.**

발급 수가 살아남은 대수를 그대로 따라갔다.

| 회차 중 살아남은 대수 | 발급 |
|---|---:|
| 3 3 3 | 10,000 |
| 3 3 2 | 8,870 |
| 3 2 1 | 538 |

| | 전 | 후 |
|---|---|---|
| `timeout` | 5초 | **8초** |
| `unhealthy_threshold` | 2회 | **5회** |
| 퇴출까지 | 20초 | **50초** |
| ASG `health_check_type` | `ELB` | **`EC2`** |

`timeout` 을 `interval` 과 같은 10초로 둘 수는 없다. ALB 가
`Health check interval must be greater than the timeout` 으로 거절한다. 그래서 10 과 8 이다.

`EC2` 로 바꾼 것이 요점이다. `ELB` 면 **"ALB 에서 빼는 것" 과 "인스턴스를 죽이는 것" 이 한
판정에 묶인다.** 이벤트가 90초인데 그 안에 종료가 일어나면 기동 4~6분 동안 대수가 줄어든
채로 끝난다. 느려서 빠진 인스턴스는 부하가 걷히면 돌아오지만, 죽여 버리면 돌아올 것이 없다.

퇴출을 이벤트 길이(90초) 밖으로 밀지는 않았다. 그러면 정말로 죽은 인스턴스에도 100초 동안
요청이 간다. 50초가 "바쁜 것은 봐주고 죽은 것은 뺀다" 의 절충이다.

**앱 대상 그룹은 그대로 둔다** (10 / 5 / 2). 상시 서비스라 판단이 다르다. 완화한 것은
평상시 desired 0 으로 놀다가 이벤트 동안만 도는 선착순 전용 ASG 뿐이다.

이 넷은 `fm-infra` `d2ff115` 로 **적용을 마쳤다.** 다만 아직 이 완화가 값을 하는 상황을
겪지 못했다. 적용 후 회차들은 회로를 끈 뒤라 인스턴스가 죽지 않았다.

## 6. 아직 정하지 못한 것

### 차가운 상태에서는 p99 를 못 지킨다

**타임아웃으로 못 고치는 문제다.** 2026-08-31 에 같은 커밋, 같은 인스턴스로 두 번 쟀다.

| | 차가움 (05:33) | 데워짐 (06:28) |
|---|---:|---:|
| 발급 / 소진 | 9,979 / 10,000 | **10,000 / 10,000** |
| 실패율 | 0.00% | 0.00% |
| 혼잡 503 | 21 (`congested-budget`) | **0** |
| 504 / 502 / 연결 오류 | 0 / 0 / 0 | 0 / 0 / 0 |
| **p99** | **4.69초** | **0.247초** |

**발급 정확성은 차가워도 지켜진다.** 초과 발급 0, 인스턴스 유실 0, 서버 오류 0.
무너지지 않는다. 못 지키는 것은 p99 하나이고 그 차이가 19배다.

그 시간이 어디 있는지는 갈렸다. 앱이 잰 요청 최대가 5,638ms 이고 k6 가 잰 최대가 5,660ms 로
거의 같다. **ALB 큐잉이나 네트워크가 아니라 앱이 그만큼 붙잡고 있었다.**

| | 차가움 | 데워짐 |
|---|---:|---:|
| 동시에 앱 안에 머문 요청 최대 | **244** | 6 |
| 가장 오래 머문 요청 | **4,839ms** | 45ms |

`commit-wait` 이 800ms 라 확정 대기는 거기서 끊긴다. 그런데 4.8초를 머물렀다. **나머지
4초는 어느 타임아웃도 덮지 않는 구간**, 즉 가상 스레드가 CPU 를 얻기까지 기다린 시간이다.

무엇이 CPU 를 먹었나. 두 가지가 잡혔다.

```
JIT 컴파일 증가분   차가움 49,676ms / 데워짐 11,113ms   90초 회차 동안
node CPU steal      차가움 11.0%    / 데워짐 3.7%
```

**차가운 JVM 은 요청을 처리하면서 동시에 자기를 컴파일한다.** 90초 회차에서 49.7초어치를
컴파일했고, 그만큼이 요청 처리에서 빠졌다. steal 은 `t3.small` 이 공유 하드웨어라 생기는
것으로 우리 통제 밖이다.

고치는 길은 워밍업을 운영 절차로 넣는 것뿐이다. 아직 안 했다.

### 워밍업을 어떻게 넣을지

측정과 설계를 [선착순쿠폰_워밍업_설계와측정.md](선착순쿠폰_워밍업_설계와측정.md) 로 옮겼다.
요지는 셋이다.

* 본 시험 전에 **3,000건**을 흘리면 p99 가 4.69초에서 0.356초로 떨어진다
* 판정 기준은 컴파일 누적이 아니라 **처리한 요청 수**다. 통과 회차가 53~66k 에서 났다
* `ApplicationRunner` 에서 데우면 readiness 가 자연히 늦춰져 `coupon-event.sh` 의
  healthy 대기가 곧 warm 대기가 된다

아직 구현하지 않았다.

### `redis.connect-timeout` 을 얼마로 둘지

되돌릴 값 100ms 는 같은 VPC 안 핸드셰이크에는 넉넉하지만, 페일오버 직후 DNS 가 아직 옛
노드를 가리키면 시도마다 100ms 에 실패하고 재시도만 빠르게 반복한다. 1초 정도가 적당해
보이지만 **페일오버를 실제로 일으켜 재 본 적이 없어 근거가 약하다.**

### 순번 회로의 실패 판정을 되살릴지

지금은 `metrics-only` 라 실패에도 안 연다. 되살리면 Redis 장애 때 요청당 왕복 2회분을
아끼는데, 그 값어치가 오판 위험을 감수할 만한지 모른다. **Redis 를 실제로 죽여 보고 정한다.**

### 상한을 찾지 않았다

도착률 333건/초는 요구 조건이지 한계가 아니다. 어디서 무너지는지는 재지 않았다.
