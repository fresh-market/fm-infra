# 선착순 쿠폰 부하 시험 기록

`fm-backend` 의 [docs/coupon/requirement.md](https://github.com/fresh-market/fm-backend/blob/main/docs/coupon/requirement.md) 가 정한 조건을 실제로 재현하고 그 결과를 남긴다.

---

## 1. 합격 기준

기준이 두 층이다. **위는 요구사항이고 아래는 팀이 스스로 세운 것이다.**

### 요구사항 (requirement.md)

> 재고 10,000장에 20,000명이 동시에 요청해도 **초과 발급 0건, 1인 최대 1매.**
> ramp-up : 60s

요구사항이 재는 것은 **정합성**이다. 같은 문서가 이렇게도 적는다.

> 도구와 처리량은 평가하지 않는다.

### 팀 SLO (coupon.md 8장)

> 부하 시험 환경에서 요구 부하를 걸었을 때, **처리된 발급 응답의 p99 가 1초 이하다.**

요구사항이 지연을 안 재므로 이것은 팀이 추가로 건 기준이다.
"처리된 발급 응답"이라 **200 응답만 대상이다.** 409(소진)와 503(혼잡)은 제외한다.

## 2. 결과

**모든 기준을 통과했다.**

| | |
|---|---|
| 일시 | **2026-08-31 (일) 00:54:56 ~ 00:56:36 KST** |
| | (UTC 2026-08-30 15:54:56 ~ 15:56:36) |
| 소요 | 1분 31초 |
| 백엔드 커밋 | `a1590c7` |
| 전용 인스턴스 | `t3.small` 3대 |

| 항목 | 기준 | 실측 | |
|---|---|---:|---|
| 초과 발급 | 0건 | **0건** (10,000 / 재고 10,000) | 통과 |
| 1인 최대 | 1매 | **1매** | 통과 |
| 번호 유실 (`gap`) | 0 | **0** | 통과 |

| 최대 동시 사용자 | (정하지 않음) | **20,000 VU** | |
| **p99 (전체 응답)** | 1초 이하 | **0.508초** | 통과 |
| 실패율 | (정하지 않음) | **0.00%** | |
| 504 / 502 / 연결 오류 / Target 5xx | | **0 / 0 / 0 / 0** | |

**혼잡 503 이 0건이다.** 재시도도 0건이고 요청 수가 정확히 20,000 이다. 한 사람이 한 번 쏘고
받아 갔다는 뜻이고, 이 회차에는 서버 오류가 한 건도 없었다.

### 이 수치에는 조건이 둘 붙는다

같은 코드로도 조건이 어긋나면 발급이 538건까지 떨어진다. 무엇이 그것을 갈랐는지가 이 시험의
가장 큰 소득이라 먼저 적는다.

| | 순번 회로 켜짐 | 순번 회로 꺼짐 |
|---|---|---|
| **차가운 JVM** | 8,870건. 혼잡 27,382. 인스턴스 유실 | 10,000건. 혼잡 **3** |
| **데워진 JVM** | 10,000건. 혼잡 741. p99 0.347초 | **10,000건. 혼잡 0. p99 0.508초** |

**순번 확보 회로가 주범이었다.** 차가운 상태에서 회로만 빼면 혼잡이 27,382건에서 3건으로
사라진다. 자세한 것은 5절에 있다.

워밍업은 2차 변수다. 회로가 없으면 차가운 JVM 은 **느릴 뿐 실패하지 않는다**
(p95 1.02초 대 0.150초). 회로가 있으면 그 느림이 문턱을 넘어 장애로 바뀐다.

### ramp-up 이 실제로 60초에 걸쳐 일어났다

VU 와 누적 요청이 같은 기울기로 올라간다. VU 하나가 사람 하나이고 각자 한 번만 쏘기 때문이다.

```
시각(KST)      VU
00:55:15      2,138
00:55:25      5,472
00:55:35      8,809
00:55:45     12,138
00:55:55     15,472
00:56:05     18,805
00:56:15     20,000    <- 60초에 도달
```

초당 약 333명씩 들어와 60초에 20,000 에 닿는다.

**총 요청도 정확히 20,000 이다.** 503 이 없어 재시도가 없었으므로, 들어온 사람 수가 곧
요청 수다. 이전 회차들에서는 여기가 24,862 나 45,202 로 부풀었다.

### 사람 20,000명이 어떻게 끝났나

```
발급 200      10,000    재고를 정확히 소진
소진 409      10,000    늦게 와서 못 받음
혼잡 503           0
              ───────
합계          20,000
```

**포기한 사람이 없다.** 재시도가 0건이라 `http_reqs` 도 정확히 20,000 이다. 한 사람이 한 번
쏘고 결과를 받아 갔다.

`coupon_already_issued` 도 0 이다. 503 을 받았는데 사실은 커밋됐던 경우가 없었다는 뜻인데,
애초에 503 자체가 없었다.

### 재시도 경로는 이번에 안 탔다

시나리오에는 503 재시도가 그대로 있다 (4절). 다만 이 회차에서는 503 이 안 나와 한 번도
쓰이지 않았다. 재시도가 실제로 도는 것은 앞선 회차들에서 확인했다.

| 회차 | 혼잡 503 | 재시도 | 총 요청 |
|---|---:|---:|---:|
| 회로 켜짐, 차가움 | 27,382 | 25,202 | 45,202 |
| 회로 꺼짐, 차가움 | 3 | 3 | 20,003 |
| **회로 꺼짐, 데워짐** | **0** | **0** | **20,000** |

**재시도가 부하 증폭기라는 것이 이 표의 요점이다.** 503 이 늘면 요청이 2.26배로 불어나고,
그 부하가 다시 503 을 늘린다. 503 을 0 으로 만드는 것이 지연을 줄이는 것보다 크게 작용한다.

### 응답 세 가지가 각각 무엇인가

발급 요청 하나는 셋 중 하나로 끝난다. **셋 다 정상 응답이고 오류가 아니다.**

| 응답 | 코드 | 언제 나오나 | 사용자가 할 일 |
|---|---|---|---|
| **200** | `ISSUED` | 순번을 받고 DB 에 써졌다 | 없다. 받았다 |
| **409** | `COUPON-005` `SOLD_OUT` | Redis 카운터가 재고를 넘겼다 | **없다. 최종이다** |
| **503** | `COUPON-006` `CONGESTED` | 아래 아홉 갈래 중 하나 | **다시 시도하면 받을 수 있다** |

409 와 503 의 차이가 핵심이다. **409 는 최종이고 503 은 재시도할 값이 있다.**
`IssueResult` 주석이 그렇게 적는다. 409 는 "재고가 없다. 최종이라 다시 시도해도 같다".

`k6` 시나리오도 이 셋을 정상 응답으로 등록한다. 그래서 `http_req_failed` 가 진짜 오류만 센다.

```js
http.setResponseCallback(http.expectedStatuses(200, 409, 422, 503));
```

### 503 이 나오는 아홉 갈래

같은 503 이라도 원인이 다르다. 앱이 `coupon_issue_results_total` 로 원인별 건수를 내보낸다.
값은 모두 `fm-backend` 의 `application-coupon.yml` 에 있다.

| 태그 | 무슨 일인가 | 걸리는 값 |
|---|---|---|
| `congested-seq-unavailable` | Redis 가 순번을 못 주거나 순번 회로가 열렸다 | `redis.timeout 100ms`<br>순번 회로 (아래) |
| `congested-budget` | 플러시 결과를 요청 예산 안에 못 받았다 | `request-budget 800ms` |
| `congested-queue-full` | 큐가 상한에 닿아 순번을 받기 전에 끊었다 | `queue-capacity 20000` |
| `congested-write-circuit` | DB 쓰기 회로가 열렸다 | 쓰기 회로 (아래) |
| `congested-db-failed` | DB 쓰기가 실패했다 | `connection-timeout 300ms`<br>`connectTimeout 250ms`<br>`socketTimeout 250ms` |
| `congested-read` | 쿠폰이나 회원을 읽지 못했다 | 위와 같은 JDBC 값 |
| `congested-not-prepared` | Redis 카운터가 없다. 이벤트 준비 전이거나 재건 중이다 | 값 없음. `event:open` 미실행 |
| `congested-seq-taken` | 그 번호를 남이 쓰고 있다 | 값 없음 |
| `congested-aborted` | 배치가 통째로 어긋났거나 앱이 내려가는 중이다 | 값 없음 |

**이번 회차는 아홉 갈래가 모두 0 이다.** 503 이 한 건도 안 났다.

이전 회차들에서는 `congested-seq-unavailable` 하나가 최대 27,382건까지 났고 나머지 여덟은
늘 0 이었다. 그 한 갈래가 순번 확보 회로에서 나온 것이었다 (5절).

### 회로 둘의 현재 상태가 다르다

**순번 확보 회로는 지금 열리지 않는다.** `CouponSeqAllocator` 가 기동할 때
`transitionToMetricsOnlyState()` 로 넘겨 두어, 판정만 하고 요청은 막지 않는다.
5절이 그 이유다.

| | 순번 회로 (Redis) | 쓰기 회로 (DB) |
|---|---|---|
| **거절하나** | **아니다.** metrics-only | 그렇다 |
| 느림 판정 | 50ms | 150ms |
| 실패율 임계 | 50% | 50% |
| 관측 창 | 최근 10초 | 최근 10초 |
| 최소 호출 | 100회 | 20회 |
| 열림 유지 | - | 3초 |

값은 `application.yml` 의 `resilience4j.circuitbreaker.instances` 에 있다. 스프링 부트
스타터가 읽는다.

> `application-coupon.yml` 에 남아 있는 `coupon.circuit:` 블록은 **죽은 설정**이다.
> 그것을 바인딩하던 `CouponCircuitProperties` 가 지워졌는데 값만 남았다. 지워야 한다.

쓰기 회로는 그대로 둔다. DB 가 죽으면 순번을 받아 봐야 쓸 수 없고, 그때는 요청 예산을 다
태우기 전에 끊는 것이 맞기 때문이다. 그리고 이번 시험에서 이 회로는 **한 번도 열리지
않았다** (`congested-write-circuit` 0건, `congested-db-failed` 0건).

### 값들이 서로 물려 있다

```
요청 예산                800ms
  ├ 커넥션 획득          300ms    HikariCP 하한이 250ms 라 그 위로 잡았다
  └ 소켓 응답 대기       250ms
     합                  550ms  <  800ms      계층이 유지된다

Redis 왕복 상한          100ms    요청 예산 밖이다. 요청당 두 번 치므로 최악 200ms
  └ 회로 느림 판정        50ms    타임아웃보다 앞
```

**계층이 역전되면 안 된다.** 안쪽(DB)이 바깥쪽(요청 예산)보다 길면, 요청 스레드가 먼저
포기해 혼잡으로 답한 뒤에 그 INSERT 가 커밋된다. 실패했다고 답했는데 발급된 상태가 된다.

이 계층은 한 번 무너진 적이 있다. HikariCP 가 `connection-timeout` 하한 250ms 를 강제하는
것을 몰라 100 으로 적었고, 앱이 기동조차 못 했다. 5절에 있다.

### `congested-budget` 만 성격이 다르다

나머지 여덟은 **아무 일도 일어나지 않은 채** 끊긴 것이다. 이것 하나만 **일이 진행 중인 채로** 답한다.

경로는 이렇다 (`CouponIssueService.record` 와 `waitFor`).

```
1. 순번 확보        Redis 가 회원에게 번호를 배정한다
2. 큐 적재          queue.submit(ticket)
3. 대기             ticket.future().get(요청 예산 800ms)
4. 시간 초과        TimeoutException
5. 503 응답         congested(BUDGET_EXCEEDED)
```

**4번에서 떠나는 것은 기다리던 요청 스레드뿐이다.** 티켓은 큐에 그대로 남고 플러시 스레드가
결국 DB 에 쓴다. 그래서 사용자는 실패로 들었는데 실제로는 발급된 상태가 될 수 있다.

**회복 경로가 있다.** 사용자가 다시 시도하면 Redis 매핑이 같은 번호를 돌려주므로
번호가 새로 타지 않고, 응답도 200 이다.

```
재시도 -> SeqOutcome.AlreadyIssued -> 200 { issueSeq, alreadyIssued: true }
```

`CouponIssueResponse` 가 이 설계를 적고 있다.

> 서버가 "사용자가 다시 눌렀다" 와 "클라이언트가 자동으로 재시도했다" 를 구분하지 못하기 때문이다.
> 둘을 같은 200 으로 답하되 이 플래그로 화면을 가른다. 실패로 답하면 첫 응답을 잃은 사용자가
> 못 받은 줄 알고 계속 다시 눌러 그것이 다시 부하가 된다.

503 의 문구가 "잠시 후 다시 시도해주세요" 인 것도 그래서다. **재시도가 설계된 회복 수단이다.**

남는 구멍은 하나다. **사용자가 재시도하지 않으면** 그 쿠폰은 발급된 채로 아무도 안 쓴다.
재고는 줄었는데 쓰는 사람이 없다.

`reclaim-after: 60s` 가 이것을 완전히 막지는 못한다. 그 값은 소진 시점에 **커밋되지 않은**
번호를 회수하는 기준이라, 이미 커밋된 이 경우에는 해당하지 않는다.

이번 회차는 이 구멍이 열릴 일 자체가 없었다. 503 이 0건이라 "실패로 듣고 떠난 사람" 이
없다. `coupon_already_issued` 도 0 이다.

503 이 27,382건 나던 회차에서도 `coupon_already_issued` 는 0 이었다. 재시도가 전부 409 를
받았다는 뜻이고, 죽은 재고는 그때도 안 생겼다.

### 상태별 지연

| 응답 | 건수 | p99 | p95 | 평균 | 최대 |
|---|---:|---:|---:|---:|---:|
| 200 발급 | 10,000 | 0.070초 | 0.060초 | 0.040초 | 0.140초 |
| **409 소진** | 10,000 | **0.560초** | 0.330초 | 0.050초 | **1.080초** |
| 503 혼잡 | **0** | - | - | - | - |
| **전체** | 20,000 | **0.508초** | 0.150초 | 0.043초 | 1.070초 |

**전체 0.508초로 SLO 1초 대비 약 2배 여유다.**

**가장 느린 것은 409 다.** 평균은 0.050초로 200 과 비슷한데 p99 와 최대는 8배다.
소진 판정 자체는 Redis 한 번으로 끝나지만, **재고가 바닥나는 그 순간에 요청이 몰려**
꼬리가 길어진다. 전체 p99 0.508초를 만드는 것이 사실상 이 꼬리다.

**200 은 꼬리가 거의 없다** (p99 0.070초, 최대 0.140초). 발급을 받은 사람은 예외 없이 빨랐다.

**503 이 한 건도 없다.** 이전 회차들에서는 이 줄이 제일 컸다. 순번 확보 회로를 끈 것이
그 차이다 (5절).

### DB 정합성

시험이 끝난 뒤 DB 를 직접 세었다.

```sql
SELECT COUNT(*) AS issued_rows, MAX(issue_seq) AS max_seq,
       MAX(issue_seq) - COUNT(*) AS gap, COUNT(DISTINCT member_id) AS members
  FROM member_coupon WHERE coupon_id = 900001;
```

```
issued_rows  10000     재고 10,000 과 일치. 초과 발급 0
max_seq      10000
gap              0     번호만 태우고 사라진 요청이 없다
members      10000     한 사람이 두 장을 받은 경우가 없다
```

**k6 가 받은 200 응답 10,000건과 DB 행 10,000건이 일치한다.**
"실패했다고 답했는데 실제로는 발급된" 죽은 재고가 0건이라는 뜻이다.

## 3. 회차를 반복하는 방법

### 데이터는 쌓이지 않는다

회차마다 앞에서 되돌린다. 실제로 여러 회차를 돌린 뒤 센 값이다.

```
member_coupon 전체   3,010,000 행

  coupon 1       더미 한정 A      1,000,000    정합성 검증용. 회차와 무관하게 고정
  coupon 2       더미 한정 B      1,000,000    고정
  coupon 3       더미 무제한      1,000,000    고정
  coupon 900001  부하시험용          10,000    회차마다 지우고 다시 채운다
```

**시험 쿠폰이 정확히 10,000행이다.** 여러 회차를 돌렸지만 누적되지 않았다.

요구사항이 정한 더미데이터(가상 유저 100만, 발급 이력 300만)는 `더미%` 이름의 다른 쿠폰에
붙어 있어 되돌리기 대상이 아니다. 시험을 몇 번 돌려도 그대로 남는다.

### 순서

```
1. ./scripts/loadtest-seed.sh reset     DB 를 되돌린다
2. 관리자 API event:open                Redis 를 다시 세운다
3. k6 run issue.js                      시험
4. ./scripts/loadtest-seed.sh verify    DB 를 센다
```

**1번과 2번을 둘 다 해야 한다.** 하나만 하면 다음 회차가 망가진다.

| 빠뜨리면 | 무슨 일이 생기나 |
|---|---|
| 1번 (DB) | 재고가 이미 0 이라 전부 409 로 끝난다 |
| 2번 (Redis) | 회원별 순번 매핑이 남아 같은 회원이 전부 "이미 발급받음" 이 된다 |

### 1번이 지우는 것

`loadtest/reset.sql` 이고 **쿠폰 900001 것만 건드린다.**

```sql
DELETE FROM member_coupon_status_history WHERE member_coupon_id IN (...coupon_id = 900001);
DELETE FROM member_coupon WHERE coupon_id = 900001;
UPDATE coupon SET is_active = FALSE, issued_quantity = 0, ... WHERE coupon_id = 900001;
```

`is_active` 를 `FALSE` 로 내리는 것이 중요하다. 켜진 채로 두면 2번의 여는 API 가
"이미 열렸다" 로 그냥 돌아가 Redis 를 다시 세우지 않는다.

### 2번이 지우는 것

`reset.sql` 은 DB 만 되돌린다. **Redis 는 여는 API 가 되돌린다.**

`CouponSeqInitializer.prepare()` 가 카운터를 세우기 전에 먼저 네 키를 `UNLINK` 로 지운다.
주석이 그 이유를 적고 있다.

> 이 메서드가 먼저 지우는 것이 중요하다. 지난 이벤트의 매핑이 남아 있으면 스크립트가 그
> 회원들을 이미 발급받은 것으로 보고 새 이벤트에서 아무것도 안 준다.

`DEL` 이 아니라 `UNLINK` 인 것은 1만 필드 해시를 그 자리에서 해제하지 않고 백그라운드로
넘기기 위해서다.

### 토큰은 다시 안 찍어도 된다

`reset.sql` 이 `member_coupon` 을 비우므로 같은 회원 20,000명이 다시 받을 수 있다.

다만 토큰 수명이 6시간이라(`mint-tokens.py` 의 `VALIDITY_SECONDS`) 그보다 오래 걸리면
다시 찍어야 한다. 만료된 채로 돌리면 401 이 쏟아지는데 앱 장애처럼 보인다.

```
sudo /opt/loadtest/refresh.sh
```

### `issued_quantity` 는 회차 중에 0 이다

`coupon.issued_quantity` 컬럼은 발급할 때마다 오르지 않는다. **종료 배치가 실제 행 수로
덮어쓴다** (`CouponConsistencyScheduler`). 이벤트를 닫기 전에는 0 인 것이 정상이다.

발급 수를 확인할 때는 이 컬럼이 아니라 `member_coupon` 행을 세야 한다.
`verify` 가 그렇게 한다.

| 실행 명령 | `k6 run loadtest/issue.js` (덮어쓰는 값 없음) |

### VU 하나가 사람 하나다

`ramp-up` 은 **전체 사용자 수에 도달하기까지의 시간**이다 (JMeter 의 정의와 같다).
60초 뒤에 VU 가 20,000 이 되고, 그때까지 초당 333명이 들어온다.

VU 는 뜨자마자 자기 몫을 한 번 쏘고 그 뒤로는 안 쏜다. **VU 가 생기는 속도가 곧 도착률**이다.

```js
const index = exec.vu.idInTest - 1;        // VU 번호 = 사람 번호
if (settled) { sleep(1); return; }         // 결과가 확정된 사람은 안 쏜다
```

### 503 만 다시 쏜다

| 응답 | 다시 쏘나 |
|---|---|
| 200 | 안 쏨 |
| 409 소진 | 안 쏨. 최종이다 |
| **503 혼잡** | **쏜다.** 응답이 "잠시 후 다시 시도해주세요" 라고 말한다 |
| 422 / 404 | 안 쏨 |
| 연결 실패 | 안 쏨. 생성기 한계라 재시도로 덮으면 그것이 지표에서 사라진다 |

기다리는 시간은 서버의 `Retry-After` 헤더를 따른다. 지금 서버는 1초를 준다.

**`MAX_ATTEMPTS` 5 는 근거가 없는 값이다.** 실제 사람이 몇 번쯤 다시 누르다 포기하는지
재 본 적이 없다. 회차를 비교할 때 이 값이 같은지 확인해야 한다.

이번 회차에서는 503 이 안 나와 재시도가 한 번도 일어나지 않았다. 이 경로가 실제로 도는
것은 앞선 회차들에서 확인했다 (2절의 표).

## 5. 시험 중에 고친 것

부하를 거는 과정에서 드러난 문제들이다. **시험의 수확은 통과 자체보다 이쪽이 크다.**

| 문제 | 어떻게 드러났나 | 조치 |
|---|---|---|
| 전용 서버가 기동조차 못 함 | `connectionTimeout cannot be less than 250ms`. HikariCP 하한에 걸려 있었다 | 백엔드가 타임아웃 계층을 다시 세움 |
| `rewriteBatchedStatements` 미적용 | 494행이 495개의 INSERT 문으로 나감 | 드라이버 옵션을 `data-source-properties` 로 이관 |
| k6 임계가 SLO 와 달랐음 | `p(95)<2000` 을 통과해도 SLO(`p99<1000`) 통과인지 알 수 없었다 | 임계를 SLO 에 맞춤 |
| 전용 서버 앱 지표 미수집 | 정작 시험 대상의 지표가 전무했다 | `prometheus.yml` 에 `coupon` job 추가 |
| 여러 대가 한 이름으로 겹침 | 전용 3대가 모두 `freshmarket-coupon` 으로 표시 | 모든 EC2 job 에 `instance_id` 라벨 추가 |
| 배치 서버 메모리 고갈 | 여유 103 MiB. SSM 에이전트와 익스포터가 죽었는데 **JVM 만 살아 `up=1` 로 보였다** | t3.micro -> t3.small |
| **순번 확보 회로가 오진** | 재고가 남았는데 요청 27,382건을 거절 | 그 회로를 metrics-only 로 (아래) |
| 회로 지표가 아예 안 나옴 | 회로가 열려도 `/actuator/prometheus` 에 흔적이 없었다 | 설정을 resilience4j 스타터로 이관 (아래) |
| 마이그레이션 번호 충돌 | `Detected resolved migration not applied: 23`. DB 는 이미 V30 인데 새 파일이 V23 이었다. 앱 3대가 크래시 루프 | `V31` 로 올림 |

`up = 1` 건이 특히 남길 만하다. **`up = 1` 이 정상을 뜻하지 않았다.**
관측 도구 자신의 실명(失明)은 그 도구가 못 잡는다.

### 순번 확보 회로가 재고를 지키지 않고 이벤트를 망가뜨리고 있었다

**이 시험의 가장 큰 소득이다.** 회로를 끄기 전과 후를 같은 차가운 JVM 에서 쟀다.

| | 회로 켜짐 (11:37) | **회로 꺼짐 (15:49)** |
|---|---:|---:|
| 혼잡 503 | 27,382 | **3** |
| 재시도 | 25,202 | **3** |
| 총 요청 | 45,202 | **20,003** |
| 발급 (DB 확인) | 8,870 | **10,000** |
| 번호 유실 (`gap`) | 16 | **0** |
| 살아남은 대수 | 3 -> 2 | **3 유지** |
| 504 / 연결 오류 | 4,663 / 4,663 | **0 / 0** |

재고 10,000개가 멀쩡히 남아 있는데 요청 27,382건을 거절하고 있었다.

무엇이 잘못이었나. 회로의 느림 판정 기준이 **50ms** 인데, 그 값은 Redis 가 느린지를 보라고
정한 것이었다. 그런데 회로가 재는 것은 Redis 왕복이 아니라 **`executeCallable` 이 도는 시간
전체**다. 거기에는 가상 스레드가 CPU 를 얻기까지 기다린 시간이 들어간다.

```
차가운 JVM (인터프리터/C1)  ->  요청당 CPU 5배  ->  2 vCPU 포화
  ->  스케줄 대기가 측정에 섞임.  Redis 왕복 0.8ms 가 측정값 105~323ms 로
    ->  느린 호출 비율 100%  ->  회로 열림
      ->  재고가 남아 있는데 503
        ->  사용자가 재시도  ->  요청이 2.26배로 불어남
          ->  CPU 100%  ->  헬스체크 5초 초과  ->  ALB 퇴출, ASG 종료
```

**회로가 자기 앱의 느림을 Redis 장애로 오진했고, 그 오진이 진짜 장애를 만들었다.**
Redis 는 그동안 한가했다. ElastiCache `EngineCPUUtilization` 이 3.7% 였다.

조치는 `CouponSeqAllocator` 가 이 회로를 `transitionToMetricsOnlyState()` 로 넘기는 것이다.
판정과 지표는 그대로 두고 거절만 안 한다. 그래서 무엇이 느렸는지는 여전히 볼 수 있다.

Redis 가 진짜로 죽으면 어떻게 되나. 순번을 못 받아 `congested-seq-unavailable` 로 답하는
것은 같다. 회로는 그 판정을 **빨리** 하려던 장치였을 뿐이고, 그 대가가 오진이었다.

### 회로 지표가 처음부터 나오지 않고 있었다

위를 밝히는 데 하루가 걸린 이유다. 회로를 `CircuitBreaker.of` 로 따로 만들고 있어서
Micrometer 의 resilience4j 바인더가 그것을 보지 못했다. 회로가 열려 요청을 거절해도
`/actuator/prometheus` 에 아무것도 안 나왔다.

레지스트리에 등록해서 고치려다 **더 큰 문제를 만들었다.** 스프링 부트가 등록된 회로에
이벤트 소비자를 붙이는데, resilience4j 는 소비자가 없으면 이벤트를 아예 안 만든다
(`hasConsumers()` 로 먼저 거른다). 소비자가 붙는 순간 호출마다 이벤트 객체가
`ZonedDateTime.now()` 와 함께 생겼다.

```
GC 총 시간    1.49초  ->  2.64초
GC 최대 정지   104ms  ->  330ms      회로의 느림 기준 50ms 를 훌쩍 넘는다
발급          7,281  ->    295
```

**정지 한 번이 그 사이의 Redis 호출을 전부 느린 것으로 만들었다.** 지표를 보려다 지표가
재려던 현상을 만든 셈이다. 지금은 회로 설정을 스프링 부트 스타터로 옮겨 이 문제가 없다.

### 시나리오가 ramp-up 60초를 재현하지 못하고 있었다

가장 오래 걸린 문제다. **시험 도구 자신이 요구 조건과 달랐다.**

원래 시나리오는 이랬다.

```js
const index = exec.scenario.iterationInTest;   // 전역 반복 번호
http.post(...);
sleep(1);                                      // 1초 뒤 다시 발사
```

VU 가 1초마다 재발사하는데 토큰을 **전역 반복 번호**로 골랐다. 그래서 먼저 뜬 VU 가
뒤에 올 사람 몫까지 가져갔고, 램프가 끝나기 전에 2만 건이 소진됐다.

측정된 도착률이다. 요구 조건은 333건/초다.

| 설정 | 2만건 완료 | 도착률 |
|---|---:|---:|
| `VUS=20000` (1차) | 25초 | 800/s |
| `VUS=20000` (2차) | 55초 | 364/s |
| `VUS=5000` | 20초 | 1,000/s |
| `VUS=10000` | 15초 | 1,333/s |
| `VUS=20000` (재실행) | 10초 | **2,000/s** |

**같은 설정인데 364 와 2,000 으로 갈렸다.** `ramping-vus` 는 도착률을 정하지 않고,
VU 가 응답을 기다리는 동안 다음 요청을 못 보내기 때문이다. **앱이 느리면 부하가 저절로
약해지고 빠르면 세진다.** 시험이 스스로 봐주고 잘하면 벌을 주는 셈이었다.

그래서 그 전 회차들의 지연 수치는 서로 비교할 수 없다. 요구 조건보다 3배에서 6배 가혹한
조건에서 잰 것이라 이 문서에서 걷어냈다. **정합성 결과는 그 회차들에서도 항상 지켜졌다.**

고친 방법은 **VU 하나를 사람 하나로 묶고 한 번만 쏘게** 하는 것이다.

```js
const index = exec.vu.idInTest - 1;    // VU 번호 = 사람 번호
if (settled) { sleep(1); return; }     // 결과가 확정된 사람은 안 쏜다
```

중간에 `ramping-arrival-rate` 로도 바꿔 봤다. 도착률은 정확히 333건/초가 나왔지만
**VU 가 42개까지밖에 안 올라갔다.** 앱이 빨라 동시에 처리 중인 요청이 그만큼뿐이었다.
`ramp-up` 이 "전체 사용자 수에 도달하는 시간" 이라는 뜻을 잃어 되돌렸다.

## 6. 아직 확인하지 않은 것

### 워밍업 없이 이벤트를 열면 어떻게 되나

**이것이 지금 남은 가장 큰 위험이다.**

회로를 끈 뒤로 차가운 JVM 도 실패하지는 않는다. 다만 느리다.

| | 차가운 JVM | 데워진 JVM |
|---|---:|---:|
| p95 | 1.02초 | 0.150초 |
| p99 | **1초 초과 (미달)** | 0.508초 |
| 발급 | 10,000 | 10,000 |
| 실패율 | 0.00% | 0.00% |

**차가운 상태에서는 p99 를 못 맞춘다.** 발급 정확성은 지켜지지만 SLO 는 못 지킨다.

그리고 `coupon-event.sh` 는 이벤트 직전에 인스턴스를 띄우는 설계다. 그대로 두면 실제
이벤트는 항상 차가운 상태로 시작한다. 즉 **지금 통과 기록은 "데워져 있으면" 이라는 조건부다.**

무엇이 데워진 상태인지는 잴 수 있다.

| 지표 | 데워짐 | 차가움 |
|---|---:|---:|
| `jvm_compilation_time_ms_total` | 10만 이상 | 4만대 |
| `jvm_classes_loaded_classes` | 29,000 이상 | 28,100 대 |
| 회차 중 `process_cpu_usage` 최대 | 14~22% | 74~85% |

가동 시간이 아니라 **처리한 트래픽**이 기준이다. 5.5시간 놀고 있던 인스턴스보다 10분 동안
실제 발급을 받은 인스턴스가 더 데워져 있었다.

아직 안 한 것은 이것을 절차로 만드는 일이다. 별도 쿠폰으로 저부하를 흘려 발급 경로를 데운
뒤 본 이벤트를 여는 형태가 될 것이다. 본 쿠폰으로 데우면 재고가 줄어 쓸 수 없다.

### 헬스체크가 바쁜 인스턴스를 죽인다

회로를 끈 뒤로는 안 나타났지만 구조는 그대로다.

```
Interval 10초 / Timeout 5초 / Unhealthy 2회   ->  20초 안에 두 번 늦으면 퇴출
ASG HealthCheckType = ELB                     ->  퇴출되면 인스턴스를 종료한다
```

CPU 가 포화하면 `/actuator/health/readiness` 가 5초를 넘긴다. 이벤트가 90초인데 그 안에
퇴출과 종료가 일어나고, 새 인스턴스는 기동에 4~6분이라 회차 내내 복구되지 않는다. 3대가
2대가 되면 남은 쪽 부하가 50% 늘어 연쇄가 된다.

실제로 그렇게 무너진 회차들의 발급 수가 살아남은 대수를 그대로 따라갔다.

| 살아남은 대수 | 발급 |
|---|---:|
| 3 3 3 | 10,000 |
| 3 3 2 | 8,870 |
| 3 2 1 | 538 |

손볼 값은 셋이다. `Timeout` 5 -> 10초, `Unhealthy` 2 -> 5회, ASG 타입 `ELB` -> `EC2`.
마지막 것은 "ALB 에서 잠깐 빼는 것" 과 "인스턴스를 죽이는 것" 을 분리한다. 아직 안 했다.

### 요구 조건보다 세게 걸면 어디서 무너지나

이번 회차는 요구 조건을 통과했지만 **상한을 찾은 것은 아니다.**
도착률을 333건/초보다 올리면 무너지는 지점이 있다. 그 값은 재지 않았다.

### MAX_ATTEMPTS 5 가 적절한가

**`MAX_ATTEMPTS` 5 에 근거가 없다.** 실제 사람이 다섯 번까지 다시 누르는지 재 본 적이 없다.

지금은 503 이 0건이라 이 값이 결과에 영향을 주지 않는다. 다만 그것이 곧 안전하다는 뜻은
아니다. 회로를 끄기 전 회차에서 재시도가 요청을 2.26배로 불렸고 그 증폭이 무너짐의
직접 원인이었다. 503 이 다시 늘어나는 상황이 오면 이 값이 증폭 계수를 정한다.

### 그 밖

- 장애 주입 중의 거동 (앱/캐시/DB 각각). 특히 **Redis 를 실제로 죽였을 때**가 남았다.
  순번 확보 회로를 끈 뒤라 이 경로의 거동이 바뀌었는데 아직 확인하지 않았다
- 등급 제한이 걸린 쿠폰. 지금 시드는 `target_grade_id` 가 없어 `findMember` 를 한 번도
  호출하지 않는다. 등급을 걸면 요청마다 DB 왕복이 하나 늘어 결과가 달라진다
- `application-coupon.yml` 에 남은 죽은 `coupon.circuit:` 블록 정리 (3절 참고)
