# 선착순 쿠폰 부하 시험 기록

`fm-backend` 의 [docs/coupon/requirement.md](https://github.com/fresh-market/fm-backend/blob/main/docs/coupon/requirement.md) 가 정한 조건을 실제로 재현하고 그 결과를 남긴다.

---

## 1. 합격 기준

기준이 두 층이다. **위는 요구사항이고 아래는 팀이 스스로 세운 것이다.**

### 요구사항 (requirement.md)

> 재고 10,000장에 20,000명이 동시에 요청해도 **초과 발급 0건, 1인 최대 1매.**
> ramp-up : 60s

요구사항이 재는 것은 **정합성**이다. 같은 문서가 이렇게도 적는다.

> 도구와 처리량은 평가하지 않는다.

### 팀 SLO (coupon.md 8장)

> 부하 시험 환경에서 요구 부하를 걸었을 때, **처리된 발급 응답의 p99 가 1초 이하다.**

요구사항이 지연을 안 재므로 이것은 팀이 추가로 건 기준이다.
"처리된 발급 응답"이라 **200 응답만 대상이다.** 409(소진)와 503(혼잡)은 제외한다.

## 2. 5,000 VU: 두 기준을 모두 통과했다

| | |
|---|---|
| 일시 | **2026-08-30 (토) 12:59:15 ~ 13:00:46 KST** |
| | (UTC 03:59:15 ~ 04:00:46) |
| 소요 | 1분 31초 |
| 조건 | **동시 사용자 5,000 VU, ramp-up 60초** (+ 유지 30초) |

| 항목 | 기준 | 실측 | |
|---|---|---:|---|
| 초과 발급 | 0건 | **0건** | 통과 |
| 1인 최대 | 1매 | **1매** | 통과 |
| ramp-up | 60초 | 60초 | 통과 |
| 요청한 사람 | 20,000명 | 20,000명 | 통과 |
| 동시 사용자 | (정하지 않음) | **5,000 VU** | |
| p99 (200 응답) | 1초 이하 | **0.086초** | 통과 |

### 응답 세 가지가 각각 무엇인가

발급 요청 하나는 셋 중 하나로 끝난다. **셋 다 정상 응답이고 오류가 아니다.**

| 응답 | 코드 | 언제 나오나 | 사용자가 할 일 |
|---|---|---|---|
| **200** | `ISSUED` | 순번을 받고 DB 에 써졌다 | 없다. 받았다 |
| **409** | `COUPON-005` `SOLD_OUT` | Redis 카운터가 재고를 넘겼다 | **없다. 최종이다** |
| **503** | `COUPON-006` `CONGESTED` | 아래 아홉 갈래 중 하나 | **다시 시도하면 받을 수 있다** |

409 와 503 의 차이가 핵심이다. **409 는 최종이고 503 은 재시도할 값이 있다.**
`IssueResult` 주석이 그렇게 적는다. 409 는 "재고가 없다. 최종이라 다시 시도해도 같다".

`k6` 시나리오도 이 셋을 정상 응답으로 등록한다. 그래서 `http_req_failed` 가 진짜 오류만 센다.

```js
http.setResponseCallback(http.expectedStatuses(200, 409, 422, 503));
```

### 503 이 나오는 아홉 갈래

같은 503 이라도 원인이 다르다. 앱이 `coupon_issue_results_total` 로 원인별 건수를 내보낸다.

| 태그 | 무슨 일인가 |
|---|---|
| `congested-seq-unavailable` | Redis 가 답하지 않거나 순번 회로가 열렸다 |
| `congested-budget` | 요청 예산 안에 답을 못 받았다. 아래에 따로 적는다 |
| `congested-queue-full` | 큐가 상한에 닿아 순번을 받기 전에 끊었다 |
| `congested-write-circuit` | DB 쓰기가 계속 실패해 쓰기 회로가 열렸다 |
| `congested-db-failed` | DB 쓰기가 실패했다 |
| `congested-not-prepared` | Redis 카운터가 없다. 이벤트 준비 전이거나 재건 중이다 |
| `congested-seq-taken` | 그 번호를 남이 쓰고 있다 |
| `congested-read` | 쿠폰이나 회원을 읽지 못했다 |
| `congested-aborted` | 배치가 통째로 어긋났거나 앱이 내려가는 중이다 |

### `congested-budget` 만 성격이 다르다

나머지 여덟은 **아무 일도 일어나지 않은 채** 끊긴 것이다. 이것 하나만 **일이 진행 중인 채로** 답한다.

경로는 이렇다 (`CouponIssueService.record` 와 `waitFor`).

```
1. 순번 확보        Redis 가 회원에게 번호를 배정한다
2. 큐 적재          queue.submit(ticket)
3. 대기             ticket.future().get(요청 예산 800ms)
4. 시간 초과        TimeoutException
5. 503 응답         congested(BUDGET_EXCEEDED)
```

**4번에서 떠나는 것은 기다리던 요청 스레드뿐이다.** 티켓은 큐에 그대로 남고 플러시 스레드가
결국 DB 에 쓴다. 그래서 사용자는 실패로 들었는데 실제로는 발급된 상태가 될 수 있다.

**회복 경로가 있다.** 사용자가 다시 시도하면 Redis 매핑이 같은 번호를 돌려주므로
번호가 새로 타지 않고, 응답도 200 이다.

```
재시도 -> SeqOutcome.AlreadyIssued -> 200 { issueSeq, alreadyIssued: true }
```

`CouponIssueResponse` 가 이 설계를 적고 있다.

> 서버가 "사용자가 다시 눌렀다" 와 "클라이언트가 자동으로 재시도했다" 를 구분하지 못하기 때문이다.
> 둘을 같은 200 으로 답하되 이 플래그로 화면을 가른다. 실패로 답하면 첫 응답을 잃은 사용자가
> 못 받은 줄 알고 계속 다시 눌러 그것이 다시 부하가 된다.

503 의 문구가 "잠시 후 다시 시도해주세요" 인 것도 그래서다. **재시도가 설계된 회복 수단이다.**

남는 구멍은 하나다. **사용자가 재시도하지 않으면** 그 쿠폰은 발급된 채로 아무도 안 쓴다.
재고는 줄었는데 쓰는 사람이 없다.

`reclaim-after: 60s` 가 이것을 완전히 막지는 못한다. 그 값은 소진 시점에 **커밋되지 않은**
번호를 회수하는 기준이라, 이미 커밋된 이 경우에는 해당하지 않는다.

이번 회차는 503 이 0건이라 이 경로를 타지 않았다.

### 응답 분포

요청 20,000건이 하나도 실패하지 않았다.

| 응답 | 건수 | |
|---|---:|---|
| 200 발급 | **10,000** | 재고를 정확히 소진 |
| 409 소진 | 10,000 | 늦게 온 사람에게 정상 안내 |
| 503 혼잡 | **0** | 밀려서 못 받아 준 요청이 없다 |
| 그 밖 | 0 | |

### 상태별 지연

| 응답 | 건수 | p99 | p95 | 평균 | 최대 |
|---|---:|---:|---:|---:|---:|
| **200 발급** | 10,000 | **0.086초** | 0.060초 | 0.041초 | 0.108초 |
| 409 소진 | 10,000 | 0.106초 | 0.045초 | 0.013초 | 0.248초 |
| 503 혼잡 | **0** | 해당 없음 | 해당 없음 | 해당 없음 | 해당 없음 |

**SLO 판정은 200 만 본다.** 합격 기준이 "처리된 발급 응답" 이기 때문이다.
0.086초로 SLO 1초 대비 **약 12배 여유**다.

**409 는 200 보다 p99 가 높은데 평균은 3배 낮다.** 소진 판정은 Redis 를 한 번 치고 끝나
대부분 13밀리초에 답한다. 그런데 재고가 바닥나는 그 순간에 요청이 몰려 꼬리가 생긴다.
p99 0.106초와 최대 0.248초가 그 꼬리다.

**503 은 0건이라 지연 값이 없다.** 측정치가 0초라는 뜻이 아니라 잴 대상이 없다는 뜻이다.
이 조건에서는 밀려서 못 받아 준 요청이 하나도 없었다.

### DB 정합성

시험이 끝난 뒤 DB 를 직접 세었다.

```sql
SELECT COUNT(*) AS issued_rows, MAX(issue_seq) AS max_seq,
       MAX(issue_seq) - COUNT(*) AS gap, COUNT(DISTINCT member_id) AS members
  FROM member_coupon WHERE coupon_id = 900001;
```

```
issued_rows  10000     재고 10,000 과 일치. 초과 발급 0
max_seq      10000
gap              0     번호만 태우고 사라진 요청이 없다
members      10000     한 사람이 두 장을 받은 경우가 없다
```

**k6 가 받은 200 응답 10,000건과 DB 행 10,000건이 일치한다.**
"실패했다고 답했는데 실제로는 발급된" 죽은 재고가 0건이라는 뜻이다.

## 3. 10,000 VU: 요구사항은 통과하고 SLO 는 미달이다

동시 사용자를 두 배로 올렸다. **요구사항은 그대로 통과하지만 팀 SLO 를 못 맞춘다.**

| | |
|---|---|
| 일시 | **2026-08-30 (토) 14:34:19 ~ 14:35:50 KST** |
| | (UTC 05:34:19 ~ 05:35:50) |
| 조건 | **동시 사용자 10,000 VU, ramp-up 60초** (+ 유지 30초) |

| 항목 | 기준 | 실측 | |
|---|---|---:|---|
| 초과 발급 | 0건 | **0건** | 통과 |
| 1인 최대 | 1매 | **1매** | 통과 |
| p99 (전체 응답) | 1초 이하 | **3.06초** | **미달** |

k6 가 임계로 자동 판정했다.

```
✗ 'p(99)<1000'  p(99)=3.06s
```

### 재고는 그대로 다 나갔다

```
issued_rows  10000     초과 발급 0
max_seq      10000
gap              0
members      10000     1인 1매
```

**정합성은 5,000 VU 와 똑같이 완전하다.** 무너진 것은 지연뿐이다.

### 어디서 느려졌나

| 응답 | 건수 | p99 | p95 | 평균 | 최대 |
|---|---:|---:|---:|---:|---:|
| 200 발급 | 10,000 | **0.125초** | 0.102초 | 0.055초 | 0.143초 |
| 409 소진 | 4,601 | 0.304초 | 0.227초 | 0.059초 | 0.328초 |
| **503 혼잡** | **5,399** | **3.877초** | 2.676초 | 1.033초 | 4.286초 |

**200 만 보면 0.125초로 여전히 여유가 크다.** 전체 p99 3.06초는 **503 이 만든 값이다.**

혼잡의 원인은 한 갈래다.

```
congested-seq-unavailable   5,399   (혼잡 전부)
```

Redis 순번 확보가 실패했거나 순번 회로가 열렸다는 뜻이다.

### 이 503 은 배압으로서 실패한 것이다

배압의 요점은 **빨리 거절하는 것**이다. 받을 수 없으면 즉시 돌려보내 자원을 아낀다.

그런데 이 거절은 p99 3.877초, 평균 1.033초가 걸렸다. **거절당한 요청도 그 시간 동안 스레드와
연결을 붙잡고 있었다.** 부하를 덜어 주기는커녕 더한 셈이다.

`congested-seq-unavailable` 로 가는 두 경로는 원래 둘 다 빠르다.

| 경로 | 걸리는 시간 |
|---|---|
| 회로가 열려 있음 (`CallNotPermitted`) | 즉시 |
| Redis 가 안 답함 (타임아웃) | 100ms |

**어느 쪽도 4초가 안 나온다.** 그 4초는 거절 판정에 도달하기 전에 어딘가에서 밀린 시간이고,
그 지점은 아직 특정하지 못했다.

### 지연을 200 만으로 재지 않는 이유

"성공 응답만 잰다" 는 관례가 있다. 빠른 실패가 지표를 좋게 왜곡하는 것을 막기 위해서다.
500 을 1밀리초에 뱉으면 p99 가 좋아 보인다.

**여기는 정반대다. 실패가 느리다.** 그래서 그 관례가 적용되지 않는다.
사용자는 응답 코드를 모른다. **4초 기다린 끝에 "다시 시도하세요" 를 받은 5,399명은
실제로 4초를 기다린 것이다.** 200 만 재면 그 경험이 지표에서 사라진다.

### 두 회차 비교

| | 5,000 VU | 10,000 VU |
|---|---:|---:|
| 발급 | 10,000 | 10,000 |
| 소진 409 | 10,000 | 4,601 |
| **혼잡 503** | **0** | **5,399** |
| p99 (전체) | 0.106초 | **3.06초** |
| p99 (200 만) | 0.086초 | 0.125초 |
| 초과 발급 | 0 | 0 |

**5,000 과 10,000 사이에 상한이 있다.** 5,000 에서는 혼잡이 한 건도 없다가
10,000 에서 5,399건이 된다. 그 사이 어디서 꺾이는지는 아직 재지 않았다.

## 4. 회차를 반복하는 방법

### 데이터는 쌓이지 않는다

회차마다 앞에서 되돌린다. 실제로 여러 회차를 돌린 뒤 센 값이다.

```
member_coupon 전체   3,010,000 행

  coupon 1       더미 한정 A      1,000,000    정합성 검증용. 회차와 무관하게 고정
  coupon 2       더미 한정 B      1,000,000    고정
  coupon 3       더미 무제한      1,000,000    고정
  coupon 900001  부하시험용          10,000    회차마다 지우고 다시 채운다
```

**시험 쿠폰이 정확히 10,000행이다.** 여러 회차를 돌렸지만 누적되지 않았다.

요구사항이 정한 더미데이터(가상 유저 100만, 발급 이력 300만)는 `더미%` 이름의 다른 쿠폰에
붙어 있어 되돌리기 대상이 아니다. 시험을 몇 번 돌려도 그대로 남는다.

### 순서

```
1. ./scripts/loadtest-seed.sh reset     DB 를 되돌린다
2. 관리자 API event:open                Redis 를 다시 세운다
3. k6 run issue.js                      시험
4. ./scripts/loadtest-seed.sh verify    DB 를 센다
```

**1번과 2번을 둘 다 해야 한다.** 하나만 하면 다음 회차가 망가진다.

| 빠뜨리면 | 무슨 일이 생기나 |
|---|---|
| 1번 (DB) | 재고가 이미 0 이라 전부 409 로 끝난다 |
| 2번 (Redis) | 회원별 순번 매핑이 남아 같은 회원이 전부 "이미 발급받음" 이 된다 |

### 1번이 지우는 것

`loadtest/reset.sql` 이고 **쿠폰 900001 것만 건드린다.**

```sql
DELETE FROM member_coupon_status_history WHERE member_coupon_id IN (...coupon_id = 900001);
DELETE FROM member_coupon WHERE coupon_id = 900001;
UPDATE coupon SET is_active = FALSE, issued_quantity = 0, ... WHERE coupon_id = 900001;
```

`is_active` 를 `FALSE` 로 내리는 것이 중요하다. 켜진 채로 두면 2번의 여는 API 가
"이미 열렸다" 로 그냥 돌아가 Redis 를 다시 세우지 않는다.

### 2번이 지우는 것

`reset.sql` 은 DB 만 되돌린다. **Redis 는 여는 API 가 되돌린다.**

`CouponSeqInitializer.prepare()` 가 카운터를 세우기 전에 먼저 네 키를 `UNLINK` 로 지운다.
주석이 그 이유를 적고 있다.

> 이 메서드가 먼저 지우는 것이 중요하다. 지난 이벤트의 매핑이 남아 있으면 스크립트가 그
> 회원들을 이미 발급받은 것으로 보고 새 이벤트에서 아무것도 안 준다.

`DEL` 이 아니라 `UNLINK` 인 것은 1만 필드 해시를 그 자리에서 해제하지 않고 백그라운드로
넘기기 위해서다.

### 토큰은 다시 안 찍어도 된다

`reset.sql` 이 `member_coupon` 을 비우므로 같은 회원 20,000명이 다시 받을 수 있다.

다만 토큰 수명이 6시간이라(`mint-tokens.py` 의 `VALIDITY_SECONDS`) 그보다 오래 걸리면
다시 찍어야 한다. 만료된 채로 돌리면 401 이 쏟아지는데 앱 장애처럼 보인다.

```
sudo /opt/loadtest/refresh.sh
```

### `issued_quantity` 는 회차 중에 0 이다

`coupon.issued_quantity` 컬럼은 발급할 때마다 오르지 않는다. **종료 배치가 실제 행 수로
덮어쓴다** (`CouponConsistencyScheduler`). 이벤트를 닫기 전에는 0 인 것이 정상이다.

발급 수를 확인할 때는 이 컬럼이 아니라 `member_coupon` 행을 세야 한다.
`verify` 가 그렇게 한다.

## 5. 시험 조건

두 회차의 조건은 **동시 사용자 수만 다르고 나머지는 같다.**

| | 5,000 VU 회차 | 10,000 VU 회차 |
|---|---|---|
| 시각 (UTC) | 03:59:15 ~ 04:00:46 | 05:34:19 ~ 05:35:50 |
| 동시 사용자 (VU) | 5,000 | 10,000 |
| ramp-up | 60초 (+ 유지 30초) | 같음 |
| 총 요청 | 20,000건 (회원 20,000명, 1인 1회) | 같음 |
| 시나리오 | `fm-backend` 의 `loadtest/issue.js` | 같음 |
| 백엔드 커밋 | `ee9d46f` | 같음 |
| 부하 생성기 | m7i-flex.large, k6 1.7.1 | 같음 |

### VU 를 바꿔도 요청하는 사람은 20,000명이다

요구사항은 **사람 수 20,000명**을 정하지 그 사람들이 동시에 몇 개의 연결을 쥐는지는 정하지 않는다.

`issue.js` 는 토큰을 VU 번호가 아니라 **반복 번호**(`exec.scenario.iterationInTest`)로 고른다.
그래서 VU 를 몇으로 두든 **서로 다른 회원 20,000명이 각자 한 번씩** 요청한다.
VU 는 그 20,000건이 동시에 몇 개씩 흐르는지만 정한다.

시나리오 주석이 이 설계를 적고 있다.

> VU 번호로 묶으면 VU 를 줄일 때 시도하는 사람 수도 같이 줄어, 재고 1만에 2만이 몰리는
> 조건 자체가 사라진다. 반복 번호로 고르면 VU 수는 동시성만 정하고 시도는 언제나 2만이다.

## 6. 시험 중에 고친 것

부하를 거는 과정에서 드러난 문제들이다. **시험의 수확은 통과 자체보다 이쪽이 크다.**

| 문제 | 어떻게 드러났나 | 조치 |
|---|---|---|
| 전용 서버가 기동조차 못 함 | `connectionTimeout cannot be less than 250ms`. HikariCP 하한에 걸려 있었다 | 백엔드가 타임아웃 계층을 다시 세움 |
| `rewriteBatchedStatements` 미적용 | 494행이 495개의 INSERT 문으로 나감 | 드라이버 옵션을 `data-source-properties` 로 이관 |
| k6 임계가 SLO 와 달랐음 | `p(95)<2000` 을 통과해도 SLO(`p99<1000`) 통과인지 알 수 없었다 | 임계를 SLO 에 맞춤 |
| 전용 서버 앱 지표 미수집 | 정작 시험 대상의 지표가 전무했다 | `prometheus.yml` 에 `coupon` job 추가 |
| 여러 대가 한 이름으로 겹침 | 전용 3대가 모두 `freshmarket-coupon` 으로 표시 | 모든 EC2 job 에 `instance_id` 라벨 추가 |
| 배치 서버 메모리 고갈 | 여유 103 MiB. SSM 에이전트와 익스포터가 죽었는데 **JVM 만 살아 `up=1` 로 보였다** | t3.micro -> t3.small |

마지막 것이 특히 남길 만하다. **`up = 1` 이 정상을 뜻하지 않았다.**
관측 도구 자신의 실명(失明)은 그 도구가 못 잡는다.

## 7. 아직 확인하지 않은 것

### 상한이 5,000 과 10,000 사이 어디인가

5,000 에서 혼잡이 0건이고 10,000 에서 5,399건이다. 그 사이를 좁히지 않았다.

### 503 이 4초나 걸리는 이유

배압은 즉시 거절해야 하는데 p99 3.877초가 나왔다. 그 경로의 두 갈래(회로 열림, Redis
타임아웃)는 각각 즉시와 100ms 라 이 값을 설명하지 못한다. **거절 판정에 도달하기 전에
밀리는 지점이 있고 아직 특정하지 못했다.**

### 그 밖

- 장애 주입 중의 거동 (앱/캐시/DB 각각)
- 워밍업 없이 시작했을 때의 첫 응답. JIT 이 덜 데워진 구간이 p99 를 크게 끌어올린다
