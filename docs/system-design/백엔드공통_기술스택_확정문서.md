# 백엔드 공통 기술 스택 확정 문서

작성 기준일: 2026-08-01
적용 대상: Spring Boot 기반 백엔드 프로젝트 (AWS 프리티어 크레딧 계정, 소규모 운영 및 검증 환경)

---

## 1. 문서 목적

본 문서는 애플리케이션, 데이터, 인프라, 관측성 전 영역의 기술 스택과 버전을 한곳에 고정한다. 특정 도메인에 의존하지 않으며, 신규 백엔드 프로젝트의 출발점으로 그대로 재사용할 수 있도록 작성한다.

버전을 문서로 못 박는 이유는 두 가지다.

1. 로컬, CI, 운영의 버전이 어긋나면 "로컬은 되는데 운영에서 깨지는" 장애가 생긴다. 검증 대상이 아닌 원인이 섞이면 문제 해결 시간이 배로 든다.
2. 관리형 서비스는 사용자가 원하는 버전을 항상 제공하지 않는다. ElastiCache가 Redis OSS를 7.1에서 멈춰 세운 것이 대표적이며, 이런 제약은 설계 시점에 확인해야 나중에 되돌리지 않는다.

## 2. 확정 스택 전체 표

### 2.1 애플리케이션

Java 와 Spring Boot 버전, 애플리케이션 라이브러리는 **`fresh-market/fm-backend` 가 소유한다.**
`build.gradle` 과 1대1로 대응하고 인프라 결정에서 파생되지 않기 때문이다.

[be 의 docs/tech-stack.md](https://github.com/fresh-market/fm-backend/blob/main/docs/tech-stack.md)

여기서는 인프라가 강제하는 것만 다룬다. 2.3절의 데이터 버전이 그렇다.

| 익스포터 | 이미지 태그 | 포트 | 어디서 도나 | 대상 |
|----------|------------|------|------------|------|

| cAdvisor | `gcr.io/cadvisor/cadvisor:v0.55.1` | **8082** | **모든 인스턴스** | 그 호스트의 컨테이너 자원, OOM |
| mysqld_exporter | `prom/mysqld-exporter:v0.17.2` | 9104 | 모니터링 | RDS 엔드포인트에 원격 접속 |
| redis_exporter | `oliver006/redis_exporter:v1.69.0` | 9121 | 모니터링 | ElastiCache 엔드포인트에 원격 접속 |
| cloudwatch_exporter | `prom/cloudwatch-exporter:v0.16.0` | 9106 | 모니터링 | 관리형 서비스 호스트 지표와 페일오버 이벤트 |

**앞의 둘은 앱과 배치 인스턴스에도 뜬다.** 그 호스트의 상태를 봐야 하므로 모니터링이 각 인스턴스로 긁으러 간다. 뒤의 셋은 모니터링 안에서만 오간다.

**cAdvisor 기본 포트가 8080 이라 앱과 겹쳐 8082 로 옮겼다.** 포트 배정 전체는 `observability/README.md` 가 갖는다.

cAdvisor 는 `v0.53.0` 이 존재하지 않는다. v0.52.1 다음이 v0.54.1 이다. 태그를 확인하지 않고 적으면 apply 가 아니라 인스턴스가 뜬 뒤 컨테이너 기동에서 드러난다.

관리형 서비스는 OS 레벨 접근이 불가능하다. `mysqld_exporter`로 엔진 내부 지표를 보고 `cloudwatch_exporter`로 인스턴스 레벨 지표(CPU, 여유 메모리, 페일오버)를 함께 봐야 그림이 완성된다. 둘 중 하나만으로는 페일오버 순간을 설명할 수 없다.

**복제 지연(`ReplicaLag`)은 지금 수집 대상이 아니다.** 대기 인스턴스로의 복제는 동기라 지연이라는 값 자체가 없다. 이 지표는 읽기 복제본을 도입하는 시점부터 의미를 갖는다(앱과 DB 장애 대응 구조 4.9절).

## 3. 버전 선정 근거

### 3.1 Prometheus 3.13.x LTS

Prometheus는 6주마다 마이너 릴리스를 내고, 그중 일부를 LTS로 지정해 1년간 버그와 보안 수정을 제공한다. 일반 마이너는 6주가 지나면 사실상 수정을 받지 못한다.

2026-08-01 기준 직전 LTS인 3.5는 2026-07-31에 지원이 끝났고, 2026-07-01에 나온 3.13이 새 LTS로 2027-07-31까지 지원된다.

주의할 점은 Prometheus 3.x가 2.x 대비 TSDB 형식과 PromQL 정규식 동작이 바뀐 메이저 변경이라는 것이다. 신규 구축이라 마이그레이션 문제는 없지만, 인터넷에서 찾은 2.x 기준 설정 예제를 그대로 붙여 넣으면 어긋난다.

### 3.2 Valkey 9.0

**Redis가 아니라 Valkey를 쓴다.** 성능 때문이 아니라 ElastiCache에서 Redis OSS가 더 올라가지 않기 때문이다.

#### ElastiCache의 Redis OSS는 7.1에서 멈췄다

Redis Ltd가 2024년 3월에 7.4부터 라이선스를 SSPL과 RSALv2로 바꿨고, AWS는 그 시점의 마지막 오픈소스 판인 7.2.4를 포크해 Valkey를 만들었다. ElastiCache에서 Redis OSS로 고를 수 있는 최고 버전은 엔진 버전 7.1이며, 이는 업스트림 Redis OSS 7.0에 대응한다.

Redis는 2025년 5월 8.0부터 AGPLv3를 선택지로 추가했지만 **AWS는 그것을 받지 않았다.** 관리형 서비스 제공자에게 소스 공개 의무가 걸릴 수 있는 라이선스라서다. AWS는 기존 노드를 Valkey로 이관했고 ElastiCache의 Redis OSS는 7.1에서 동결된 상태다.

즉 Redis를 고르면 **지금 7.1이고 앞으로도 7.1이다.**

#### 버전 번호가 Redis와 대응하지 않는다

Valkey는 Redis 7.2.4에서 갈라져 나왔으므로 그 뒤의 Redis 버전과 번호가 짝을 이루지 않는다. **호환은 버전 대 버전이 아니라 명령어 단위로 봐야 한다.**

```
Redis 7.2.4  (BSD, 마지막 오픈소스 판)
    |
    +-- Valkey 7.2 -- 8.0 -- 8.1 -- 9.0 -- 9.1
    |
    +-- Redis 7.4 -- 8.0        SSPL / RSALv2 / AGPLv3
```

프로토콜(RESP2, RESP3)은 포크 시점 그대로라 클라이언트 라이브러리는 양쪽에 그대로 붙는다. 갈리는 것은 명령어다.

#### 9.0인 이유

Redis 7.4가 넣은 **해시 필드 만료**(`HEXPIRE`, `HPEXPIRE`, `HEXPIREAT`, `HTTL`)를 쓸 수 있어야 한다. Valkey는 이 명령을 **9.0**에서 넣었고 8.1까지는 없다. Valkey 공식 문서는 이 API가 Redis 8.0 API와 완전 호환이라고 밝히고 있다.

ElastiCache는 9.1도 제공한다. **9.0으로 고정한 것은 방금 필요해진 기능이 9.0에서 들어왔고, 그 위로 더 올릴 요구가 아직 없기 때문이다.** 9.1은 필요해질 때 올린다. Prometheus나 Grafana처럼 지원 종료일이 임박해서 고른 것이 아니므로 지원 창을 근거로 삼지 않았다.

#### 로컬 이미지

```
valkey/valkey:9.0-alpine
```

**`9-alpine`을 쓰면 안 된다.** 그 태그는 9.1로 풀린다. 운영이 9.0이므로 로컬도 9.0으로 고정해야 동작이 일치한다. `mysql:8.4`와 같은 마이너 고정 방식이다.

#### redis_exporter는 그대로 쓴다

관측 구성의 익스포터 이름이 `redis_exporter`인 것은 바뀌지 않는다. Valkey가 RESP 호환이라 같은 익스포터가 그대로 붙는다. **이름이 Redis라고 해서 엔진이 Redis인 것이 아니다.**

#### 노드 구성은 replication group 으로 만든다

평상시부터 노드 2대다. 캐시가 Degradable 이라 복제본이 필요 없다고 보았으나, 캐시 소실 구간을 감수하지 않기로 하고 뒤집었다 (`INF-37`).

| 구간 | 구성 | 월 비용 |
|---|---|---|
| 단일 노드 (2026-08-26 이전) | replication group, 노드 1대 (primary), AZ-a | 11.68 USD |
| **현재** | primary AZ-a + 복제본 AZ-c, Multi-AZ, 자동 페일오버 | 23.36 USD |

선착순 발급 카운터처럼 캐시가 소실되면 원본에서 재생성할 수 없는 값을 들고 있는 구간이 원래 정해 둔 전환 조건이었다. 그 조건을 기다리지 않고 먼저 올린 것이다.

**단일 노드일 때도 replication group 으로 만들어 두었다.** 그 덕에 복제본 추가가 이관 없이 플래그 변경으로 끝났다. Terraform 은 리소스 종류가 갈린다.

| 리소스 | 나중에 복제본 추가 |
|---|---|
| `aws_elasticache_cluster` | **불가** |
| `aws_elasticache_replication_group` (`num_cache_clusters = 1`) | 가능 |

전자로 만들면 필요해진 시점에 새로 만들어 갈아타야 한다. **비용 차이가 0 이므로 지금 정하면 되는 일이다.**

**서브넷 그룹에 AZ-c 도 넣는다.** Multi-AZ 는 다른 AZ 에 복제본이 있어야 켜지므로, AZ-a 만 등록해 두면 그때 서브넷 그룹부터 고쳐야 한다.

복제본을 붙이면 자동 페일오버가 생긴다. 프라이머리가 죽으면 복제 지연이 가장 적은 복제본이 수 초 안에 승격되고 프라이머리 엔드포인트 DNS 가 자동 갱신되므로 앱 설정 변경이 없다. 다만 **프라이머리를 재부팅하면 복제본까지 자기 사본을 지운다.** 이중화가 막는 것은 노드 고장이지 재부팅이 아니다.

durability(Valkey 9.0 의 Multi-AZ 트랜잭션 로그)는 쓸 수 없다. 지원 인스턴스가 R/M/C 계열뿐이라 `cache.t4g.micro` 가 빠져 있고, Cluster Mode Disabled 도 미지원이며, 생성 시에만 켤 수 있어 나중에 추가할 수도 없다.

#### 되돌릴 수 있다

Valkey와 Redis OSS 사이의 전환은 ElastiCache가 양방향으로 지원한다. 다만 되돌리면 7.1로 내려가면서 해시 필드 만료를 잃는다.

### 3.3 Grafana 12.4.x

Grafana는 LTS라는 명칭을 쓰지 않는다. 대신 각 마이너를 9개월 지원하고, 메이저의 마지막 마이너만 15개월 지원한다. 이 마지막 마이너가 실질적인 LTS 역할을 한다.

2026-08-01 기준 지원 라인은 13.1, 13.0, 12.4, 12.3이며 12.3은 2026-08-19에 종료된다. 12.x의 마지막 마이너인 12.4가 2027-05-24까지 지원되어 가장 긴 창을 가진다. 13.0은 2027-01-09에 종료되므로 최신이 곧 안정은 아니다.

추가 근거로 Amazon Managed Grafana가 12.4 워크스페이스 생성과 10.4에서 12.4로의 인플레이스 업그레이드를 지원한다. 나중에 관리형으로 옮기더라도 버전이 이미 맞는다.

### 3.4 Loki 3.7.x

Loki는 LTS 제도가 없고, 현재 메이저의 최근 두 마이너와 직전 메이저의 마지막 마이너에만 보안 패치를 제공한다. 2026-08-01 기준 3.7과 3.6이 지원 중이고 3.5는 2026-03-26에 종료됐다.

지원 라인 중 최신인 3.7.4를 쓴다. 로그 수집 에이전트는 Promtail이 아니라 Grafana Alloy를 쓴다. Promtail은 Alloy로 대체되는 방향이라 신규 구성에서 택할 이유가 없다.

### 3.5 관측성 자체 호스팅

AWS에는 대응하는 관리형 서비스가 있으나, 이 규모에서는 자체 호스팅이 더 싸다.

전제: 활성 시계열 약 4,000개(앱 1대, 호스트 2대, DB, 캐시 익스포터 합산), 15초 스크랩 기준 월 약 7억 샘플.

| 항목 | 15초 스크랩 | 60초 스크랩 |
|---|---|---|
| Amazon Managed Service for Prometheus | 약 74 USD | 약 16 USD |
| Amazon Managed Grafana (편집자 1명) | 9 USD | 9 USD |
| CloudWatch Logs (로그 15GB 가정) | 약 8~12 USD | 약 8~12 USD |
| 관리형 합계 | 약 91~95 USD | 약 33~37 USD |
| 자체 호스팅 (t4g.small + EBS 20GB) | 14 USD | 14 USD |

AMP는 첫 20억 샘플까지 1,000만 샘플당 0.90 USD이며, 프리티어로 월 4,000만 샘플과 10GB 저장이 무료다. 무료 한도는 약 230개 시계열을 15초로 스크랩하는 수준이라 실제 구성에서는 금방 초과한다.

비용보다 중요한 것은 구조다. **관리형은 스크랩 간격을 촘촘히 할수록 비용이 늘어난다.** 페일오버 RTO 2분이나 인스턴스 전환 30초 같은 짧은 사건을 관측하려면 5초에서 15초 해상도가 필요한데, 5초로 내리면 AMP 비용이 월 230 USD 근처가 된다. 관측 해상도와 비용이 정면으로 충돌하는 구조는 장애 검증과 상성이 나쁘다.

단점도 분명하다. 모니터링 인스턴스가 단일 장애점이며, 이 인스턴스가 죽으면 장애를 감지할 수단이 사라진다. 보완책으로 **핵심 알람은 CloudWatch에도 이중 설정**한다. CloudWatch 알람은 상시 무료 한도(알람 10개) 안에서 처리한다.

### 3.6 분산 추적 (선택)

추적 백엔드는 두 선택지가 있으며, Prometheus와 달리 관리형이 더 저렴하다.

| 항목 | Grafana Tempo 자체 호스팅 | AWS X-Ray |
|---|---|---|
| 추가 메모리 | 300~500MB | 0 |
| 인스턴스 영향 | t4g.small 2GB로는 부족, t4g.medium 필요 | 없음 |
| 추가 비용 | 인스턴스 업그레이드 월 12 USD | 아래 계산 |
| Grafana 연동 | 네이티브, 지표와 로그로 점프 | 데이터소스 플러그인 경유 |
| 보존 | 직접 설정 | 30일 무료 |

X-Ray는 월 10만 트레이스 기록과 100만 트레이스 조회가 무료이고, 초과분은 기록 100만 건당 5 USD다. 부하 시험 40시간을 평균 50 RPS, 10% 샘플링으로 잡으면 72만 트레이스가 나오고 과금은 약 3 USD다.

AMP가 비쌌던 이유는 스크랩 간격에 비례해 샘플이 무한정 늘어나는 구조였고, X-Ray는 샘플링 비율로 상한을 직접 잡을 수 있는 구조이기 때문이다.

계측은 어느 쪽을 택하든 OpenTelemetry로 통일한다. 백엔드를 바꿔도 애플리케이션 코드는 그대로다. AWS도 X-Ray SDK와 데몬을 유지보수 모드로 두고 OpenTelemetry 기반 계측을 권장한다.


### 3.7 Terraform 버전

**Terraform에는 LTS가 없다.** 지원 정책은 최신 메이저 릴리스와 직전 두 개까지 패치를 제공하는 방식이며, 동시에 세 개 릴리스가 지원된다. Ubuntu나 Java처럼 수년짜리 지원 창을 주는 개념이 존재하지 않는다.

따라서 "LTS에 해당하는 선택"은 **최신 안정 마이너를 고정하고 정기적으로 올리는 것**이다. 현재 1.15.1 을 기준으로 한다.

```hcl
terraform {
  required_version = "~> 1.15"     # 1.15.1 기준. 구축 시점 최신 패치 확인

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }

  backend "s3" {
    bucket       = "tfstate-${var.project}"
    key          = "infra/terraform.tfstate"
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true
  }
}
```

코어 버전보다 **프로바이더 버전 고정이 실질적으로 더 중요하다.** AWS 프로바이더는 메이저 업그레이드에서 리소스 스키마가 바뀌는 경우가 있어, 고정하지 않으면 어제 통과한 `plan`이 오늘 실패한다.

#### 라이선스에 관한 참고

HashiCorp는 2023년 8월에 Terraform 1.6부터 라이선스를 MPL 2.0에서 BUSL 1.1로 변경했다. 최종 사용자가 자기 인프라에 `terraform apply`를 수행하는 용도에는 영향이 없다. 영향을 받는 것은 Terraform을 감싸거나 확장하는 상용 제품을 만드는 경우다.

대안으로 OpenTofu가 있다. MPL 2.0 라이선스의 포크로 Linux Foundation이 관리하며 2025년 4월 CNCF에 편입되었고, 2026년 6월 기준 안정 버전은 1.12.2다. 지원 정책은 Terraform과 동일하며, 대부분의 구성이 수정 없이 동작해 마이그레이션은 바이너리 교체 수준이다.

HCL 파일은 양쪽에서 동일하게 동작하므로 이 선택은 나중에 뒤집어도 비용이 거의 없다. 본 문서는 Terraform을 기준으로 하되, 개방형 라이선스가 조직 정책상 요구될 경우 OpenTofu로 전환한다.

### 3.9 SonarQube Cloud 를 택한 이유

PR 단위 정적 분석이 목적이므로 서버를 자체 호스팅하지 않는다.

| 항목 | 자체 호스팅 | Cloud |
|------|-------------|-------|
| 인프라 | EC2 + EBS, 월 약 22 USD | 없음 |
| GitHub PR 연동 | GitHub App 등록, 웹훅, 인증 설정 | 저장소 연결 한 번 |
| PR 데코레이션 | 직접 구성 | 기본 제공 |
| 서버 유지보수 | 업그레이드, 백업 | 없음 |
| 네트워크 | **VPC 노출 설정 필요** | 없음 |

**네트워크가 결정적이다.** 이 인프라는 NAT Gateway 가 없고 ALB 뒤에 앱만 두는 구조다. GitHub Actions 러너가 접근할 수 있도록 Sonar 서버를 노출하려면 리스너와 인증서와 보안 그룹을 추가로 만들어야 한다.

저장소를 공개로 운영하므로 Cloud 는 무료다. **인프라 비용이 0 이라 월 예산에 영향이 없다.**

참고로 SonarQube Server 2026.1 LTA 는 Java 17 지원이 제거되어 Java 21 또는 25 가 필요하고 JRE 가 아닌 JDK 를 요구한다. 자체 호스팅으로 전환하게 되면 이 요건을 확인한다. Gradle 스캐너는 7.6.4 또는 8.4 이상이 필요하며, 이는 Cloud 에서도 동일하다.

#### 품질 게이트 정책

**두 조건 중 하나라도 실패하면 병합을 차단한다.**

| 조건 | 기준 | 판정 주체 | 동작 |
|------|------|-----------|------|
| 커버리지 | service 패키지 메서드 100% 미만 | Gradle | 병합 차단 |
| 정적 분석 | **Blocker 이슈 존재** | SonarQube | 병합 차단 |

**SonarQube 는 커버리지를 판정하지 않는다.** 버그, 취약점, 코드 스멜만 본다. 커버리지 판정은 Gradle 이 맡아 두 기준이 충돌하지 않게 한다. 상세는 [be 의 build-gate-rationale.md](https://github.com/fresh-market/fm-backend/blob/main/docs/code-architecture/build-gate-rationale.md) 에 있다.

| 항목 | 설정 |
|------|------|
| 분석 시점 | PR 생성과 갱신 |
| 병합 차단 | **함** |
| 강제 수단 | 브랜치 보호의 필수 상태 검사 |
| 커버리지 리포트 | JaCoCo XML 을 SonarScanner 가 수집 |

## 4. 관측성 구성

### 4.1 데이터 흐름

```
앱 컨테이너 (Spring Boot 4)
  -> /actuator/prometheus            -> Prometheus 스크랩 (15초)
  -> stdout JSON 로그 -> Alloy       -> Loki
  -> OTLP 스팬 -> OTel Collector     -> 추적 백엔드

EC2 호스트   -> node_exporter        -> Prometheus
컨테이너     -> cAdvisor             -> Prometheus
RDS          -> mysqld_exporter      -> Prometheus
RDS/ALB/캐시 -> cloudwatch_exporter  -> Prometheus
ElastiCache  -> redis_exporter       -> Prometheus

Prometheus -> Alertmanager -> Slack Webhook (직접)
CloudWatch  -> SNS -> AWS Chatbot -> Slack
Prometheus, Loki -> Grafana
```

### 4.2 앱 연동 설정

**액추에이터를 8081 로 분리한다.** 8080 에는 `/actuator` 경로가 아예 존재하지 않게 되므로, 밖에서 막을 규칙이 필요 없다. 보안 그룹이 8081 을 ALB 와 모니터링에게만 열어 두면 끝난다.

리스너 규칙으로 막는 방법도 있으나 택하지 않았다. 규칙 하나가 지워지면 그대로 열리고, Route 53 헬스체크가 밖에서 `liveness` 를 찔러야 해서 예외 규칙을 또 겹쳐 쌓아야 한다.

```yaml
server:
  port: 8080

management:
  server:
    port: 8081                       # 액추에이터 전용 포트
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
  endpoint:
    health:
      probes:
        enabled: true
      show-details: never          # 밖에서 볼 수 있으므로 상세를 숨긴다
      group:
        readiness:
          include: diskSpace         # 공유 의존성은 넣지 않는다 (INF-16)
  metrics:
    tags:
      application: ${APP_NAME}
      instance: ${APP_INSTANCE_ID}
  tracing:
    sampling:
      probability: ${TRACE_SAMPLE_RATE:0.1}
```

Micrometer 레지스트리 버전은 Spring Boot 4.0.5의 BOM이 관리하므로 별도로 고정하지 않는다. 의존성은 `micrometer-registry-prometheus`를 추가한다.

`/actuator/prometheus`는 외부에 노출하면 내부 구조가 새어 나간다. ALB 리스너 규칙에서 `/actuator/**` 경로를 차단하고, Prometheus는 VPC 내부에서 인스턴스에 직접 스크랩한다.

### 4.3 로그 형식

Loki는 로그 본문을 인덱싱하지 않고 레이블만 인덱싱한다. 레이블 설계가 곧 검색 성능이다.

| 레이블 | 값 예시 | 주의 |
|--------|---------|------|
| `app` | 서비스명 | |
| `instance` | app-1 | |
| `env` | prod, local | |
| `level` | INFO, ERROR | |

식별자처럼 값의 종류가 무한한 항목은 레이블에 넣지 않는다. 카디널리티가 폭발해 Loki가 느려진다. 이런 값은 본문 JSON 필드로 두고 쿼리 시 파싱한다.

요청마다 `traceId`를 MDC에 넣고 JSON 본문에 포함시킨다. 이 값이 있어야 롤링 배포의 혼재 구간에서 구 버전과 신 버전의 로그를 구분해 따라갈 수 있다.

### 4.4 샘플링 전략 (추적)

| 구간 | 샘플링 | 이유 |
|---|---|---|
| 평상시 | 10% | 기본 관측 |
| 부하 시험 | 5% | 트레이스 폭증 억제 |
| 장애 주입 실험 | 100% | 사건이 짧아 놓치면 재현이 어려움 |
| 오류 응답 | 항상 100% | 테일 샘플링으로 오류는 전량 보존 |

페일오버는 2분 안에 끝나는데 10% 샘플링이면 그 구간의 실패 요청 대부분을 놓친다. 환경 변수 하나로 100%로 올릴 수 있게 해 두고, 실험 스크립트가 주입 직전에 변경한다.

### 4.5 알람

알람 정의, 경로 배분, 심각도, 전달 채널은 [알람과 알림 설계 문서](./백엔드공통_알람과알림_설계.md)에 정리했다. 요약하면 다음과 같다.

| 구분 | 개수 | 경로 | 도착 채널 |
|------|------|------|------|
| Critical | 9 | CloudWatch 6, Prometheus 3 | `#alerts-critical` |
| Warning | 11 | 전부 Prometheus | `#alerts-warning` |

CloudWatch 6개 중 5개는 지표 알람이고 1개(RDS 페일오버)는 이벤트 구독이다. 알람 지표로 계산되는 것은 5개이며 프리티어 한도 10개 안에 든다.

CloudWatch에 두는 6개는 **모니터링 인스턴스가 죽어도 알아야 하는 것들**이다. 프리티어 알람 지표 10개 안에 들어간다.

버스트 인스턴스를 쓰므로 CPU 크레딧 잔량 알람이 반드시 필요하다. 크레딧이 소진되면 인스턴스가 살아 있는데도 성능이 급락해, 장애로 보이지 않는 장애가 생긴다.

| 인스턴스 | 시간당 적립 | 최대 누적 | 100% 부하 시 소진 |
|------|------|------|------|
| t3.small, t4g.small, t3a.small | 24 | 576 | 약 6시간 |
| db.t4g.micro | 12 | 288 | 약 2.7시간 |

**RDS 가 EC2 보다 두 배 빨리 소진된다.** 부하 시험 중에는 RDS 크레딧을 먼저 본다.

### 5.3 CPU 크레딧 과금 주의

RDS의 T4g와 T3 인스턴스는 Unlimited 모드로 동작하며, 24시간 이동 평균 CPU 사용률이 기준선을 넘으면 vCPU 시간당 0.075 USD가 부과된다. 모든 리전과 인스턴스 크기에 동일하게 적용되고 예약 인스턴스로 커버되지 않는다.

부하 시험 중에는 기준선을 확실히 넘는다. 금액 자체는 크지 않으나 **RDS는 Unlimited 모드를 끌 수 없다는 점**이 중요하다. EC2는 Standard 모드로 바꿔 크레딧 과금 대신 성능 저하를 택할 수 있지만 RDS에는 선택지가 없다.

**EC2 도 전부 Unlimited 로 둔다.** T3, T3a, T4g 의 기본값이고 시작 템플릿에서 바꾸지 않는다. 부하 시험을 반복하기 때문이다.

Standard 로 두면 회차마다 다른 숫자가 나온다. 1회차는 크레딧이 만충이라 제 성능을 내고, 3회차는 소진되어 기준선으로 스로틀된다. **앱이 느려진 것이 아니라 하이퍼바이저가 조인 것인데 지표에서 구분되지 않는다.** 8장이 "같은 조건에서 같은 지표를 잰다"고 한 전제가 깨진다.

그 대신 비용이 조용히 쌓인다. 100% 부하 기준 t3.small 한 대가 시간당 0.08 USD, RDS 가 0.12 USD 다. 2시간 세션을 열 번 돌리면 10 USD 에 가까워진다.

```
전용 3대 + 앱 2대   시간당 약 0.40 USD
RDS                 시간당 약 0.12 USD
```

**`CpuCreditLow` 와 `CpuCreditCritical` 알람은 성능 경고가 아니다.** Unlimited 에서는 크레딧이 말라도 느려지지 않으므로, 저 선을 넘는 것은 "여기부터 돈이 나간다"는 뜻이다. Standard 로 바꾸는 날 그 알람은 성능 경고가 된다.

**캐시는 사정이 다르다.** `cache.t4g.micro` 도 버스터블인데 ElastiCache 에는 EC2 같은 Unlimited 선택지가 없다. 선착순 구간에서 캐시가 판정 주체이므로(`coupon.md` 4장) 발급 요청 하나마다 Lua 가 한 번씩 돈다. **여기서 크레딧이 마르면 실제로 느려진다.** `aws_elasticache_cpucredit_balance_average` 를 첫 부하 시험의 관찰 대상에 넣는다.

### 5.4 프리티어

AWS 프리티어는 2025-07-15부터 개편되어, 신규 계정은 가입 시 100 USD 크레딧을 받고 특정 서비스 사용 시 추가 100 USD를 받는다. 무료 플랜은 계정 개설일로부터 6개월 또는 크레딧 소진 중 빠른 쪽에 만료된다. 2025-07-15 이전 생성 계정은 기존의 12개월 프리티어 체계가 적용된다.

상시 운영 기준 월 140 USD이면 크레딧 200 USD로 약 6주다. 도메인 등록비는 크레딧으로 결제되지 않을 수 있으므로 별도로 확인한다. 기간을 늘리려면 부록 A의 절감 방안을 검토한다.

아웃바운드 데이터 전송은 상시 무료 100GB 한도 안에서 처리된다.

### 5.5 예산 가드레일

AWS Budgets로 크레딧 소진율 알람을 설정한다. 무료이며, 예산의 50%, 80%, 100% 지점에 알림을 건다.

### 5.6 도메인과 TLS 현황

**도메인을 사지 못했다.** 프리 티어 무료 플랜은 Route 53 도메인 등록 서비스를 쓸 수 없다.

```
AccessDeniedException: Free Tier accounts are not supported for this service
```

`db_backup_retention_days` 를 7로 올리지 못하는 것과 같은 계정 플랜 제약이다. IAM 권한 문제가 아니다.
ACM 도 함께 막힌다. 소유를 검증할 도메인이 없으면 인증서를 발급받을 수 없다.

**그래서 진입점이 둘로 갈렸다.**

| 진입점 | 주소 | 프로토콜 | 인증 |
|---|---|---|---|
| 앱 | ALB DNS 이름 | **평문 HTTP** | 없음 |
| Grafana | `<이름>.duckdns.org` | HTTPS (Let's Encrypt) | Caddy basic_auth + Grafana 계정 |

DuckDNS 이름은 Grafana 를 위해 만든 것이다. **앱은 도메인을 쓰지 않는다.**
부하 시험도 실 운영도 ALB DNS 이름으로 직접 간다.

#### 이 상태에서 성립하지 않는 것

**`INF-17` 이 미충족이다.** 무상태 JWT 를 헤더로 보내는데 앱 구간이 평문이라,
토큰이 그대로 노출되고 가로챈 쪽이 그 사용자로 행세할 수 있다.
`INF-02` 로 무상태 인증을 고른 순간 따라온 제약이므로, 실제 사용자를 받기 전에는 해소해야 한다.

**외부 관점 감시가 없다.** `INF-19` 의 Route 53 헬스체크는 도메인이 있어야 만들어진다.
Prometheus 는 VPC 안이라 ALB 가 죽어도 앱 지표는 정상으로 보이는데, 그 사각지대를 메울 눈이 지금 없다.
무중단 배포 문서와 앱과 DB 장애 대응 문서가 이 헬스체크를 전제로 롤백을 판단하므로,
해당 절차는 현재 근거 지표가 없는 상태로 읽어야 한다.

**부하 시험은 HTTP 로 잰다.** 앱 경로에 TLS 가 없으므로 그것이 프로덕션과 같은 조건이다.
도메인이 생긴 뒤 HTTPS 로 다시 재는 절차는 필요 없다.

#### 도메인이 생기면 되돌릴 것

1. `duckdns_hostname` 을 비우고 `domain_name` 을 채운다. Caddy 와 EIP 가 사라진다
2. Grafana 는 ALB + Google 로그인 경로로 옮겨 간다. 공용 비밀번호가 필요 없어진다
3. Route 53 헬스체크가 생겨 `INF-19` 가 성립한다
4. 앱 진입점이 HTTPS 가 되어 `INF-17` 이 충족된다
5. 비용이 월 약 2.20 USD 늘고 도메인 등록비가 별도로 붙는다

절차는 `observability/README.md` 에 있다.

## 6. 이미지 태그 고정 원칙

`latest` 태그는 어디에도 쓰지 않는다. 재현 불가능한 환경은 장애 원인 분석 자체를 불가능하게 만든다.

```yaml
services:
  app:
    image: ghcr.io/${GITHUB_OWNER}/${APP_NAME}:${GIT_SHA}
  mysql:
    image: mysql:8.4
  valkey:
    image: valkey/valkey:9.0-alpine
  prometheus:
    image: prom/prometheus:v3.13.1
  grafana:
    image: grafana/grafana:12.4.3
  loki:
    image: grafana/loki:3.7.4
```

애플리케이션 이미지 태그는 커밋 SHA를 쓴다. 시맨틱 버전은 사람이 붙이는 것이라 롤백 대상을 특정하기 어렵고, 커밋 SHA는 코드와 1:1로 대응한다.

Grafana와 Loki의 패치 번호는 구축 시점의 최신 패치로 확정한 뒤 이 문서를 갱신한다.

## 부록 B. 프리 티어 계정 제약

2026-08-20 에 계정을 만들었고 AWS 의 새 프리 티어(`FREE` 플랜)에 들어간다. 2025-07-15 이후 개설 계정이 대상이다.

| 항목 | 값 |
|---|---|
| 크레딧 | 가입 100 USD + 활동 5개 x 20 USD = **200 USD** |
| 활동 | EC2, RDS, Lambda, Bedrock, Budgets. 콘솔의 Explore AWS 위젯에서 수행 |
| 활동 마감 | 계정 개설 후 6개월 |
| 크레딧 만료 | 계정 개설 후 12개월 |
| 플랜 만료 | 2027-02-10 |

확인은 `aws freetier get-account-plan-state --region us-east-1` 로 한다.

### B.1 확정값을 막는 제약

**RDS 백업 보존 기간에 상한이 있다.** 확정값 7일이 거부된다.

```
FreeTierRestrictionError: The specified backup retention period exceeds
the maximum available to free tier customers.
```

현재 1일로 낮춰 두었다. 상세는 백업과 복원 설계 3.1절에 있다.

**다른 제약이 더 있을 수 있다.** 공식 문서가 `FREE` 플랜의 서비스별 상한을 정리해 두지 않았다. 새 리소스를 만들 때 `FreeTierRestrictionError` 가 나오면 이 부류다.

### B.2 플랜 만료가 계정을 닫는다

> When your free plan expires, **AWS closes your account, and you'll lose access to your resources and data.**

데이터는 90일간 보관되고 그 안에 유료 플랜으로 올리면 복구된다. 안 올리면 영구 삭제다.

이 인프라는 월 약 100 USD 다. 크레딧 200 USD 로 **약 2개월**이다. 그 전에 유료 전환을 결정해야 한다.

**6개월 안에 올리면 남은 크레딧이 이후 청구서에 자동 적용된다.** 다만 Organizations 나 Control Tower 에 넣으면 크레딧이 즉시 만료되므로 그 경로는 피한다.

## 부록 A. 운영 비용 절감 방안 (참고)

**기본 전제는 상시 가동이다.** 모든 인프라 리소스는 종료되지 않으며, 본문의 비용 기준도 한 달 상시 운영이다.

본 부록의 절차는 **운영자가 스크립트로 명시적으로 실행하는 예외 작업**이다. 자동화된 정기 절차가 아니고, 다른 문서의 배포나 검증 절차는 이 작업이 실행되지 않았다고 가정하지 않는다. 대신 각 절차는 시작 전에 리소스 상태를 확인한다.

검증이나 학습 목적처럼 상시 가동이 필요 없는 기간에 가동 시간을 줄여 비용을 낮출 수 있다. 채택 시에는 함께 적힌 제약과 규칙을 반드시 지켜야 한다.

**중요한 전제 하나.** 절감은 가동 시간으로만 하고, **인프라 사양은 상시 운영 기준을 그대로 유지한다.** 사양을 낮추면 부하 시험 결과가 실제 운영을 대변하지 못해 검증 자체가 무의미해진다.

### A.1 두 가지 모델

| 모델 | 방식 | 월 근사 |
|------|------|---------|
| 상시 운영 | 항상 켜 둔다 | 약 162 USD |
| 중지 방식 | EC2와 RDS를 세션 단위로 중지 | 약 66 USD |
| 파괴 방식 | 세션 종료 시 전체 삭제, 스냅샷으로 데이터 보존 | 약 21 USD |

아래 계산은 하루 4시간 x 20일 = 월 80시간 가동을 가정한다.

### A.2 리소스별 중지 가능 여부

| 리소스 | 중지 | 중지 중 과금 | 비고 |
|--------|------|--------------|------|
| EC2 | 가능 | EBS만 | 컴퓨트 과금 중단 |
| RDS | 가능 | 스토리지, 백업 | 최대 7일 후 자동 재시작 |
| EBS | 불가 | 전액 | 인스턴스를 꺼도 계속 과금 |
| ElastiCache | **불가** | 전액 | 삭제해야 과금 중단 |
| ALB | **불가** | 전액 | 삭제해야 하며 DNS 이름이 바뀜 |
| 스냅샷, S3 | 해당 없음 | 저장량 | 소액 |

**ALB와 ElastiCache가 중지 불가라는 점이 중지 방식의 절감 한계를 결정한다.** 이 둘만으로 월 29 USD가 고정된다.

### A.3 RDS 중지의 제약 사항

Amazon RDS 사용 설명서의 "DB 인스턴스의 일시적 중지" 기준이다.

| 사실 | 설계 영향 |
|------|-----------|
| 다중 AZ 배포에서도 중지 가능 (MySQL 지원, SQL Server만 불가) | 중지 방식이 성립하는 근거 |
| 최대 7일 연속. 이후 자동 시작 | 주 1회 이상 재중지 자동화 필요 |
| 중지 중 스토리지와 백업 스토리지는 계속 과금 | 절감 대상은 인스턴스 시간뿐 |
| DNS 엔드포인트, 파라미터 그룹, 보안 그룹, PITR용 트랜잭션 로그 유지 | 재시작 후 접속 정보 갱신 불필요 |
| 시작 시 인스턴스 복구로 몇 분에서 몇 시간 소요 가능 | **세션 시작 시간이 불확실. 첫 세션에서 실측 필요** |
| 중지된 인스턴스는 수정 불가 | `terraform apply` 전에 반드시 시작 |
| 다중 AZ는 시작 후 기본과 보조 AZ가 뒤바뀔 수 있음 | AZ 고정을 전제한 설계 금지 |
| 읽기 전용 복제본을 포함하거나 복제본인 인스턴스는 중지 불가 | 복제본 도입 시 이 모델이 깨짐 |

### A.4 중지와 재가동 절차

```
최초 1회    terraform apply
재가동   1. RDS start + 모니터링 EC2 start   (동시. 서로 무관)
         2. ASG desired = 1                   (RDS available 이후)
         3. readiness 확인

중지     1. ASG desired = 0
         2. 관측 데이터 내보내기
         3. 모니터링 EC2 stop
         4. RDS stop                          (완료 대기 불필요)
구성 변경   (반드시 시작 상태에서) terraform apply
안전장치    EventBridge 일일 강제 정리, AWS Budgets 알람
```

순서는 의존 방향에서 나온다. 시작할 때는 의존받는 쪽(RDS)부터 올리고, 종료할 때는 의존하는 쪽(앱)부터 내린다. RDS보다 앱을 먼저 올리면 커넥션 확보 실패로 기동과 교체가 반복되고, 앱보다 RDS를 먼저 내리면 커넥션 오류가 세션 마지막 구간의 지표를 오염시킨다. 단계별 근거는 A.8절에 정리했다. 재가동 후에는 무중단 배포 문서 2.2절의 상태 점검을 거친 뒤 작업을 시작한다.

**앱 인스턴스는 중지가 아니라 ASG desired 0으로 내린다.** ASG는 중지된 인스턴스를 비정상으로 판정해 교체하므로, `stop-instances`를 쓰면 세션을 끝낼 수 없다. 반면 **모니터링 인스턴스는 ASG에 넣지 않고 stop/start로 다룬다.** desired 0은 인스턴스를 종료시켜 EBS까지 삭제하므로 Prometheus와 Loki 데이터가 사라진다.

**시작과 중지를 Terraform으로 수행하지 않는다.** 상태 전환은 인프라 정의가 아니라 운영 명령이다. 중지된 리소스에 대해 `terraform plan`이 드리프트로 인식하는지는 구축 초기에 한 번 확인하고, 필요하면 "apply 전 반드시 start" 규칙을 절차에 명시한다.

### A.7 채택 시 지켜야 할 규칙

**중지 방식을 택하면**

1. **모든 인프라 변경을 Terraform으로만 한다.** 콘솔에서 손으로 고치는 순간 코드와 실제가 어긋나고, IaC를 도입한 의미가 사라진다. 파괴 방식은 이 규칙을 구조적으로 강제하지만 중지 방식은 사람이 지켜야 한다.
2. EventBridge로 매일 정해진 시각에 강제 중지한다. RDS의 7일 자동 시작 제약에도 함께 대응된다.
3. `terraform apply` 전에 반드시 인스턴스를 시작한다. 중지 상태에서는 수정이 불가능하다.
4. 첫 재가동에서 RDS 시작 소요 시간을 실측해 가동 계획에 반영한다.
5. **재가동 후에는 반드시 상태 점검을 거친 뒤 배포나 시험을 시작한다.** 절차는 무중단 배포 문서 2.2절과 동일하다.

**파괴 방식을 택하면**

1. 영속 계층과 휘발 계층을 명확히 나눈다. DB 스냅샷, 실험 결과, Grafana 대시보드 정의, 시크릿, Terraform 상태가 영속 대상이다.
2. **Grafana 대시보드를 코드로 관리한다.** UI에서 만들면 파괴와 함께 사라진다.
3. `destroy` 직전에 스냅샷 생성과 관측 데이터 내보내기를 자동으로 수행한다. 이 단계가 빠지면 한 달 뒤에 남는 것이 없다.
4. Route 53 호스팅 영역은 이미 영속 계층에 있으므로, alias 레코드만 Terraform이 매 세션 갱신하게 한다.
5. 정리 작업이 중간에 실패해 리소스가 남는 경우를 대비해 시간 기반 청소 작업을 별도로 둔다.

### A.8 중지와 재가동 순서의 근거

순서는 의존 방향에서 나온다.

> 올릴 때는 의존받는 쪽부터, 내릴 때는 의존하는 쪽부터.

앱은 DB에 의존하고, 관측은 앱에 의존하지 않는다. 이 두 사실이 순서를 결정한다.

#### 재가동

| 순서 | 작업 | 근거 | 소요 |
|---|---|---|---|
| 1 | RDS start + 모니터링 start (동시) | 서로 무관하므로 병렬. RDS가 가장 오래 걸리므로 먼저 건다 | RDS 수 분~수십 분 |
| 2 | ASG desired 를 운영값(현재 1)으로 | RDS available 이후에만 | 4~6분 |
| 3 | readiness 확인 | 대상 그룹 healthy 로 판정 | 최대 2분 |

**RDS를 먼저 올리는 이유는 두 가지다.** 첫째, RDS가 준비되기 전에 앱을 올리면 HikariCP가 초기 커넥션을 확보하지 못해 애플리케이션 컨텍스트가 뜨지 않고 컨테이너가 종료된다. 그러면 ASG가 비정상으로 판정해 교체하며, RDS가 준비될 때까지 기동과 교체를 반복한다. 둘째, RDS 시작은 인스턴스 복구를 동반해 소요가 불확실하므로 가장 긴 작업을 먼저 걸어야 전체 대기가 줄어든다.

**모니터링을 앱보다 먼저 올리는 이유**는 앱 기동 자체가 관측 대상이기 때문이다. 앱이 뜬 뒤에 모니터링을 켜면 기동에 실패했을 때 원인을 볼 지표가 없다. 먼저 켜면 스크랩 실패가 몇 분 기록되지만, 이 잡음은 시각 기준으로 걸러내면 된다. 관측 공백보다 잡음이 낫다.

#### 중지

| 순서 | 작업 | 근거 | 소요 |
|---|---|---|---|
| 1 | ASG desired = 0 | 앱이 DB에 의존하므로 먼저 내린다 | 1~2분 |
| 2 | 관측 데이터 내보내기 | 앱이 내려간 뒤라야 종료 구간까지 포함된다 | 2~5분 |
| 3 | 모니터링 EC2 stop | 내보내기 완료 후 | 1~2분 |
| 4 | RDS stop | 아무도 의존하지 않는다. 완료 대기 불필요 | 수 분~1시간 |

**1번을 먼저 하는 이유**는 반대로 하면 지표가 오염되기 때문이다. RDS를 먼저 내리면 살아 있는 앱이 커넥션 오류를 대량으로 뿜고, 그 오류가 마지막 구간의 지표와 로그에 남는다. 나중에 그래프를 보면 장애가 있었던 것처럼 보이는데 실제로는 정상 종료 절차였을 뿐이다.

```bash
aws autoscaling set-desired-capacity \
  --auto-scaling-group-name "${PROJECT}-app" --desired-capacity 0
```

#### 자주 하는 실수

| 실수 | 결과 |
|---|---|
| RDS보다 ASG를 먼저 올림 | 기동 실패와 인스턴스 교체 루프 |
| 모니터링을 앱보다 늦게 올림 | 기동 실패 시 원인 지표 없음 |
| RDS를 앱보다 먼저 내림 | 커넥션 오류가 지표를 오염시킴 |
| 내보내기 전에 모니터링을 내림 | 그 기간 실험 데이터 소실 |
| 앱 인스턴스를 stop-instances로 중지 | ASG가 비정상 판정해 교체 |
| 재가동 후 상태 점검 없이 배포 | 교체된 인스턴스 기동 실패 |

### A.9 시험 착수 전 점검

부하 시험, 장애 주입, 복원 리허설 등 **운영 환경과 동일한 구성에서 수행하는 모든 시험**에 적용한다.

배포 사전 점검(무중단 배포 문서 2.2절)과 목적이 다르다.

| 구분 | 배포 사전 점검 | 시험 사전 점검 |
|------|----------------|----------------|
| 막으려는 것 | 배포 실패 | **측정 결과 오염** |
| 판단 기준 | 절차가 성공할 수 있는가 | 결과를 신뢰할 수 있는가 |
| 크레딧 확인 | 없음 | 예정 시간만큼 있는가 |

크레딧이 부족한 상태로 부하를 걸면 측정한 값이 서버 성능이 아니라 **크레딧 소진 시점**이 된다. 인스턴스가 살아 있는데도 기준선 이상으로 CPU가 올라가지 못해, 실제보다 낮은 처리량이 기록된다. 더 나쁜 것은 **어느 지점부터 오염되었는지 사후에 구분하기 어렵다는 점**이다.

#### A.9.1 고정 임계를 쓰지 않는 이유

시험 유형마다 필요한 시간이 다르고, 인프라 구성도 시간이 지나면 바뀐다. 하나의 고정 임계로는 짧은 시험이 불필요하게 막히거나 긴 시험이 도중에 마른다.

따라서 판정을 두 축으로 나눈다.

| 축 | 정하는 것 | 주체 |
|------|-----------|------|
| 시험 길이 | 몇 분 돌릴 것인가 | **사람이 선택** (유형 또는 직접 입력) |
| 필요 잔량 | 그 시간에 얼마가 필요한가 | **스크립트가 현재 구성을 조회해 계산** |

```
입력   13분, 목표 부하 100%
  ->
조회   현재 앱 인스턴스와 타입, RDS 인스턴스와 클래스
  ->
계산   대상별 필요 잔량과 현재 잔량
  ->
판정   가장 부족한 대상 기준으로 통과 또는 차단
```

**인스턴스 타입을 상수로 박지 않는다.** t3.small 을 t3.medium 으로 승급하면 vCPU 와 적립량이 달라지는데, 상수로 두면 계산이 조용히 틀린다.

#### A.9.2 시험 유형별 표준 구성

| 유형 | 램프업 | 측정 | 총 시간 |
|------|--------|------|---------|
| 장애 주입 | 2분 | 5분 | 7분 |
| 배포 검증 | - | 8분 | 8분 |
| 기준선 측정 | 3분 | 10분 | 13분 |
| 크레딧 소진 시험 | 3분 | 소진까지 | 가변 (게이트 면제) |

**워밍업은 시험 구성에서 뺀다.** 목표 부하의 30% 정도로 도는 구간이라 시험 세션 밖에서 미리 수행하면 된다. 앱이 이미 떠서 트래픽을 받고 있었다면 JIT 컴파일과 클래스 로딩은 끝나 있다.

측정 시간이 유형마다 다른 근거는 다음과 같다.

| 측정 시간 | 판단 가능한 것 |
|-----------|----------------|
| 5분 | 평균 처리량, 사건 발생 여부 |
| 10분 | 위 + 안정된 p99 |
| 15분 이상 | 위 + GC 주기 관찰 |

장애 주입은 사건이 짧고 관찰 대상이 명확해 5분이면 충분하다. RDS 페일오버는 2분 안에 끝난다.

기준선 측정을 10분으로 잡은 것은 **p99 가 안정되는 최소선**이기 때문이다. p99 는 상위 1% 라 표본이 적으면 GC 한 번에 크게 흔들린다. 15분이면 GC 주기까지 볼 수 있으나, 그 대가로 필요 잔량이 늘고 회복 대기가 길어진다. GC 는 이 프로젝트의 증명 항목이 아니므로 문제가 의심될 때 별도로 길게 돌린다.

**크레딧 소진 시험은 게이트를 면제한다.** 크레딧을 다 쓰는 것이 목적이므로 잔량을 요구하는 것 자체가 모순이다.

#### A.9.3 필요 잔량 계산

1 CPU 크레딧은 vCPU 하나를 1분간 100% 사용하는 양이다.

```
분당 소비   = vCPU 수 x (목표 부하율 / 100)
분당 적립   = 시간당 적립 / 60
분당 순소비 = 분당 소비 - 분당 적립

필요 잔량 = (측정 시간 x 분당 순소비)
          + (램프업 시간 x 분당 순소비 x 0.5)
          + 지표 지연 보정
```

**램프업은 0.5 를 곱한다.** 부하가 0 에서 목표까지 선형 증가하므로 평균 소비가 절반이다.

**지표 지연 보정은 계수가 아니라 덧셈이다.** CloudWatch 기본 모니터링이 5분 간격이라 조회한 값이 최대 5분 전 것이다. 그동안 100% 부하였다면 실제 잔량은 `5 x 분당 순소비` 만큼 낮다. 이 오차는 **시험 길이와 무관하므로 곱셈 계수로 처리하면 안 된다.** 긴 시험일수록 과도하게 요구하게 된다.

```
지표 지연 보정 = 5 x 분당 순소비
```

기준선 측정(램프업 3분, 측정 10분)을 db.t4g.micro 기준으로 계산하면 이렇다.

```
분당 순소비 = 2 - (12 / 60) = 1.8
필요 잔량   = (10 x 1.8) + (3 x 1.8 x 0.5) + (5 x 1.8)
            = 18 + 2.7 + 9 = 29.7 -> 30
```

#### A.9.4 인스턴스별 기준값

적립량은 API 로 조회할 수 없어 표가 필요하다. **미등록 타입이면 계산하지 않고 실패시킨다.** 기본값을 넣으면 잘못된 계산으로 시험이 통과해 버린다.

| 타입 | vCPU | 시간당 적립 | 최대 누적 |
|------|------|-------------|-----------|
| t3.nano, t4g.nano | 2 | 6 | 144 |
| t3.micro, t4g.micro | 2 | 12 | 288 |
| t3.small, t4g.small, t3a.small | 2 | 24 | 576 |
| t3.medium, t4g.medium | 2 | 24 | 576 |
| t3.large, t4g.large | 2 | 36 | 864 |

RDS 인스턴스 클래스는 앞에 `db.` 가 붙지만 크레딧 규격은 같다. vCPU 수는 `describe-instance-types` 로 조회할 수 있으나, 위 범위에서는 전부 2 이므로 표로 함께 관리한다.

**새 타입을 도입하면 이 표에 추가한다.** AWS 버스터블 인스턴스 문서의 크레딧 표가 출처다.

#### A.9.5 여러 대상이 있을 때의 판정

앱이 여러 대이거나 RDS 에 읽기 복제본이 있으면 대상이 늘어난다.

| 방식 | 판정 | 적절한가 |
|------|------|----------|
| 합산 | 전체 잔량의 합 | **아니오.** 한 대만 말라도 그 인스턴스가 느려짐 |
| 평균 | 평균 잔량 | 아니오. 편차를 숨김 |
| **최솟값** | 가장 부족한 대상 기준 | **예** |

크레딧은 인스턴스별로 관리된다. 앱 한 대가 마르면 ALB 가 균등 분배하는 이상 그쪽으로 간 요청이 느려져 전체 p99 가 나빠진다. RDS 도 라이터와 리더 중 하나만 말라도 해당 쿼리가 느려진다.

**따라서 모든 대상의 가능 시간을 계산해 최솟값을 취한다.**

읽기 복제본을 도입하면 부하 성격에 따라 소비가 갈린다.

| 부하 | 라이터 | 리더 |
|------|--------|------|
| 읽기 위주 | 낮음 | 분산 |
| 쓰기 위주 | **높음** | 낮음 |

라이터가 병목이 되므로 라이터 기준으로 보수적으로 판정한다.

#### A.9.6 점검 스크립트

```bash
#!/usr/bin/env bash
set -euo pipefail

# 사용법: ./test-precheck.sh --minutes 13 --rampup 3 [--target-cpu 100]
MEASURE_MIN=""; RAMPUP_MIN=0; TARGET_CPU=100
while [ $# -gt 0 ]; do
  case "$1" in
    --minutes)    MEASURE_MIN=$2; shift 2 ;;
    --rampup)     RAMPUP_MIN=$2;  shift 2 ;;
    --target-cpu) TARGET_CPU=$2;  shift 2 ;;
    *) echo "알 수 없는 인자: $1" >&2; exit 1 ;;
  esac
done
[ -n "$MEASURE_MIN" ] || { echo "--minutes 필수" >&2; exit 1; }

LAG_MIN=5            # CloudWatch 기본 모니터링 간격
MIN_POSSIBLE=999999
BLOCKED=0

fail() { echo "시험 사전 점검 실패: $1" >&2; BLOCKED=1; }

# 인스턴스 타입에서 시간당 적립량을 구한다. 미등록이면 실패한다.
credit_per_hour() {
  case "${1#db.}" in
    t3.nano|t4g.nano)                 echo 6  ;;
    t3.micro|t4g.micro|t3a.micro)     echo 12 ;;
    t3.small|t4g.small|t3a.small)     echo 24 ;;
    t3.medium|t4g.medium|t3a.medium)  echo 24 ;;
    t3.large|t4g.large|t3a.large)     echo 36 ;;
    *) return 1 ;;
  esac
}

vcpu_of() {
  aws ec2 describe-instance-types --instance-types "${1#db.}" \
    --query 'InstanceTypes[0].VCpuInfo.DefaultVCpus' --output text 2>/dev/null || echo 2
}

current_balance() {
  aws cloudwatch get-metric-statistics \
    --namespace "$1" --metric-name CPUCreditBalance \
    --dimensions "Name=$2,Value=$3" \
    --start-time "$(date -u -d '15 minutes ago' +%Y-%m-%dT%H:%M:%SZ)" \
    --end-time   "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
    --period 300 --statistics Minimum \
    --query 'Datapoints | sort_by(@, &Timestamp)[-1].Minimum' --output text
}

evaluate() {
  local namespace=$1 dimension=$2 id=$3 itype=$4 label=$5
  local earn vcpu balance need possible wait_min

  earn=$(credit_per_hour "$itype") \
    || { fail "${label}: 미등록 인스턴스 타입 ${itype}. A.9.4 표에 추가 필요"; return; }
  vcpu=$(vcpu_of "$itype")

  balance=$(current_balance "$namespace" "$dimension" "$id")
  [ "$balance" != "None" ] || { fail "${label}: 크레딧 지표 조회 실패"; return; }

  read -r need possible <<EOF2
$(awk -v v="$vcpu" -v e="$earn" -v c="$TARGET_CPU" \
      -v m="$MEASURE_MIN" -v r="$RAMPUP_MIN" -v l="$LAG_MIN" -v b="$balance" '
  BEGIN {
    per_min = v * (c / 100) - (e / 60)
    if (per_min <= 0) { print 0, 999999; exit }
    need = m * per_min + r * per_min * 0.5 + l * per_min
    poss = (b - l * per_min) / per_min
    if (poss < 0) poss = 0
    printf "%d %d", need + 0.5, poss
  }')
EOF2

  [ "$possible" -lt "$MIN_POSSIBLE" ] && MIN_POSSIBLE=$possible

  if [ "$(awk -v b="$balance" -v n="$need" 'BEGIN{print (b>=n)?1:0}')" = "1" ]; then
    echo "  [통과] ${label} (${itype}) 잔량 ${balance}, 필요 ${need}, 최대 ${possible}분"
  else
    wait_min=$(awk -v b="$balance" -v n="$need" -v e="$earn" \
      'BEGIN { printf "%d", (n - b) / e * 60 }')
    fail "${label} (${itype}) 잔량 ${balance}, 필요 ${need}. 현재 ${possible}분만 가능. 유휴 기준 약 ${wait_min}분 후 재시도"
  fi
}

echo "시험 사전 점검: 측정 ${MEASURE_MIN}분 + 램프업 ${RAMPUP_MIN}분, 목표 부하 ${TARGET_CPU}%"

# 앱: ASG 에서 현재 인스턴스와 타입을 함께 조회한다
# 파이프 대신 프로세스 치환을 쓴다. 파이프로 while 을 돌리면 서브셸에서 실행되어
# BLOCKED 와 MIN_POSSIBLE 변경이 바깥으로 전달되지 않는다.
while read -r ID ITYPE; do
  [ -n "$ID" ] || continue
  evaluate AWS/EC2 InstanceId "$ID" "$ITYPE" "앱 ${ID}"
done < <(aws autoscaling describe-auto-scaling-groups \
           --auto-scaling-group-names "$ASG_NAME" \
           --query 'AutoScalingGroups[0].Instances[].[InstanceId,InstanceType]' \
           --output text)

# RDS: 프로젝트 태그로 라이터와 리더를 모두 조회한다
while read -r ID ICLASS; do
  [ -n "$ID" ] || continue
  evaluate AWS/RDS DBInstanceIdentifier "$ID" "$ICLASS" "RDS ${ID}"
done < <(aws rds describe-db-instances \
           --query "DBInstances[?TagList[?Key=='Project'&&Value=='${PROJECT}']].[DBInstanceIdentifier,DBInstanceClass]" \
           --output text)

# 모니터링 인스턴스 (단독. ASG 밖)
evaluate AWS/EC2 InstanceId "$MONITORING_INSTANCE_ID" "$MONITORING_INSTANCE_TYPE" "모니터링"

[ "$BLOCKED" -eq 0 ] || exit 1
echo "시험 가능. 전체 기준 최대 ${MIN_POSSIBLE}분"
```

실패 메시지에 세 가지를 담는다.

| 정보 | 쓰임 |
|------|------|
| 현재 잔량과 필요량 | 얼마나 부족한지 |
| **현재 가능한 시간** | 시험을 줄여서 진행할지 판단 |
| **회복 대기 시간** | 언제 다시 시도할지 |

**막기만 하면 개발자가 무엇을 해야 할지 모른다.** 두 번째가 있으면 "13분은 못 하지만 8분은 되니 장애 주입만 하자"는 판단이 가능하다.

#### A.9.7 목표 부하율 인자

`--target-cpu` 는 기본 100 이다. 이 값을 낮추면 필요 잔량이 줄어든다.

| 목표 부하 | db.t4g.micro 분당 순소비 | 13분 시험 필요 잔량 |
|-----------|--------------------------|---------------------|
| 100% | 1.8 | 30 |
| 70% | 1.2 | 20 |
| 50% | 0.8 | 13 |
| 10% (기준선 이하) | **적립이 소비를 상회** | 0 |

**기준선 이하 부하에서는 크레딧이 오히려 쌓인다.** db.t4g.micro 의 기준선은 10% 이므로 그 아래로는 게이트가 무의미하다. 스크립트는 분당 순소비가 0 이하면 제한 없음으로 처리한다.

앱을 여러 대로 늘렸을 때 이 인자가 중요해진다. 같은 총 부하라도 인스턴스가 늘면 인스턴스당 부하율이 내려가 소비가 준다. 다만 **시험 목적이 "1대의 한계 측정"이면 인스턴스를 늘려도 부하를 그만큼 올리므로 소비는 그대로다.** 어느 쪽인지는 스크립트가 판단할 수 없으므로 개발자가 입력한다.

#### A.9.8 그 외 점검 항목

크레딧 외에 확인할 것들이다.

| 항목 | 기준 | 어긋났을 때 |
|------|------|-------------|
| RDS 상태 | 모든 인스턴스 `available` | 시험 중 기동이 완료되면 구간이 갈림 |
| ElastiCache 상태 | `available` | 강등 경로가 섞여 판정이 흐려짐 |
| 대상 그룹 | healthy 수가 desired 와 일치 | 이미 축소된 용량으로 측정하게 됨 |
| 모니터링 | Prometheus, Loki 응답 | 관측 없는 시험은 무의미 |
| Watchdog | 최근 5분 내 신호 | 알림 파이프라인이 끊긴 상태 |
| 직전 시험과의 간격 | 10분 이상 | 지표 해상도 문제 |
| 배포 진행 여부 | 진행 중이 아님 | 인스턴스 수가 달라 조건이 바뀜 |

#### A.9.9 직전 시험과 10분 간격을 두는 이유

CloudWatch 기본 모니터링은 5분 간격이다. 부하 시험 직후에는 **마지막 데이터 포인트가 시험 시작 전 값일 수 있어, 실제보다 높은 잔량이 보인다.**

```
14:00  잔량 200. 시험 시작
14:13  시험 종료. 실제 잔량 177
14:14  재시험 시도 -> 조회된 값은 14:10 시점의 189   <- 실제와 다름
```

스크립트가 `Minimum` 통계를 쓰고 지연 보정을 더하는 것도 같은 이유다. 그럼에도 오차는 남으므로 간격 규칙을 함께 둔다.

#### A.9.10 알람 임계와의 관계

게이트가 예정 시간 기반으로 동작하므로 알람 임계와 역할이 분리된다.

| 구분 | 기준 | 목적 |
|------|------|------|
| 알람 경고 (최대의 30%) | 고정 | 추세를 알린다. 곧 시험이 어려워진다는 예고 |
| 알람 위험 (최대의 10%) | 고정 | 평상시에 여기까지 떨어졌다면 원인 조사 |
| 시험 게이트 | **예정 시간과 현재 구성 기반** | 이번 시험이 가능한가 |

**알람은 상태를 알리고 게이트는 작업을 막는다.** 목적이 다르므로 같은 값을 쓸 이유가 없다.

시험 직후가 아닌데 위험 알람이 뜬다면 시험 때문이 아니라 비효율적인 코드나 예상 못 한 부하가 있다는 신호다.

#### A.9.11 시험 후 처리

| 항목 | 내용 |
|------|------|
| 관측 데이터 내보내기 | Prometheus 스냅샷, k6 결과를 S3 로 |
| 크레딧 회복 대기 | 다음 시험의 예정 시간에 필요한 만큼 |
| 알람 침묵 해제 | 시험용으로 침묵시킨 알람 복원 |
| 시험 조건 기록 | 시작 시각, 측정과 램프업 시간, 목표 부하율, 대상별 시작 잔량, 인스턴스 수와 타입 |

마지막 항목이 중요하다. **같은 시험을 나중에 반복할 때 조건이 같아야 비교가 성립한다.** 인스턴스 타입이나 개수가 다르면 같은 부하에도 다른 결과가 나온다.

#### A.9.12 확장이 필요해지는 조건

현재 스크립트는 앱 ASG, RDS, 모니터링 인스턴스를 대상으로 한다. 다음 경우 확장한다.

| 조건 | 추가 작업 |
|------|-----------|
| 새 인스턴스 타입 도입 | A.9.4 표에 적립량 추가 |
| ElastiCache 를 버스터블로 운영 | 대상에 추가 |
| RDS 읽기 복제본 도입 | 이미 태그 기반 조회로 대응됨. 라이터 우선 판정만 확인 |
| 부하 생성 인스턴스가 병목 | t3a.small 도 대상에 추가 |
