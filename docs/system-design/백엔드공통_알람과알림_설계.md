## 1. 문서 목적

지금까지 다섯 문서에 흩어져 있던 알람 후보를 한곳에 모으고, 각각의 경로와 심각도와 전달 채널을 정한다.

**임계값의 상당수는 비어 있다.** 부하 시험과 실측 없이 정한 숫자는 오탐과 미탐을 동시에 만든다. 값이 정해진 것과 정해지지 않은 것을 구분해 표시했다.

전제는 두 가지다.

| 전제 | 내용 |
|---|---|
| 무료 한도 우선 | CloudWatch 프리티어 안에서 운용한다 |
| 모니터링은 단일 장애점 | 모니터링이 죽어도 알 수 있는 경로가 필요하다 |

## 2. 경로 배분 원칙

판단 기준은 하나다. **모니터링 인스턴스가 죽어도 알아야 하는가.**

```
알람 후보
  |
  +-- 모니터링이 죽으면 알 수 없는가?
  |     예 -> CloudWatch (무료 한도 내)
  |     아니오
  |       |
  |       +-- 앱이 직접 노출하는 지표인가?
  |             예 -> Prometheus (추가 비용 없음)
  |             아니오 -> cloudwatch_exporter -> Prometheus
```

관측성을 자체 호스팅하기로 한 결정(INF-10)의 대가가 여기 있다. 관리형 대비 비용은 낮지만 모니터링 인스턴스가 단일 장애점이 되므로, 그것을 감시할 수단이 밖에 있어야 한다.

### 2.1 CloudWatch에 두는 것

| 알람 | 발생 방식 | 지표 또는 이벤트 | 이유 |
|---|---|---|---|
| 모니터링 인스턴스 소실 | 지표 알람 | `StatusCheckFailed` | Prometheus는 자기 죽음을 알릴 수 없다 |
| Route 53 헬스체크 실패 | 지표 알람 | `HealthCheckStatus` | 외부 관점. 모니터링과 독립 |
| ALB 정상 호스트 수 | 지표 알람 | `HealthyHostCount` | 서비스 중단 직결 |
| ACM 인증서 잔여일 | 지표 알람 | `DaysToExpiry` | 놓치면 전면 접속 불가 |
| 백업 미생성 | 지표 알람 | `LatestRestorableTime` 기반 | 복구 불가로 직결 |
| RDS 페일오버 발생 | **이벤트 구독** | RDS 이벤트 카테고리 `failover` | 이벤트 소스가 AWS |

**지표 알람 5개만 알람 지표로 계산된다. 무료 한도 10개 중 5개 여유.**

마지막 행은 CloudWatch 지표에 임계를 거는 방식이 아니라 **RDS 이벤트 구독이 SNS 주제로 직접 발행하는 구조**다. 따라서 알람 지표 개수에 포함되지 않는다.

```bash
aws rds create-event-subscription \
  --subscription-name "${PROJECT}-failover" \
  --sns-topic-arn "$SNS_CRITICAL_ARN" \
  --source-type db-instance \
  --event-categories failover \
  --source-ids "$DB_ID"
```

**메시지 형식이 지표 알람과 다르다.** AWS Chatbot이 지표 알람은 구조화해 표시하지만 서비스 이벤트를 어떻게 렌더링하는지는 확인하지 않았다. 원문 JSON으로 나올 수 있으므로 구축 시 실제로 발동시켜 확인한다.

여유분은 예비로 남긴다. 운영하다 CloudWatch에 두어야 할 항목이 나올 수 있다.

### 2.2 Prometheus에 두는 것

| 알람 | 수집 경로 |
|---|---|
| 5xx 비율 | cloudwatch_exporter |
| ALB 502 발생 | cloudwatch_exporter |
| TargetResponseTime p99 | cloudwatch_exporter |
| ConsumedLCUs | cloudwatch_exporter |
| RDS 여유 메모리 | cloudwatch_exporter |
| CPU 크레딧 잔량 | cloudwatch_exporter |
| HikariCP 활성 및 대기 커넥션 | 앱 actuator |
| 톰캣 사용 중 스레드 | 앱 actuator |
| readiness 실패 | 앱 actuator |
| 배치 미실행 | 앱 지표 |
| 정합성 검증 실패 | 앱 지표 |
| 캐시 연결 실패 | redis_exporter |
| 컨테이너 재기동 반복 | cAdvisor |
| 디스크 사용률 | node_exporter |

**14개. 추가 비용 없음.**

## 3. 무료 한도 관리

### 3.1 한도와 사용 계획

CloudWatch 프리티어는 커스텀 지표 10개, 표준 해상도 알람 지표 10개, API 요청 100만 건, 로그 수집 5GB와 아카이브 5GB, 대시보드 3개를 포함한다. 대부분 12개월 한정이 아니라 상시 무료이며, **한도는 리전별로 적용되고 리전 간 합산되지 않는다.**

| 항목 | 한도 | 사용 예정 | 여유 |
|---|---|---|---|
| 알람 지표 | 10 | **5** | 5 |
| 커스텀 지표 | 10 | **0** | 10 |
| API 요청 | 100만 | 약 20만 | 넉넉 |
| 로그 수집 | 5GB | 수십 MB | 넉넉 |
| 대시보드 | 3 | **0** | 3 |
| SNS 알림 | 100만 | 수백 | 넉넉 |

커스텀 지표와 대시보드를 0으로 두는 이유는 Prometheus와 Grafana가 그 역할을 하기 때문이다. 중복해서 쓸 이유가 없다.

### 3.2 알람은 개수가 아니라 지표 수로 센다

**알람은 알람에 포함된 지표 수를 기준으로 과금된다.** 알람 표현식에 나열된 지표마다 과금되며, 메트릭 수식을 쓰면 하나의 알람에 최대 10개까지 들어갈 수 있다.

즉 알람 하나가 지표 하나를 보면 1로 세지만, 지표 셋을 조합하면 3으로 센다. 2.1절의 6개는 전부 단일 지표 알람이다.

### 3.3 금지 규칙

| 규칙 | 이유 |
|---|---|
| 이상 탐지 알람 금지 | 실제 값, 상한, 하한 세 지표를 감시해 3배 |
| 복합 알람 금지 | 결합 수와 무관하게 개당 0.50 USD |
| 고해상도 알람 금지 | 지표당 0.30 USD (표준은 0.10) |
| 커스텀 지표 전송 금지 | 지표당 월 0.30 USD |
| CloudWatch 대시보드 금지 | 4개째부터 개당 3 USD. Grafana 사용 |
| 로그 그룹 보존 기간 필수 지정 | 기본값이 무기한이라 저장이 누적 |
| RDS 일반 로그 비활성 | 부하 시험 중 GB 단위로 증가 |

로그 보존 기간은 Terraform에서 강제한다.

```hcl
resource "aws_cloudwatch_log_group" "rds_slowquery" {
  name              = "/aws/rds/instance/${var.db_id}/slowquery"
  retention_in_days = 30   # 생략 불가 규칙
}
```

### 3.4 cloudwatch_exporter 스크랩 간격

**CloudWatch 지표 자체가 기본 60초 간격이다.** 15초로 긁으면 같은 값을 네 번 받으면서 API 요청만 네 배로 늘어난다.

| 지표군 | 간격 | 근거 |
|---|---|---|
| ALB 5xx, 502, 응답시간 | 60초 | 원본 간격과 일치 |
| RDS 여유 메모리, 커넥션 | 60초 | 동일 |
| CPU 크레딧 | 300초 | 서서히 변함 |

앱 지표는 Prometheus가 직접 15초로 긁으므로 그 간격이 유지된다. **짧은 간격이 필요한 것은 앱 지표이지 관리형 서비스 지표가 아니다.**

이렇게 조정하면 월 API 요청이 약 20만 건으로 무료 한도 100만 건 안에 넉넉히 들어간다. 15초 간격으로 지표 6개를 긁으면 월 약 104만 건이 되어 한도를 넘는다.

## 4. 알림 채널

### 4.1 경로

```
CloudWatch 지표 알람 (5개) --+
                             +--> SNS 주제 (critical) --+--> AWS Chatbot --> Slack #alerts-critical
RDS 이벤트 구독 (1개) --------+                          +--> 이메일 (대체 경로)

Prometheus --> Alertmanager --+--> Slack Webhook --> #alerts-critical
                              +--> Slack Webhook --> #alerts-warning
```

**SNS 주제는 하나만 만든다.** CloudWatch로 보내는 6개가 전부 Critical 이므로 warning 주제로 갈 메시지가 없다. 나중에 CloudWatch 쪽에 Warning 알람을 추가하게 되면 그때 주제를 하나 더 만든다.

Warning 11개는 전부 Prometheus 쪽이며 Alertmanager 가 Slack 으로 직접 보낸다.

#### SNS 를 거치는 이유

CloudWatch 알람은 외부 서비스를 직접 호출할 수 없다. 알람이 수행할 수 있는 동작은 SNS 발행, Auto Scaling 실행, EC2 조작 정도다. 따라서 Slack 으로 보내려면 SNS 를 거쳐야 한다.

부수적인 이점도 있다. **발행자는 수신처를 모른다.** 알람 설정을 건드리지 않고 구독만 추가하면 수신처가 늘어난다. Slack 과 이메일을 함께 붙인 이중 경로가 이 구조 덕분에 가능하다.

SNS 는 발행된 메시지를 보관하지 않는다. 전달 후 조회할 수 없으므로, 알람 이력은 CloudWatch 알람의 상태 변경 이력이나 Slack 채널 기록으로 확인한다.

**경로가 둘로 갈린다는 점이 중요하다.**

| 출처 | 발송 주체 | 필요한 것 | 도착 채널 | 비용 |
|---|---|---|---|---|
| CloudWatch 6개 (전부 Critical) | AWS Chatbot | Chatbot 연동, SNS 주제 1개 | `#alerts-critical` | 0 (SNS 월 100만 건 무료) |
| Prometheus 3개 (Critical) | **Alertmanager** | Slack Webhook | `#alerts-critical` | 0 |
| Prometheus 11개 (Warning) | **Alertmanager** | Slack Webhook | `#alerts-warning` | 0 |

**Prometheus 쪽은 Chatbot을 거치지 않는다.** Alertmanager가 Slack Webhook을 직접 지원하므로 AWS 서비스를 경유할 이유가 없다. 알람 개수 제한도 없고 비용도 들지 않는다.

**AWS Chatbot이 Slack을 직접 지원하므로 변환 코드가 필요 없다.** Discord를 검토했으나 Chatbot이 지원하지 않아 Lambda를 직접 만들어야 했고, 그 Lambda가 새로운 단일 장애점이 되어 다시 그것을 감시할 알람이 필요해지는 문제가 있었다.

이메일 대체 경로는 Slack 자체 장애나 Chatbot 연동 문제를 대비한다.

#### 두 경로를 유지하는 이유

**Alertmanager는 모니터링 인스턴스 안에서 돈다.** 그 인스턴스가 죽으면 Prometheus와 함께 죽고, 알람이 오지 않으며 안 온다는 사실 자체를 알 수 없다.

| 상황 | Prometheus 경로 | CloudWatch 경로 |
|---|---|---|
| 앱 장애 | 동작 | 동작 |
| DB 장애 | 동작 | 동작 |
| **모니터링 인스턴스 소실** | **침묵** | 동작 |

2.1절에서 CloudWatch에 6개를 남긴 근거가 이 표의 마지막 행이다.

### 4.2 Alertmanager 설정

```yaml
# alertmanager.yml
route:
  receiver: warning
  group_by: [alertname, instance]
  group_wait: 30s          # 같은 그룹의 알람을 모아 보내기까지 대기
  group_interval: 5m       # 같은 그룹에 새 알람이 추가될 때 간격
  repeat_interval: 4h      # 해소되지 않은 알람의 재발송 주기
  routes:
    - matchers: [severity="critical"]
      receiver: critical
      repeat_interval: 1h
    - matchers: [severity="watchdog"]
      receiver: watchdog
      group_wait: 0s
      group_interval: 5m
      repeat_interval: 5m

receivers:
  - name: critical
    slack_configs:
      - api_url_file: /run/secrets/slack_webhook_critical
        channel: '#alerts-critical'
        title: '[CRITICAL] {{ .CommonLabels.alertname }}'
        text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'
        send_resolved: true      # 대응 중인 사람이 복구를 알아야 한다
  - name: warning
    slack_configs:
      - api_url_file: /run/secrets/slack_webhook_warning
        channel: '#alerts-warning'
        title: '[WARNING] {{ .CommonLabels.alertname }}'
        send_resolved: false     # 스스로 해소되는 경우가 많아 소음이 된다
  - name: watchdog
    slack_configs:
      - api_url_file: /run/secrets/slack_webhook_watchdog
        channel: '#alerts-watchdog'
        send_resolved: false
```

#### 해소 통지를 심각도별로 나누는 이유

`send_resolved`는 알람이 해소되었을 때 복구 통지를 보낼지 결정한다. 기본값은 꺼짐이다.

| 심각도 | 설정 | 근거 |
|---|---|---|
| Critical | 켬 | 사람이 대응에 들어간 상태라 "끝났다"를 알려야 한다 |
| Warning | 끔 | 저절로 해소되는 경우가 많아 메시지가 두 배가 된다 |

**대응하지 않은 알람의 복구 통지는 정보 가치가 없다.** CPU 크레딧이 임계 아래로 떨어졌다 저절로 회복되는 식의 알람에까지 복구 통지를 켜면 채널이 소음으로 찬다.

CloudWatch 쪽은 6개가 전부 Critical 이므로 모두 켠다. 알람에 OK 상태 동작을 지정하면 된다.

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name "${PROJECT}-healthy-host-count" \
  --alarm-actions "$SNS_CRITICAL_ARN" \
  --ok-actions "$SNS_CRITICAL_ARN"      # 이 줄이 복구 통지
```

### 4.3 Watchdog: 알림이 오지 않는 것을 감지한다

**Alertmanager가 죽거나 Slack 연동이 끊기면 알람이 오지 않고, 오지 않는다는 사실을 알 수 없다.** 모니터링 인스턴스가 통째로 소실되면 CloudWatch가 잡지만, Alertmanager 프로세스만 죽는 경우는 아무도 모른다.

**항상 참인 알람을 하나 두고 주기적으로 발송한다.** 그것이 오지 않으면 파이프라인이 끊긴 것이다.

```yaml
# prometheus/rules/watchdog.yml
groups:
  - name: watchdog
    rules:
      - alert: Watchdog
        expr: vector(1)          # 항상 참
        labels:
          severity: watchdog
        annotations:
          description: "알림 파이프라인이 살아 있음을 확인하는 신호"
```

5분마다 발송되므로 하루 288건이다. **사람이 읽는 채널에 보내면 안 된다.** 전용 채널 `#alerts-watchdog`에 쌓아 두고, 다음 시점에만 확인한다.

| 확인 시점 | 확인 내용 |
|---|---|
| Critical 알람을 받았을 때 | 마지막 watchdog 시각이 5분 이내인가 |
| 장시간 알람이 없어 이상할 때 | 동일 |
| 세션 시작 후 | 파이프라인이 살아났는가 |
| 주 1회 알람 통계 검토 시 | 끊긴 구간이 있었는가 |

**첫 행이 실질적인 쓰임이다.** Critical 알람이 왔을 때 watchdog 채널의 마지막 메시지가 30분 전이면, 그 사이 다른 알람도 누락되었을 수 있다는 신호다.

자동 감시(CloudWatch 알람으로 watchdog 부재를 감지)도 가능하나 채택하지 않았다. 로그 기반 지표 필터가 커스텀 지표로 계산되는지 확인이 필요하고, 무료 한도 관리가 복잡해진다. **비용과 복잡도가 0인 수동 확인으로 시작하고, 누락 사고가 실제로 발생하면 자동화를 검토한다.**

이 방식의 한계는 명확하다. **사람이 확인하지 않으면 감지되지 않는다.** 다만 알림 파이프라인이 끊긴 상태에서 아무 알람도 오지 않는 것보다는, 알람이 왔을 때 파이프라인 상태를 함께 확인할 수단이 있는 편이 낫다.

**웹훅 URL은 설정 파일에 평문으로 넣지 않는다.** 이 URL을 아는 사람은 누구나 해당 채널에 글을 쓸 수 있어 사실상 자격증명이다. SSM Parameter Store SecureString에 보관하고, 컨테이너 기동 시 파일로 주입해 `api_url_file`로 참조한다.

`repeat_interval`을 심각도별로 다르게 둔 이유는, Critical은 해소될 때까지 잊히면 안 되고 Warning은 반복되면 소음이 되기 때문이다.

### 4.4 채널 분리

| 채널 | 대상 | 발송 주체 | 멘션 | 해소 통지 |
|---|---|---|---|---|
| `#alerts-critical` | 서비스 중단, 데이터 손실 위험 | Chatbot, Alertmanager | 팀 역할 태그 | 켬 |
| `#alerts-warning` | 예방적 경보, 추세 이상 | Alertmanager | 없음 | 끔 |
| `#alerts-deploy` | 배포 시작, 성공, 실패 | **GitHub Actions** | 실패 시만 | - |
| `#alerts-watchdog` | 파이프라인 생존 신호 (5분 주기) | Alertmanager | 없음 | 끔 |

채널은 팀 Slack 워크스페이스에 개발 구현 착수 전에 생성한다.

**야간과 주말을 구분하지 않는다.** 검증 환경이라 즉시 대응이 필수는 아니지만, 시간대별로 발송을 나누면 규칙이 복잡해지고 "이 시간에는 안 오는 게 정상"이라는 예외가 생긴다. 받되 대응 여부는 상황에 따라 판단한다.

**채널 분리가 알람 피로를 줄이는 가장 단순한 수단이다.** 모든 알람이 한 채널에 섞이면 중요한 것을 놓친다.

### 4.5 Chatbot 권한

Chatbot은 Slack 채널에서 CloudWatch 조회 명령을 실행할 수 있다. 편리하지만 **읽기 전용 정책만 부여한다.** 쓰기 권한이 붙으면 채널 접근 권한이 곧 인프라 변경 권한이 된다.

### 4.6 이력 보존

Slack 무료 플랜은 메시지 이력이 90일까지 조회된다. 이 프로젝트 기간을 덮으므로 별도 보존은 하지 않는다.

사후 분석에는 CloudWatch 알람 자체의 상태 변경 이력과 Prometheus의 지표 이력을 쓴다. 알람 이력을 별도 로그로 남기는 것은 중복이다.

## 5. 알람 정의

심각도는 둘로만 나눈다. 셋 이상으로 나누면 중간 등급의 처리 기준이 모호해진다.

| 심각도 | 기준 | 채널 |
|---|---|---|
| Critical | 서비스가 중단되었거나 데이터가 손실될 수 있음 | `#alerts-critical` |
| Warning | 방치하면 Critical이 됨 | `#alerts-warning` |

### 5.1 Critical

| 알람 | 경로 | 조건 | 대응 |
|---|---|---|---|
| 외부 접속 실패 | CloudWatch | Route 53 헬스체크 2회 연속 실패 | 즉시 확인 |
| 정상 호스트 수 0 | CloudWatch | `HealthyHostCount` 0, 1분 지속 | 앱 상태 확인 |
| 모니터링 인스턴스 소실 | CloudWatch | `StatusCheckFailed` 2회 | 재기동 |
| RDS 페일오버 발생 | CloudWatch (이벤트 구독) | 이벤트 카테고리 `failover` | 앱 재연결 확인 |
| 인증서 만료 임박 | CloudWatch | 잔여 30일 미만 | 갱신 확인 |
| 백업 미생성 | CloudWatch | `LatestRestorableTime`이 (미정)분 이상 지연 | 백업 설정 확인 |
| 정합성 검증 실패 | Prometheus | 검증 쿼리가 0행이 아님 | **원인 차단 후** 백업과 복원 문서 9절 런북 (5.4절) |
| 5xx 비율 급증 | Prometheus | 배포 전 대비 2배, 3분 지속 | 롤백 판단 |
| 502 발생 | Prometheus | (미정) 초과 | 앱 프로세스 확인 |

**정합성 검증 실패만 사고 발생과 증상 발현 사이에 시간차가 있는 유형을 다룬다.** 나머지 알람은 사고와 증상이 같은 시각에 일어나지만, 누적 값 오차는 발생 시점에 아무 오류도 내지 않고 며칠 뒤 무관해 보이는 다른 트랜잭션에서 실패로 나타난다. 상세는 5.4절에 정리했다.

### 5.2 Warning

| 알람 | 경로 | 조건 | 대응 |
|---|---|---|---|
| CPU 크레딧 잔량 (경고) | Prometheus | 최대 누적량의 30% 미만 (t3.small 173, db.t4g.micro 86) | 부하 확인 |
| CPU 크레딧 잔량 (위험) | Prometheus | 최대 누적량의 10% 미만 (t3.small 58, db.t4g.micro 29) | 즉시 원인 조치 |
| RDS 여유 메모리 | Prometheus | (미정) 미만 | 쿼리 확인 |
| HikariCP 대기 커넥션 | Prometheus | 풀 크기의 90% 초과 | 느린 쿼리 확인 |
| 톰캣 스레드 사용률 | Prometheus | (미정)% 초과 | 병목 확인 |
| p99 응답시간 | Prometheus | 기준선 대비 3배 | 원인 조사 |
| 배치 미실행 | Prometheus | 주기 초과 후 실행 로그 부재 | 스케줄러 확인 |
| 캐시 연결 실패 | Prometheus | 1분 지속 | 강등 경로 동작 확인 |
| 컨테이너 재기동 반복 | Prometheus | 10분 내 3회 이상 | OOM 여부 확인 |
| 디스크 사용률 | Prometheus | 80% 초과 | 로그 정리 |
| ConsumedLCUs | Prometheus | (미정) 초과 | 비용 확인 |
| readiness 실패 | Prometheus | 90초 초과 | 배포 중단 |

### 5.3 배포 알림

알람이 아니라 정보성 통지다. **GitHub Actions 워크플로가 Slack Webhook 으로 직접 보낸다.** CloudWatch 나 Alertmanager 를 거치지 않는다. 배포 진행 상황은 지표가 아니라 워크플로의 단계 정보이므로, 그것을 아는 주체가 직접 보내는 것이 단순하다.

| 통지 | 시점 | 멘션 |
|---|---|---|
| 배포 시작 | SSM 갱신 직후 | 없음 |
| 신규 인스턴스 healthy | 검증 통과 | 없음 |
| 배포 완료 | 구 인스턴스 종료 후 | 없음 |
| 배포 실패 | 중단 시 | **팀 역할 태그** |
| 롤백 수행 | 시작과 완료 | 팀 역할 태그 |

Webhook URL 은 GitHub Actions 시크릿에 보관한다. SSM 에 두는 다른 URL 과 달리 워크플로가 AWS 자격증명을 얻기 전에도 써야 하므로, 저장소 시크릿이 적합하다.

배포 중 발생하는 일시적 경보는 7.1절의 억제 규칙으로 `#alerts-warning` 에서 걸러진다. 두 채널의 역할이 겹치지 않는다.

### 5.4 정합성 검증 실패 알람의 대응

#### 왜 별도 취급이 필요한가

다른 알람은 **사고 발생, 증상 발현, 감지가 같은 시각에 일어난다.**

```
14:00  인스턴스 소실
14:00  사용자 요청이 502 로 실패
14:00  헬스체크 실패 -> 알람 발생
```

알람이 없어도 사용자가 먼저 알려준다.

누적 값 오차는 다르다.

```
14:00  배치가 중복 실행되어 재고 수량이 +3 부풀려짐
14:00  오류 없음. 로그도 깨끗함. 예외도 발생하지 않음
14:00  사용자 화면에는 재고 3개가 더 있는 것으로 표시됨
       (실제 로트에는 없지만 화면상 정상)
       ... 며칠간 정상 주문이 계속 처리됨 ...
17:20  누군가 그 3개를 주문
17:20  차감하려는데 실제 로트에 재고가 없어 주문 실패
17:20  "재고 부족" 오류 발생  <- 사고 원인과 전혀 달라 보인다
```

**사고는 14:00 에 났는데 오류는 며칠 뒤 17:20 에 나고, 그 오류 메시지는 원인을 가리키지 않는다.**

이 시간차가 세 가지 문제를 만든다.

| 문제 | 내용 |
|---|---|
| 원인 추적 곤란 | 17:20 의 재고 부족을 보고 며칠 전 배치를 의심하기까지 시간이 걸린다 |
| 복구 불가능 | 사고 직후면 13:55 로 되돌리면 되지만, 며칠 지나면 그 사이 정상 주문이 수백 건 쌓여 있다 |
| 피해 누적 | 배치가 5분 주기면 인지할 때까지 같은 오류가 반복된다. 하루면 288회 |

정합성 검증 배치는 **증상이 나타나기 전에 원인을 잡는다.**

| 감지 수단 | 잡는 시점 |
|---|---|
| 재고 부족 오류 알람 | 17:20 (증상) |
| 정합성 검증 배치 (시간당 1회) | 15:00 (원인. 다음 검증 주기) |

1시간 안에 발견하면 유입된 정상 데이터가 적어 부분 복구가 수월하다. **검증 주기가 곧 복구 가능성을 결정한다.**

#### 대응이 다른 이유

| 구분 | 일반 알람 | 정합성 검증 실패 |
|---|---|---|
| 알리는 것 | 지금 문제가 생기고 있다 | 이미 문제가 생겼다 |
| 복구 대상 | 인스턴스, 프로세스 | **데이터** |
| 대응 | 복구하면 끝 | 사고 이후 유입분을 함께 판단해야 함 |

정상 호스트 수가 0이면 인스턴스를 살리면 된다. 그러나 누적 값이 이력과 맞지 않으면 되돌릴 것이 데이터이고, 그 사이에 정상 거래가 쌓여 있다.

**따라서 이 알람은 "고쳐라"가 아니라 "런북을 시작하라"는 신호다.**

```
1. 원인 차단   확대 중인가? 배치 중지 또는 배포 롤백      <- 복원보다 먼저
2. 범위 파악   몇 건인가, 오차 크기는 얼마인가
3. 시점 특정   변경 이력을 거슬러 사고 발생 시각을 찾는다
4. 방식 결정   부분 복구인가 전체 복원인가
5. 실행        백업과 복원 문서 7절
6. 기록        같은 문서 9.2절
```

**1번이 복원보다 먼저다.** 잘못된 배치가 계속 돌고 있는데 복원부터 하면 복원본도 곧 오염된다.

3번이 가능하려면 변경 이력이 있어야 한다. 없으면 시점을 특정할 수 없고 부분 복구가 불가능해진다. INF-27이 되돌릴 수 없는 항목인 이유다.

#### 알람 메시지에 담을 정보

검증 쿼리는 "몇 번 행이 얼마나 어긋났다"까지만 알려준다. **언제부터 어긋났는지는 말해주지 않는다.** 1차 판단에 필요한 정보를 알람 메시지에 함께 실으면 대응이 빨라진다.

| 담을 정보 | 얻는 것 |
|---|---|
| 어긋난 레코드 수 | 범위 감각 |
| 최대 오차 크기 | 심각도 |
| 해당 레코드의 최근 변경 시각 | 사고 시점 추정 |
| 최근 변경 주체 (BATCH 인가 사용자인가) | 원인 추정 |

마지막 둘이 특히 유용하다. 어긋난 레코드들의 최근 변경이 전부 같은 시각의 BATCH 라면 원인이 배치라는 것이 즉시 드러난다.

## 6. CPU 크레딧 알람 상세

앞선 논의에서 임계값 산정 방법이 명확하지 않았던 항목이라 따로 정리한다.

### 6.1 지표 출처

`CPUCreditBalance`는 하이퍼바이저가 관리하는 값이라 **인스턴스 내부에서 볼 수 없다.** node_exporter로는 수집이 불가능하며, CloudWatch가 유일한 출처다. cloudwatch_exporter를 통해 Prometheus로 가져온다.

### 6.2 임계값 산정

잔량의 절대값만으로는 판단이 어렵다. **남은 시간으로 환산해야 대응 여유를 알 수 있다.**

```
소진까지 남은 시간 = 현재 잔량 / (시간당 소비량 - 시간당 적립량)
```

1 CPU 크레딧은 vCPU 하나를 1분간 100% 사용하는 양이다. 최대 누적량은 24시간 동안 적립 가능한 양과 같다(시간당 적립량 x 24).

| 인스턴스 | vCPU | 기준선 | 시간당 적립 | 최대 누적 | 경고(30%) | 위험(10%) |
|---|---|---|---|---|---|---|
| t3.small (앱) | 2 | 20% | 24 | 576 | 173 | 58 |
| t4g.small (모니터링) | 2 | 20% | 24 | 576 | 173 | 58 |
| db.t4g.micro (RDS) | 2 | 10% | 12 | 288 | 86 | 29 |

t3.small 은 시간당 24 크레딧을 적립하며 최대 576 까지 누적된다. 한도를 넘으면 새로 적립되는 크레딧은 버려진다.

#### 임계값이 주는 대응 여유

두 vCPU 를 100% 쓰면 시간당 120 크레딧을 소비하므로, 적립분을 빼면 순소비는 시간당 96 이다.

| 인스턴스 | 잔량 만재(100%) | 경고 시점(30%) | 위험 시점(10%) |
|---|---|---|---|
| t3.small | 6시간 | 1.8시간 | 0.6시간 |
| db.t4g.micro | 2.7시간 | 0.8시간 | 0.3시간 |

**위험 임계에서는 대응 여유가 30분 남짓이다.** 경고 단계에서 원인을 확인하지 않으면 사실상 손쓸 시간이 없다. 그래서 두 단계로 나눈다.

RDS 는 EC2 보다 적립량이 절반이라 소진이 두 배 빠르다. 부하 시험 중에는 RDS 쪽 크레딧을 먼저 본다.

### 6.3 시험 착수 게이트로도 쓰인다

시험을 시작하기 전에 크레딧이 충분한지 확인한다. 부족한 상태로 부하를 걸면 측정한 값이 서버 성능이 아니라 크레딧 소진 시점이 된다.

**다만 게이트는 알람과 다른 기준을 쓴다.** 고정 임계가 아니라 **예정 시험 시간과 그 시점의 인프라 구성을 함께 보고 계산**한다.

| 축 | 정하는 것 | 주체 |
|---|---|---|
| 시험 길이 | 몇 분 돌릴 것인가 | 사람이 선택 |
| 필요 잔량 | 그 시간에 얼마가 필요한가 | 스크립트가 구성 조회 후 계산 |

시험 유형마다 필요 시간이 다르고(장애 주입 7분, 기준선 측정 13분), 인스턴스 타입과 개수도 시간이 지나면 바뀐다. 하나의 고정값으로는 짧은 시험이 불필요하게 막히거나 긴 시험이 도중에 마른다.

| 구분 | 기준 | 목적 |
|---|---|---|
| 알람 경고 (30%) | 고정 | 곧 시험이 어려워진다는 예고 |
| 알람 위험 (10%) | 고정 | 평상시에 여기까지 떨어졌다면 원인 조사 |
| 시험 게이트 | **예정 시간 기반** | 이번 시험이 가능한가 |

**알람은 상태를 알리고 게이트는 작업을 막는다.** 계산식과 점검 스크립트는 기술 스택 문서 부록 A.9에 있다.

### 6.4 스케일링 트리거로 쓰지 않는다

오토스케일링 설계 문서 3.2절에서 정한 내용이다. 크레딧 소진은 트래픽 증가가 아니라 비효율적인 코드 때문일 수도 있어, 인스턴스를 늘려도 근본 원인이 남는다. **알람으로 알리고 사람이 판단한다.**

### 6.5 수집 간격

CloudWatch 기본 모니터링은 5분 간격이다. 크레딧은 서서히 변하므로 5분이면 충분하다. 1분 간격으로 보려면 상세 모니터링을 켜야 하고 이는 유료다.

부하 시험 구간에만 상세 모니터링을 켜는 방법도 있다. 평상시에는 크레딧이 줄 일이 거의 없다.

## 7. 알람 규칙의 코드 관리

**설정을 인스턴스에서 직접 고치면 재생성 시 사라진다.** 절감 스크립트로 인스턴스를 내렸다 올리거나 Terraform 으로 재생성하면 초기 상태로 돌아간다.

| 대상 | 형태 | 관리 방법 |
|---|---|---|
| Prometheus 알람 규칙 | 파일 | Git |
| Alertmanager 설정 | 파일 | Git |
| Grafana 대시보드와 데이터소스 | 파일 | Git |
| CloudWatch 알람, SNS 주제, RDS 이벤트 구독 | AWS 리소스 | **Terraform** |

### 7.1 파일 배치

```
repo/
└─ monitoring/
   ├─ prometheus/
   │  ├─ prometheus.yml
   │  └─ rules/
   │     ├─ critical.yml
   │     ├─ warning.yml
   │     └─ watchdog.yml
   ├─ alertmanager/
   │  └─ alertmanager.yml
   └─ grafana/
      └─ provisioning/
         ├─ dashboards/
         └─ datasources/
```

```yaml
# 모니터링 인스턴스의 compose
services:
  prometheus:
    image: prom/prometheus:v3.13.1
    volumes:
      - ./prometheus:/etc/prometheus:ro     # 읽기 전용
      - prom-data:/prometheus
  alertmanager:
    image: prom/alertmanager
    volumes:
      - ./alertmanager:/etc/alertmanager:ro
      - /run/secrets:/run/secrets:ro
```

**설정을 읽기 전용으로 마운트한다.** 컨테이너 안에서 고치지 못하게 막아, 모든 변경이 Git 을 거치게 강제한다. 인프라 변경을 Terraform 으로만 한다는 규칙과 같은 논리다.

### 7.2 반영 방법

GitHub Actions 에서 SSM 으로 파일을 내려보내고 설정을 다시 읽게 한다. 재기동이 필요 없다.

```bash
curl -X POST http://localhost:9090/-/reload      # Prometheus
curl -X POST http://localhost:9093/-/reload      # Alertmanager
```

Grafana 는 프로비저닝 디렉터리를 주기적으로 다시 읽으므로 별도 호출이 필요 없다.

### 7.3 웹훅 URL 관리

| URL | 보관 위치 | 이유 |
|---|---|---|
| Alertmanager 용 3개 (critical, warning, watchdog) | SSM SecureString | 컨테이너 기동 시 파일로 주입 |
| GitHub Actions 용 1개 (deploy) | 저장소 시크릿 | AWS 자격증명 획득 전에 필요 |

**웹훅 URL 은 사실상 자격증명이다.** 이 URL 을 아는 사람은 누구나 해당 채널에 글을 쓸 수 있다. 설정 파일이나 워크플로에 평문으로 넣지 않는다.

## 8. 알람 피로 방지

FMEA 초안에서 알람 피로가 RPN 36으로 나왔던 항목이다. 알람이 많아지면 진짜 알람을 무시하게 된다.

| 규칙 | 내용 |
|---|---|
| 심각도는 둘만 | Critical과 Warning. 중간 등급을 만들지 않는다 |
| 채널 분리 | 심각도별로 다른 채널 |
| 멘션은 Critical만 | Warning에 역할 태그를 붙이지 않는다 |
| 지속 시간 조건 필수 | 순간 스파이크로 발동하지 않게 한다 |
| 발생 빈도 검토 | 주 1회 알람 발생 통계를 보고 오탐이 잦으면 임계를 조정한다 |
| 무시하기로 한 알람은 삭제 | 끄지 않고 방치하면 다른 알람까지 무시하게 된다 |

마지막 규칙이 실질적이다. **"이건 원래 그래"라는 알람이 하나 생기면 채널 전체의 신뢰도가 떨어진다.**

### 8.1 Alertmanager로 구현하는 부분

위 규칙 중 셋은 Alertmanager 기능으로 처리한다. 사람의 규율에 맡기지 않아도 되는 부분이다.

| 기능 | 규칙 | 동작 |
|---|---|---|
| 그룹화 | 소음 감소 | 같은 원인의 알람 여러 개를 한 메시지로 묶음 |
| 억제 (inhibition) | 파생 알람 숨김 | 상위 알람이 켜져 있으면 하위 알람을 보내지 않음 |
| 침묵 (silence) | 점검 중 중지 | 지정 기간 동안 특정 알람을 일시 정지 |
| 재발송 간격 | 반복 조절 | 해소될 때까지 반복하되 주기를 심각도별로 조절 |

**억제가 가장 효과가 크다.** 인스턴스 하나가 죽으면 readiness 실패, 커넥션 풀 이상, 배치 미실행이 동시에 발생하는데 원인은 하나다. 파생 알람을 그대로 보내면 채널에 네 건이 쏟아진다.

```yaml
inhibit_rules:
  # 인스턴스가 죽으면 그 인스턴스의 Warning 알람은 보내지 않는다
  - source_matchers: [alertname="InstanceDown"]
    target_matchers: [severity="warning"]
    equal: [instance]

  # DB 장애 중에는 앱의 커넥션 관련 Warning 을 숨긴다
  - source_matchers: [alertname="DatabaseUnavailable"]
    target_matchers: [alertname=~"HikariPool.*|TomcatThreads.*"]

  # 배포 중에는 재기동으로 인한 Warning 을 숨긴다
  - source_matchers: [alertname="DeploymentInProgress"]
    target_matchers: [severity="warning"]
```

세 번째 규칙은 배포 절차에서 `DeploymentInProgress` 알람을 의도적으로 발생시키고 배포가 끝나면 해소하는 방식으로 동작한다. 배포 중 재기동으로 생기는 일시적 경보가 채널을 채우는 것을 막는다.

**침묵은 계획된 작업에 쓴다.** 절감 스크립트로 리소스를 내리거나 복원 리허설을 할 때, 관련 알람을 미리 침묵시키지 않으면 채널이 알람으로 찬다.

```bash
amtool silence add alertname=InstanceDown   --duration=2h --comment="복원 리허설"
```

### 8.2 CloudWatch 쪽 한계

CloudWatch 알람에는 억제 기능이 없다. 복합 알람으로 유사한 효과를 낼 수 있으나 개당 0.50 USD라 3.3절에서 금지했다.

CloudWatch에 남긴 6개는 서로 파생 관계가 약해 억제가 필요 없다. 다만 **모니터링 인스턴스 소실과 Route 53 헬스체크 실패가 동시에 뜰 수는 있다.** 모니터링이 죽어도 서비스는 살아 있으므로 실제로는 겹치지 않지만, 인프라 전체 장애 시에는 두 건이 함께 온다. 이 정도는 감수한다.

## 9. 검증

알람 자체가 동작하는지 확인해야 한다. 발동하지 않는 알람은 없는 것과 같다.

| 항목 | 방법 |
|---|---|
| Slack 연동 (Chatbot 경로) | CloudWatch 알람 강제 발동 |
| Slack 연동 (Alertmanager 경로) | `amtool alert add` 로 테스트 알람 발송 |
| 억제 규칙 | 상위 알람 발동 후 하위 알람이 묻히는지 확인 |
| 침묵 | `amtool silence add` 후 알람이 오지 않는지 확인 |
| 해소 통지 | Critical 알람 해소 시 복구 메시지가 오는가, Warning 은 오지 않는가 |
| Watchdog | 5분 주기로 도착하는가. Alertmanager 중지 시 끊기는가 |
| 배포 알림 | GitHub Actions 에서 `#alerts-deploy` 로 도착하는가 |
| 설정 재적용 | Git 변경 후 reload 로 반영되는가, 인스턴스 재생성 후에도 유지되는가 |
| 이메일 대체 경로 | SNS에서 직접 발행 |
| 채널 분리 | Critical과 Warning을 각각 발동 |
| 정상 호스트 수 0 | 인스턴스 종료 |
| RDS 페일오버 | reboot with failover. **Chatbot의 이벤트 메시지 렌더링 형식도 함께 확인** |
| 캐시 연결 실패 | 보안 그룹 차단 |
| 컨테이너 재기동 반복 | 메모리 제한으로 OOM 유발 |
| 정합성 검증 실패 | 테스트 데이터에 의도적 오차 삽입 |
| 알람 메시지 정보 | 오차 건수, 최대 오차, 최근 변경 시각과 주체가 포함되는가 |

**정합성 검증 실패 알람은 반드시 검증한다.** 이 알람은 실제 사고가 나기 전까지 한 번도 발동하지 않으므로, 동작 여부를 확인할 기회가 없다. 롤백 스크립트를 매 배포 후 연습하는 것과 같은 이유다. 평소에 실행되지 않는 코드는 사고 시점에 처음 돌아간다.
