## 1. 문서 목적과 범위

본 문서는 장애 대응 설계의 1단계 산출물이다. "무엇이 깨질 수 있는가"를 나열하기에 앞서, **어디까지 견딜 것인지**와 **무엇을 포기할 것인지**를 먼저 정한다.

목표를 정하지 않고 이중화부터 시작하면, 비용은 계속 늘어나는데 "이만하면 됐다"고 판단할 기준이 없다. 목표가 있으면 각 이중화 투자가 어떤 목표를 지키기 위한 것인지 설명할 수 있고, 검증도 목표 대비 실측으로 할 수 있다.

범위는 단일 리전(ap-northeast-2) 내의 가용영역 장애까지다. 리전 전체 소실은 다루지 않는다. 소규모 예산으로 다중 리전을 구성하는 것이 불가능하며, 단기 검증 기간에 확인할 방법도 없다.

## 2. 설계의 전제: 어떤 장애가 더 위험한가

백엔드 시스템의 장애는 크게 두 부류다.

| 부류 | 예 | 발견 시점 | 대응 방향 |
|---|---|---|---|
| 가용성 장애 | 인스턴스 소실, DB 페일오버, 배포 실패 | 즉시 | 이중화와 자동 전환 |
| 정합성 장애 | 중복 처리, 부분 실패, 갱신 손실 | 며칠 뒤 다른 증상으로 | 멱등성과 검증 장치 |

이중화는 가용성 장애만 막는다. 정합성 장애는 오히려 이중화 때문에 생긴다. 인스턴스를 2대로 늘리는 순간 배치가 두 번 돌고, 무중단 배포를 하는 순간 두 버전이 같은 데이터를 건드린다.

**따라서 이 설계의 우선순위는 "멈추지 않게 하는 것"이 아니라 "멈췄다 살아난 뒤 데이터가 맞는 것"이다.** 이 판단이 이후 모든 결정의 기준이 된다.

프로젝트별로 이 전제가 얼마나 강하게 적용되는지는 도메인의 성격에 달렸다. 아래 조건에 하나라도 해당하면 정합성 장애를 최우선으로 다뤄야 한다.

- 수량이나 잔액을 증감하는 연산이 있다 (재고, 포인트, 크레딧, 좌석, 한도)
- 배치가 상태를 전이시키면서 자원을 되돌린다 (만료 처리, 취소, 정산)
- 외부 시스템에 부수 효과를 남긴다 (결제, 발송, 통지)

세 조건 모두 해당하지 않는 순수 조회성 서비스라면, 가용성 중심으로 단순화해도 된다.

## 3. 아키텍처 토폴로지

```
Internet
   |
   v
  Route 53 (호스팅 영역, alias 레코드)
   |
   v
  ALB (2 AZ, HTTPS 443, ACM 인증서)
   |
   +--> app-1  (t3.small, Docker + Compose + systemd)
   |    (현재 1대. ASG 구성상 최대 2, 2 AZ 서브넷 등록. AZ 는 ASG 가 고른다)
            |
            +--> RDS MySQL 8.4  (db.t4g.micro, Multi-AZ)
            |         primary  --동기복제->  standby  (읽기 불가. AZ 는 페일오버로 뒤바뀐다)
            +--> ElastiCache Valkey 9.0 (cache.t4g.micro, 2노드 Multi-AZ, primary AZ-a)
            +--> SSM Parameter Store (서명 키, DB 자격증명)

  batch (t4g.micro, AZ-a 고정, ASG 밖 단독)
     스케줄러 전용. ALB 에 붙지 않고 인바운드가 없다
            |
            +--> RDS MySQL 8.4

  monitoring (t4g.small, AZ-a 고정, ASG 밖)
     Prometheus 3.13 / Grafana 12.4 / Loki 3.7 / Alertmanager / OTel Collector
            |
            +--> app, RDS, ElastiCache 스크랩

  load (t3a.small, AZ-a, 부하 시험 시간에만 기동)
     k6
```

NAT Gateway는 사용하지 않는다. 앱 인스턴스는 퍼블릭 서브넷에 두되, 인바운드는 ALB 보안 그룹에서 오는 트래픽만 허용하고 운영 접근은 SSM Session Manager로 처리한다. 22번 포트는 열지 않는다.

### 3.1 남아 있는 단일 장애점

남아 있는 단일 장애점을 숨기지 않고 명시한다.

| 단일 장애점 | 소실 시 영향 | 수용 근거 |
|---|---|---|
| 앱 인스턴스 | 서비스 전면 중단 | 현재 1대 운영. desired 2로 언제든 해소 가능 (4.3절) |
| 모니터링 인스턴스 | 감지 수단 상실 | 핵심 알람은 CloudWatch에 이중 설정. Route 53 헬스체크는 독립 동작 |
| ALB | 서비스 전면 중단 | AZ 단위 이상은 AWS가 자동 처리. 설정, 인증서, 삭제, 스케일링은 우리 대응. 리전 단위 ELB 장애만 범위 제외 |
| Route 53 | 도메인 조회 불가 | 관리형. 인증서 만료와 검증 레코드는 별도 감시 |
| 리전 | 서비스 전면 중단 | 범위 밖으로 명시적 제외 |

**캐시는 이 표에서 빠졌다.** 프라이머리 AZ-a, 복제본 AZ-c 로 이중화해 노드 하나를 잃어도 자동 페일오버가 받는다(`INF-37`).
다만 등급은 Degradable 그대로다. 이중화는 노드 한 대의 소실을 덮을 뿐이고 캐시가 통째로 비는 경우까지 없애지 않아, 강등 경로는 그대로 둔다.

## 4. 가용성 목표

### 4.1 RTO와 RPO

목표치는 **현재 구성(앱 1대)** 기준이다. 이중화 전환 시의 값은 4.3절에 별도로 둔다.

| 장애 시나리오 | RTO 목표 | RPO 목표 | 보장 메커니즘 |
|---|---|---|---|
| 앱 컨테이너 급사 | 10초 | 0 | Docker restart policy. 주된 복구 경로 |
| 앱 인스턴스 소실 | 5분 | 0 | ASG 교체. 부팅 + Docker + JVM |
| AZ 1개 소실 | 5분 | 0 | ASG가 다른 AZ 서브넷에 재기동 |
| DB 인스턴스 장애 | 2분 | 0 | 동기 복제이므로 커밋 손실 없음 |
| 캐시 노드 소실 | (미정) | 복제 지연분 | 자동 페일오버로 복제본 승격. 복제가 비동기다 |
| 캐시 전량 소실 | 30초 | 캐시 전량 | 원본 조회 경로로 강등 |
| 논리적 데이터 사고 | 60분 | 5분 | RDS PITR |
| 배포 실패 (구 인스턴스 유지 중) | 무영향 | 0 | 전환 전이므로 프로덕션 무관 |
| 배포 실패 (구 인스턴스 종료 후) | 8분 | 0 | 증설부터 재수행 |
| 모니터링 소실 | 30분 | 지표 공백 | CloudWatch 이중 알람 |

RPO가 0이 아닌 유일한 구간은 PITR이다. 나머지는 동기 복제 또는 무상태 구조라 손실이 없다.

### 4.2 목표를 정한 근거

**앱 컨테이너 10초.** Docker healthcheck 실패 후 재기동한다. 인스턴스가 1대인 현재 구성에서 이것이 주된 복구 경로다. 컨테이너 수준에서 회복되지 않으면 인스턴스 교체까지 가야 한다.

**앱 인스턴스 5분.** ASG가 desired 미달을 감지하고 새 인스턴스를 기동한다. EC2 부팅, Docker 설치, 이미지 pull, JVM 기동을 합쳐 4~6분이다. 인스턴스가 1대이므로 이 구간은 그대로 다운타임이 된다. 커스텀 AMI를 도입하면 2~3분으로 줄어든다.

**AZ 소실 5분.** 앱이 한 AZ에만 있으므로 그 AZ가 죽으면 인스턴스 소실과 같다. ASG가 다른 AZ 서브넷에 재기동하므로 복구 경로는 같다.

**DB 2분.** RDS Multi-AZ 페일오버는 통상 60초에서 120초가 걸린다. 이 값은 AWS가 제어하므로 줄일 수 없다. 대신 이 2분 동안 애플리케이션이 어떻게 행동하는지는 우리가 정할 수 있으며, 커넥션 풀 재연결과 재시도 정책에서 다룬다.

**2분은 통상 구간의 상한이라 여유가 없다.** 대량 트랜잭션이 열려 있거나 복구 과정이 길어지면 이 시간은 늘어난다. 배치가 대량 쓰기를 도는 중에 페일오버가 나면 초과가 정상 동작이다. 목표를 넘겼을 때는 사건 시점에 열려 있던 트랜잭션부터 확인한다.

**PITR 60분 / RPO 5분.** RDS는 트랜잭션 로그를 5분마다 S3에 업로드한다. **RPO 5분은 이 구조에서 나오는 값이지 임의로 정한 목표치가 아니다.** 반면 **RTO 60분은 아직 근거가 없고 실측한 적도 없다.** 복원은 새 인스턴스를 만드는 작업이라 데이터 크기와 마지막 스냅샷 이후 쌓인 로그 양에 따라 달라진다. 첫 복원 리허설에서 측정해 갱신한다. 상세는 백업과 복원 설계 문서를 참조한다.

**배포 실패 무영향 또는 8분.** 신규 인스턴스가 healthy가 될 때까지 구 인스턴스가 서비스를 유지하므로, 그 단계에서 실패하면 프로덕션은 영향받지 않는다. 구 인스턴스를 종료한 뒤 회귀가 발견되면 이전 SHA로 증설부터 다시 하므로 8분이 든다.

### 4.3 이중화 전환

`desired_capacity`를 1에서 2로 올리는 것이 전부다. 인프라 구성 변경은 필요 없다.

| 항목 | 1대 (현재) | 2대 (전환 후) |
|---|---|---|
| 앱 인스턴스 소실 RTO | 5분 | 30초 |
| AZ 1개 소실 RTO | 5분 | 30초 |
| 배포 실패 RTO (종료 후) | 8분 | 5분 |
| 단일 장애점 | 앱 인스턴스 포함 | 앱 제외 |
| DB 커넥션 총량 | 약 23 (배포 중 33) | 약 33 (배포 중 45) |
| 월 비용 | 약 140 USD | 약 162 USD |

전환 전 확인할 것은 다음과 같다.

| 항목 | 확인 |
|---|---|
| RDS `max_connections` | 배포 중 45를 수용하는가. 예측값 60이라 여유가 25%뿐이다 |
| 배치 재실행 안전성 | 조건부 UPDATE가 구현되어 동작하는가 |
| 조건부 UPDATE | 모든 누적 연산에 적용되었는가 |
| 배포 절차 | 인스턴스 수를 하드코딩한 곳이 없는가 |

앞의 셋은 1대일 때 검증할 수 없다. **전환과 동시에 확인하면 늦으므로, 일시 증설로 미리 확인한다.**

## 5. 구성요소 의존성 등급

등급은 세 가지로 나눈다.

| 등급 | 정의 | 처리 원칙 |
|---|---|---|
| Critical | 소실 시 서비스가 멈추거나 데이터가 깨진다 | 이중화 또는 복구 보장 필수 |
| Degradable | 소실 시 느려지지만 기능은 동작한다 | 강등 경로를 코드로 명시 |
| Deferrable | 소실 시 처리가 지연되지만 나중에 따라잡을 수 있다 | 지연 허용, 중복은 불가 |

| 구성요소 | 등급 | 소실 시 영향 | 대응 |
|---|---|---|---|
| RDBMS | Critical | 전면 중단, 진실의 원천 소실 | Multi-AZ + PITR |
| 앱 인스턴스 | Critical | 이중화로 흡수 | ALB + 2 AZ |
| ALB | Critical | 전면 중단 | 관리형 이중화에 의존 |
| 캐시 (조회 가속) | Degradable | 응답 지연, 기능 정상 | 노드 하나면 자동 페일오버, 전량 소실이면 원본 직조회로 강등 |
| 캐시 (세션 저장) | Critical | 전 사용자 로그아웃 | stateless 인증으로 회피하거나 노드 이중화 |
| 배치, 스케줄러 | Deferrable | 처리 지연 | 지연 허용, 중복은 불가 |
| 모니터링 | Deferrable | 감지 지연 | CloudWatch 이중 알람 |

**같은 Redis라도 용도에 따라 등급이 다르다는 점이 핵심이다.** 캐시 하나를 세 용도로 겸용하면 가장 높은 등급을 따라가므로, 용도를 분리하는 것만으로 이중화 비용을 줄일 수 있다.

권장 분리 전략은 다음과 같다.

| 용도 | 권장 위치 | 이유 |
|---|---|---|
| 조회 캐시 | Redis | 소실돼도 원본에서 다시 만든다 |
| 세션 | 없음 (stateless 인증) | 상태를 없애면 등급 자체가 사라진다 |
| 토큰 무효화 목록 | RDBMS | 소실 시 취소된 토큰이 되살아난다 |

## 6. 인증 방식과 파급

### 6.1 결정

stateless 인증(JWT)을 기본으로 한다. access token은 10분 내외, refresh token은 회전과 재사용 탐지를 적용한다.

### 6.2 얻는 것

- 앱 인스턴스가 상태를 갖지 않으므로 교체, 증설, 축소가 자유롭다
- ALB 스티키 세션이 불필요하다
- 인스턴스 1대가 죽어도 사용자가 로그아웃되지 않는다
- 캐시를 Critical에서 뺄 수 있다

### 6.3 치르는 비용

| 문제 | 내용 | 완화 |
|---|---|---|
| 즉시 차단 불가 | 계정 차단, 탈퇴, 권한 강등이 토큰 만료까지 반영되지 않음 | access TTL 10분 + 무효화 기준 시각 컬럼 |
| refresh는 결국 상태 | 회전과 재사용 탐지를 하려면 서버가 발급분을 기억해야 함 | 토큰 테이블(해시 저장) |
| 서명 키가 새 단일 장애점 | 키 소실 시 전 사용자 로그아웃, 교체 시 무중단 회전 필요 | `kid` 헤더로 구 키와 신 키 동시 허용, SSM Parameter Store 보관 |
| 시계 오차 | `exp`, `nbf` 검증이 인스턴스 시각에 의존 | Amazon Time Sync Service |

### 6.4 무효화 기준 시각 패턴

즉시 차단 불가를 완화하는 표준 방법이다. 주체 테이블에 무효화 기준 시각을 두고, 토큰의 발급 시각과 비교한다.

```java
// 차단, 탈퇴, 권한 변경, 비밀번호 변경 시 현재 시각으로 갱신한다.
public boolean isTokenStillValid(Claims claims, Principal principal) {
    Instant issuedAt = claims.getIssuedAt().toInstant();
    Instant invalidatedAt = principal.getTokenInvalidatedAt();   // null 가능
    return invalidatedAt == null || issuedAt.isAfter(invalidatedAt);
}
```

매 요청마다 이 검사를 하면 DB 조회가 생겨 stateless 이점이 줄어든다. 즉시성이 필요한 경로(관리자 API, 금액이 오가는 API)에만 적용하고, 나머지는 access TTL로 상한을 두는 것이 절충안이다.

### 6.5 스키마 변경 예정 사항

| 변경 | 목적 |
|---|---|
| 토큰 테이블 신규 (subject_id, token_hash, jti, expires_at, rotated_from_jti, revoked_at) | 회전과 재사용 탐지 |
| 주체 테이블에 `token_invalidated_at` 컬럼 추가 | 일괄 무효화 기준점 |
| 관리자 테이블에 `token_invalidated_at` 컬럼 추가 | 권한 강등 즉시 반영 |

토큰은 원문이 아니라 해시를 저장한다. DB가 유출되면 저장된 토큰으로 바로 로그인이 되기 때문이다.

## 7. 배포 전략

### 7.1 방식

인스턴스 단위 롤링을 채택한다. 상세 설계는 무중단 배포 문서를 참조하며, 검토했으나 채택하지 않은 대안은 같은 문서 부록 A에 정리했다.

| 항목 | 값 |
|---|---|
| 전환 방식 | 신규를 먼저 띄우고 검증한 뒤 구 인스턴스를 종료 |
| 배포 중 용량 | 100% |
| 배포 소요 | 6~8분 |
| 롤백 소요 | 6~8분 |
| 혼재 구간 | 약 1분 |
| 추가 인스턴스 | 배포 중 1대 |

**이 표는 무중단 배포 문서 1절과 같은 값이다.** 한때 "인스턴스를 하나씩 빼고 교체"(용량 50%, 3~4분)로 적혀 있었으나 그것은 채택하지 않은 변형이다. 실제 절차는 `desired +1` 로 신규를 먼저 띄우므로 용량이 줄지 않고, 그만큼 시간이 더 든다(`INF-29`).

**채택 근거는 이 인프라가 운영 환경에 올라가기 전의 검증 환경이라는 점이다.** 배포 실패가 실사용자에게 미치는 영향이 없으므로 실패 시 영향 범위를 줄이는 방식의 가치가 낮은 반면, 배포 시간은 검증 반복 횟수를 직접 결정한다. 부수적으로 구성요소가 적을수록 그 자체가 장애 원인이 될 여지도 줄어든다.

실사용자 트래픽을 받게 되거나 부하 시험 중 배포가 필요해지면 재검토한다. 재검토 조건은 무중단 배포 문서 부록 A.6에 정리했다.

### 7.2 종료 타임아웃 계층

안쪽에서 바깥쪽으로 갈수록 길어야 한다. 하나라도 역전되면 처리 중 요청이 잘린다.

| 계층 | 설정 | 값 |
|---|---|---|
| ALB 대상 그룹 | deregistration delay | 30초 |
| Spring Boot | `spring.lifecycle.timeout-per-shutdown-phase` | 30초 |
| Docker Compose | `stop_grace_period` | 45초 |
| systemd | `TimeoutStopSec` | 60초 |

헬스체크 경로는 `/actuator/health/readiness`, 간격 10초, 정상 임계값 2, 비정상 임계값 2로 둔다.

**readiness 그룹에는 인스턴스 로컬 상태만 포함한다.** DB, 캐시, 외부 API 같은 공유 의존성은 제외한다. 포함하면 해당 의존성이 죽었을 때 모든 인스턴스가 동시에 unhealthy가 되어 대상 그룹이 비고, 상황이 나아지는 대신 악화된다. 자세한 근거는 앱과 DB 장애 대응 구조 문서 4.1절을 참조한다.

### 7.3 배포 절차

```
1. GitHub Actions: 이미지 빌드, GHCR push (태그 = 커밋 SHA)
2. 인스턴스 1: deregister-targets
3. 인스턴스 1: draining 완료 대기 (최대 30초)
4. 인스턴스 1: compose pull + up -d
5. 인스턴스 1: 로컬 readiness 폴링 (최대 90초)
6. 인스턴스 1: register-targets, healthy 확인
7. 실패하면 여기서 중단. 인스턴스 2는 건드리지 않는다
8. 성공하면 인스턴스 2에 대해 2~6 반복
```

7번이 안전장치다. 1번 교체가 실패했는데 2번까지 진행하면 서비스가 통째로 내려간다. 중단 시점에는 구버전 1대가 트래픽을 받고 있으므로 서비스는 유지된다.

### 7.4 혼재 구간이 강제하는 규칙

롤링은 구버전과 신버전이 **약 1분간** 공존한다. 신규가 대상 그룹에 등록된 시점부터 구 인스턴스가 드레이닝을 마칠 때까지다.

**배치는 여기에 해당하지 않는다.** 배치는 전용 인스턴스에서 돌고 롤링 대상이 아니라 중지 후 교체하므로 혼재 구간이 없다(`INF-05`). 다만 다음 두 규칙은 여전히 선택이 아니다.

**1. 스키마는 확장 후 축소(expand and contract)만 허용한다.**

```sql
-- 1차 배포: 추가만 한다. 구버전과 신버전이 모두 동작한다.
ALTER TABLE account ADD COLUMN token_invalidated_at DATETIME(3) NULL;

-- 신버전 안정화 후 별도 배포에서 구 컬럼을 정리한다.
```

한 배포 안에 컬럼 삭제나 이름 변경을 넣으면 롤백이 불가능해진다. CI에서 파괴적 DDL을 감지해 차단하는 규칙을 두면 사람이 실수해도 막힌다.

**2. 상태 전이는 조건부 UPDATE로 멱등하게 만든다.** 배치는 배포와 인스턴스 교체로 중간에 끊기고 다음 주기에 다시 도므로 재실행이 안전해야 한다. 자세한 내용은 배치 설계 문서를 참조한다.

### 7.5 롤백 트리거

| 신호 | 조건 | 동작 |
|---|---|---|
| readiness 미통과 | 90초 초과 | 즉시 중단, 해당 인스턴스만 구버전 복귀 |
| 5xx 비율 | 배포 전 대비 2배, 3분 지속 | 자동 롤백 |
| p99 응답시간 | 배포 전 대비 3배 | 경보 후 수동 판단 |
| 핵심 비즈니스 지표 | 절대값 하락 (예: 주요 트랜잭션 성공률) | 즉시 수동 롤백 |

롤백 스크립트는 평소에 실행되지 않는 코드라 정작 필요한 순간에 처음 돌아간다. **매 배포 후 롤백을 한 번씩 연습 항목으로 수행한다.**

| INF-24 | 모니터링 인스턴스는 ASG에 넣지 않음 | desired 0은 EBS까지 삭제해 관측 데이터 소실 | 아니오 |
| INF-35 | 읽기 분리가 필요해지면 Multi-AZ 를 유지한 채 읽기 복제본을 추가한다 | 대기 인스턴스를 복제본으로 바꾸면 자동 페일오버를 잃는다. 복제본에는 자동 승격이 없다 | 예(도입하지 않는 것이 기본) |
| INF-36 | 캐시를 단일 노드라도 replication group 으로 생성 | 복제본 추가는 replication group 에만 가능. 나중에 바꾸려면 이관이 필요하고 지금 정하면 비용 차이가 0 | 아니오 |
| INF-38 | Grafana 만 DuckDNS + Caddy 로 HTTPS 노출하고, 앱 진입점은 ALB DNS 이름의 평문 HTTP 로 둔다 | 프리 티어 계정은 Route 53 도메인 등록을 쓸 수 없다. 팀원이 지표를 브라우저로 봐야 해서 Grafana 만 먼저 열었다. 앱은 도메인을 쓰지 않기로 했다 | 예(도메인을 사면 `INF-17` 로 복귀) |
| INF-37 | 캐시를 2노드 Multi-AZ 로 운영 (`INF-04` 대체) | 팀이 캐시 소실 구간을 감수하지 않기로 했다. `INF-36` 덕에 이관도 재생성도 없이 플래그 변경으로 끝났고 월 11.68 USD 가 는다. 등급은 Degradable 그대로 두어 강등 경로를 유지한다 | 예(노드 수를 1로 되돌리면 된다) |

INF-06만 되돌릴 수 없는 항목이다. 나머지는 구성 변경이지만 이것은 안전 요건이라 협상 대상이 아니다.

## 11. 진행 상태와 다음 단계

### 11.1 완료

| 산출물 | 문서 |
|---|---|
| 가용성 목표, 의존성 등급, 토폴로지, 의사결정 기록 | 본 문서 |
| 기술 스택과 버전 확정, 비용 산정 | 기술 스택 확정 문서 |
| 요청 경로 장애 대응 (앱, DB, ALB) | 앱과 DB 장애 대응 구조 |
| 무중단 배포와 롤백 | 무중단 배포 문서 |
| 배치 재실행 안전성 | 배치 설계 문서 |
| 백업, 복원, 정합성 감지 | 백업과 복원 설계 문서 |
| 오토스케일링 (골격만) | 오토스케일링 설계 문서 |
| 알람 경로, 심각도, 알림 채널 | 알람과 알림 설계 문서 |
| 전체 조감 | 시스템 디자인 종합 |

전체 장애 유형을 망라하는 FMEA는 수행하지 않기로 했다. 초안을 작성해 보니 상위 위험이 요청 경로와 배치에 집중되어 있어, 그 둘의 구조를 먼저 확정하는 편이 실효가 컸다. 필요해지면 위 문서들을 입력으로 다시 수행한다.

### 11.2 다음 단계

문서 설계는 일단락되었고, **실행 가능한 산출물이 없다.** 지금까지 설계한 안전장치 대부분이 아직 존재하지 않는 자동화에 의존하고 있다.

### 11.3 착수 전 확인이 필요한 값
