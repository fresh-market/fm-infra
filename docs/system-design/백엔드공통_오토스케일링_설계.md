## 1. 문서 목적과 범위

과다 트래픽 시 앱 인스턴스를 자동으로 늘리고, 트래픽이 줄면 되돌리는 구조를 설계한다.

**2026-08-29 부터 앱 ASG 에만 적용한다.** 도착률 기준 target tracking 이고 min 1 / max 3 이다.

**선착순 전용 ASG 에는 걸지 않는다** (`INF-40`). 확장 판정에 최소 3분이 걸리는데 선착순 쇄도는
그보다 짧게 끝나 판정 전에 재고가 소진된다. 전용 ASG 의 대수는 `coupon-event.sh` 가 이벤트 전에 정한다.

다만 **임계값이 실측이 아니다.** 대상당 분당 6000 요청은 시작값이고, 한 대가 견디는 도착률을
부하 시험에서 잰 뒤 역산해야 한다. 그 전까지는 정책이 있다는 것과 옳은 지점에서 도는 것이 다르다.

| 구분 | 지금 확정 | 실측 후 확정 |
|---|---|---|
| 정책 종류와 선택 근거 | 확정 | - |
| 스케일 아웃 안전 요건 | 확정 | - |
| 스케일 인 안전장치 | 확정 | - |
| 인스턴스 상한 도출 방법 | 확정 | 실제 상한값 |
| 임계값과 목표값 | - | **부하 시험 필요** |
| 쿨다운과 워밍업 | 산출식 확정 | 기동 시간 실측 |

임계값을 감으로 정하면 스케일링이 해가 된다. 너무 낮으면 불필요하게 늘어 비용만 쓰고, 너무 높으면 이미 느려진 뒤에 늘어 의미가 없다. **비워 두는 것이 잘못된 값을 넣는 것보다 낫다.**

## 2. 선행 조건 점검

스케일 아웃이 안전하려면 갖춰야 할 것들이다. 대부분 다른 결정의 부수 효과로 이미 확보되어 있다.

| 요건 | 상태 | 근거 |
|---|---|---|
| 앱 무상태성 | 확보 | JWT stateless (INF-02) |
| 세션 공유 불필요 | 확보 | 상태 자체가 없음 |
| 스티키 세션 불필요 | 확보 | 동일 |
| 버전 진실 외부화 | 확보 | SSM `current-sha` (INF-25) |
| DB 엔드포인트 외부화 | 확보 | SSM `db-endpoint` (INF-26) |
| 2 AZ 서브넷 등록 | 확보 | ASG가 두 서브넷 참조 |
| 배포 절차의 인스턴스 수 무관성 | 확보 | 목록 기반 처리 |
| 배치 실행 위치 | 전용 인스턴스 1대로 분리 | 배치 설계 문서 |
| 조건부 UPDATE | 설계 완료, 구현 필요 | 동일 |
| **스케일 인 안전장치** | **미확보** | 본 문서 5절 |

마지막 항목만 새로 필요하다. 나머지는 이중화를 전제로 설계해 온 결과다.

**스케일 인 안전장치가 없는 채로 정책을 켰다.** 축소는 lifecycle hook 의 유예와 ALB deregistration delay 에
기대고 있고, 처리 중이던 요청이 끊기는지는 확인하지 않았다. 부하 시험에서 축소를 관찰해야 한다.

## 3. 정책 종류와 선택

### 3.1 후보

| 정책 | 동작 | 이 구성에 적합한가 |
|---|---|---|
| 대상 추적 (Target Tracking) | 지표를 목표값에 맞춰 자동 조절 | **적합** |
| 단계 조정 (Step Scaling) | 임계 구간별로 증감량 지정 | 과함 |
| 단순 조정 (Simple Scaling) | 임계 초과 시 고정량 증감 | 구식 |
| 예약 조정 (Scheduled) | 시각 기반 | 트래픽 패턴이 없어 부적합 |

**대상 추적을 권한다.** 임계값 하나만 정하면 되고, 증감량과 쿨다운을 AWS가 조절한다. 검증 환경에서 정책 자체를 튜닝하는 데 시간을 쓸 이유가 없다.

### 3.2 추적 지표 선택

여기가 이 구성의 핵심 판단이다.

| 지표 | 문제 |
|---|---|
| `ASGAverageCPUUtilization` | **버스트 인스턴스에서 왜곡됨** |
| `ALBRequestCountPerTarget` | 요청당 비용이 균일하다는 가정 필요 |
| `TargetResponseTime` 기반 커스텀 | 사용자 체감에 가장 가까움 |

**CPU 사용률을 쓰지 않는 이유**는 t3.small이 버스트 인스턴스이기 때문이다.

```
크레딧 충분: CPU 40%, 응답 빠름          -> 스케일 아웃 안 함 (정상)
크레딧 소진: CPU 40%(제한된 상태), 응답 느림 -> 여전히 스케일 아웃 안 함 (문제)
```

크레딧이 소진되면 CPU가 기준선 이상 올라가지 못하므로, 실제로는 포화 상태인데 지표상으로는 여유가 있어 보인다. **CPU 기반 정책은 크레딧 소진을 구조적으로 감지하지 못한다.**

권장 조합은 다음과 같다.

| 순위 | 지표 | 역할 |
|---|---|---|
| 1 | `ALBRequestCountPerTarget` | 주 정책. 인스턴스당 요청 수 |
| 2 | CPU 크레딧 잔량 알람 | 보조. 소진 임박 시 경보. 알람과 알림 설계 문서 6절 |

CPU 크레딧을 스케일링 트리거로 쓰지 않고 알람으로만 두는 이유는, 크레딧 소진이 트래픽 증가가 아니라 비효율적인 코드 때문일 수도 있기 때문이다. 그 경우 인스턴스를 늘려도 근본 원인이 남는다.

## 4. 인스턴스 상한: DB에서 역산한다

**앱을 늘려도 DB가 먼저 막힌다.** 상한은 앱의 처리 능력이 아니라 `max_connections`에서 결정된다.

**앱 커넥션만 세면 안 된다.** 배치 인스턴스가 같은 jar를 `prod,batch` 프로필로 띄워 풀을 똑같이 10개 갖는다. 아래 표는 배치와 관리 커넥션을 포함한 총량이다.

| 앱 인스턴스 | 앱 | 배치 | 관리 | 평상시 합계 | 배포 중 |
|---|---:|---:|---:|---:|---:|
| **1 (하한)** | 10 | 10 | 3 | 23 | 33 |
| 2 | 20 | 10 | 3 | 33 | **45** |
| **3 (상한)** | 30 | 10 | 3 | **43** | 53 |
| 4 | 40 | 10 | 3 | 53 | 65 |
| 8 | 80 | 10 | 3 | 93 | 105 |

산출식은 다음과 같다.

```
최대 인스턴스 수 = (max_connections x 안전계수 - 예약분) / 인스턴스당 풀 크기 - 1

안전계수: 0.8 (관리 커넥션과 여유)
예약분: 배치 인스턴스 풀 10, 모니터링 익스포터, 운영자 접속
-1: 배포 중 일시 증설분
```

**예약분에 배치 10개를 반드시 넣는다.** 빠뜨리면 상한이 한 대 이상 부풀려진다.

`max_connections` 예측값 60(앱과 DB 장애 대응 구조 4.5절)을 대입하면 이렇다.

```
(60 x 0.8 - 13) / 10 - 1 = (48 - 13) / 10 - 1 = 2.5  ->  2대
```

**실제로는 3대로 두었다.** 차이는 마지막 `-1` 항 하나다. 그 항은 배포 중 신규 한 대가
설 자리를 남겨 두는 몫인데, 이번에 그것을 포기했다. `max_size` 3 이 확장 상한과 배포 여유를
겸하므로 **3대까지 올라간 동안에는 배포가 막힌다.** 스케일 인을 기다리면 풀린다.

```
-1 을 빼면:  (60 x 0.8 - 13) / 10 = 3.5  ->  3대
```

3대 평상시 43 은 안전선 48 안에 든다. 넘는 것은 그 상태에서 배포할 때의 53 뿐이고,
막아 둔 것이 정확히 그 경우다. 하드 리밋 60 은 어느 쪽도 넘지 않는다.

`OPS-1-02`(`max_connections`가 목표 인스턴스 수를 수용하는가)는 이 계산으로 해소됐다.
남은 것은 임계값이다. 대상당 분당 6000 요청은 실측이 아니라 시작값이고,
한 대가 견디는 도착률을 부하 시험에서 잰 뒤 역산해야 한다.

**60은 2026-08-23 에 실측한 값이다** (`SHOW VARIABLES LIKE 'max_connections'`).
공식 유도값과 같아 예측이 맞았다.

```sql
SHOW VARIABLES LIKE 'max_connections';
```

이 값이 상한을 감당하지 못하면 선택지는 셋이다.

| 방법 | 대가 |
|---|---|
| 인스턴스당 풀 크기 축소 | 인스턴스당 처리량 감소 |
| RDS 인스턴스 승급 | 비용 증가 |
| RDS Proxy 도입 | 시간당 요금 추가, 구성 복잡도 |

**앱만 늘리는 스케일 아웃은 DB 상한 안에서만 유효하다.** 그 이상 필요하면 DB 쪽을 먼저 손봐야 한다.

## 5. 스케일 인 안전장치

가장 위험한 지점이다. 스케일 인은 인스턴스를 종료하는데, **그 인스턴스가 배치를 실행 중일 수 있다.**

### 5.1 문제

**배치 인스턴스는 ASG 밖 단독이라 스케일 인 대상이 아니다.** 배치가 도는 중에 ASG 가 그 인스턴스를 고르는 일은 없다.

그래도 앱 인스턴스에서 처리 중이던 요청은 끊긴다. 그리고 배치 인스턴스도 배포로 중지되면 같은 형태가 된다.

```
t0    배치 인스턴스가 만료 처리 배치 실행 중
t30   배포로 중지
t60   배치가 중간에 끊김
t?    다음 주기에 처음부터 재실행
```

부분 처리 상태가 남고, 이미 처리된 건이 다시 처리된다. **재실행 안전성은 스케일 인과 무관하게 필요하다.**

### 5.2 대응 1: 수명주기 훅

ASG 수명주기 훅으로 종료를 지연시키고, 그동안 진행 중인 배치를 마치게 한다.

```
스케일 인 결정
  -> Terminating:Wait 상태로 진입 (훅)
  -> 인스턴스가 "배치 없음"을 확인하고 완료 신호
  -> 실제 종료
```

인스턴스에서 종료 신호를 받으면 다음을 수행한다.

1. 새 배치 실행을 중단한다 (플래그 설정)
2. 진행 중인 배치가 끝날 때까지 기다린다
3. 수명주기 훅에 완료 신호를 보낸다

```java
// 종료 신호를 받으면 새 배치를 받지 않는다
@Component
public class ShutdownGate {

    private final AtomicBoolean draining = new AtomicBoolean(false);
    private final AtomicInteger running = new AtomicInteger(0);

    public boolean tryEnter() {
        if (draining.get()) {
            return false;
        }
        running.incrementAndGet();
        return true;
    }

    public void exit() {
        running.decrementAndGet();
    }

    public void startDraining() {
        draining.set(true);
    }

    public boolean isIdle() {
        return running.get() == 0;
    }
}
```

```java
@Scheduled(cron = "0 */5 * * * *")
public void run() {
    if (!shutdownGate.tryEnter()) {
        return;   // 종료 중인 인스턴스는 새 배치를 시작하지 않는다
    }
    try {
        Optional<LockHandle> handle = distributedLock.tryAcquire(LOCK_NAME, LOCK_TTL);
        if (handle.isEmpty()) {
            return;
        }
        try {
            service.execute(handle.get().fenceToken());
        } finally {
            distributedLock.release(handle.get());
        }
    } finally {
        shutdownGate.exit();
    }
}
```

**훅에는 제한 시간이 있다.** 배치가 그보다 길면 강제 종료되므로, 배치 소요 시간을 알아야 훅 시간을 정할 수 있다.

### 5.3 대응 2: 배치를 스케일링 대상에서 분리

근본적인 해결은 배치를 웹 요청 처리와 분리하는 것이다.

| 구성 | 배치 실행 위치 | 스케일 인 영향 |
|---|---|---|
| 현재 (통합) | 모든 인스턴스 | 종료 시 배치 중단 |
| 분리 | 전용 인스턴스 1대 | 웹 인스턴스는 자유롭게 증감 |

분리하면 스케일링과 배치가 완전히 독립적이 된다. 대신 인스턴스가 하나 더 필요하고, 그 인스턴스가 단일 장애점이 된다.

**규모가 커지면 분리가 맞고, 지금 규모에서는 훅으로 충분하다.** 판단 기준은 배치 실행 시간이 스케일 인 빈도 대비 얼마나 긴가다.

### 5.4 대응 3: 조건부 UPDATE는 그대로

훅이 실패하거나 강제 종료되는 경우가 남는다. **배치 설계 문서 4장의 조건부 UPDATE 방어는 여기서도 최종 보루다.**

중간에 끊긴 배치가 재실행되어도 이미 처리된 건은 `affected rows 0`으로 걸러진다. 훅은 최적화이고, 정합성 보장은 조건부 UPDATE가 한다.

## 6. 쿨다운과 워밍업

### 6.1 산출식

```
인스턴스 워밍업 = 기동 시간 + readiness 통과 시간 + 여유
쿨다운 = 워밍업 + 지표 반영 지연
```

**인스턴스 기동 시간이 모든 값의 출발점이다.** 현재 추정치는 4~6분이며 실측하지 않았다. 커스텀 AMI를 도입하면 2~3분으로 줄어든다.

### 6.2 워밍업이 짧으면 생기는 문제

기동 중인 인스턴스가 아직 트래픽을 받지 못하는데 지표에는 이미 포함되면, 인스턴스당 요청 수가 실제보다 낮게 계산된다. 그러면 스케일 아웃이 필요한데도 발동하지 않는다.

반대로 워밍업이 너무 길면 이미 준비된 인스턴스를 계산에서 계속 빼서 불필요한 추가 증설이 일어난다.

### 6.3 기동 시간이 긴 것의 함의

**기동에 5분이 걸리면 5분 뒤의 트래픽에 대응하는 셈이다.** 급격한 트래픽 증가에는 사실상 무력하다.

| 트래픽 패턴 | 오토스케일링 효과 |
|---|---|
| 완만한 증가 (수십 분) | 유효 |
| 급격한 증가 (수 분) | **거의 무효** |
| 순간 폭증 | 무효 |

급격한 증가에 대응하려면 기동 시간을 줄이거나(커스텀 AMI), 미리 여유 용량을 두거나, 예약 조정으로 사전에 늘려야 한다. **오토스케일링만으로 모든 트래픽 패턴을 감당할 수 없다는 점을 전제로 해야 한다.**

## 7. 스케일 아웃이 만드는 부하 이동

앱을 늘리면 병목이 다른 곳으로 옮겨간다. 늘리기 전에 이동할 곳을 확인해야 한다.

| 구성요소 | 앱이 늘면 | 한계 |
|---|---|---|
| RDS 커넥션 | 비례 증가 | `max_connections` |
| RDS CPU | 쿼리 수 비례 증가 | 크레딧 소진 후 급락 |
| ElastiCache | 연결 수 증가 | 2노드. 쓰기는 primary 한 대가 받는다 |
| ALB LCU | 처리량 비례 | 비용 증가 |
| 모니터링 | 스크랩 대상 증가 | t4g.small 메모리 |

**RDS가 가장 먼저 막힌다.** 앱 인스턴스를 늘려도 DB가 단일 인스턴스라 쓰기 처리량은 늘지 않는다. 읽기가 병목이면 읽기 복제본이 필요하고, 쓰기가 병목이면 인스턴스 승급이나 샤딩이 필요하다.

즉 **오토스케일링은 앱이 병목일 때만 유효하다.** 부하 시험에서 병목 위치를 먼저 확인해야 도입 여부를 판단할 수 있다.

## 8. 실측으로 채워야 할 값

부하 시험 후 아래를 채운다.

| 항목 | 측정 방법 | 채울 값 |
|---|---|---|
| 인스턴스당 처리 가능 RPS | 단계적 부하 증가 중 p99가 목표를 넘는 지점 | (미정) |
| `ALBRequestCountPerTarget` 목표값 | 위 값의 60~70% | (미정) |
| 인스턴스 기동 시간 | 증설부터 healthy까지 | **(미정)** 첫 배포에서 재고 `default_instance_warmup` 을 그 값으로 바꾼다. 현재 300 은 `health_check_grace_period` 와 맞춘 임시값이다 |
| 인스턴스 워밍업 | 기동 시간 + 여유 | (미정) |
| RDS `max_connections` | `SHOW VARIABLES` | (미정) |
| 최대 인스턴스 수 | 4절 산출식 | (미정) |
| 배치 최대 실행 시간 | 배치 로그 | (미정) |
| 수명주기 훅 제한 시간 | 배치 최대 실행 시간 + 여유 | (미정) |
| 병목 위치 | 부하 증가 시 먼저 포화되는 구성요소 | (미정) |

**마지막 항목이 도입 여부를 결정한다.** 병목이 DB면 앱을 늘려도 소용이 없다.

### 8.1 측정 절차

```
0. 시험 사전 점검 (기술 스택 문서 부록 A.9. 기준선 측정은 램프업 3분 + 측정 10분)
1. 앱 1대로 부하를 단계적으로 올린다
2. p99 응답시간, 오류율, CPU 크레딧, DB 커넥션, DB CPU 를 함께 기록한다
3. 어느 지표가 먼저 한계에 닿는지 확인한다  <- 병목 위치
4. 병목이 앱이면 계속. DB면 오토스케일링을 보류한다
5. 앱이 병목이면 p99 목표를 넘는 지점의 RPS 를 기록한다
6. 2대로 늘려 처리량이 선형에 가깝게 증가하는지 확인한다
7. 선형이 아니면 공유 자원에서 경합이 일어나는 것이므로 원인을 찾는다
```

6번과 7번이 중요하다. **인스턴스를 두 배로 늘렸는데 처리량이 1.2배만 늘면 스케일 아웃의 효과가 거의 없다는 뜻이다.**

## 9. 비용 영향

| 인스턴스 | 월 비용 (앱만) | 총계 |
|---|---|---|
| **1 (하한)** | 18.98 USD | 약 140 USD |
| 2 | 37.96 USD | 약 162 USD |
| **3 (상한)** | 56.94 USD | 약 181 USD |
| 4 | 75.92 USD | 약 203 USD |

**오토스케일링은 비용 상한을 없앤다.** 트래픽이 예상보다 크면 청구액도 비례해 늘어난다. 검증 환경에서는 최대 인스턴스 수를 낮게 잡아 상한을 강제하는 편이 안전하다.

부하 시험 중 스케일링이 발동하면 시험 대상이 달라진다는 점도 유의해야 한다. **1대 성능을 측정하려면 스케일링 정책을 꺼야 한다.**

## 10. 검증 계획

도입 시 확인할 항목이다.

| 항목 | 내용 |
|---|---|
| 주입 | 임계값을 넘는 부하를 인가 |
| 확인 1 | 스케일 아웃이 발동하는가 |
| 확인 2 | 신규 인스턴스가 신 버전으로 기동하는가 (SSM) |
| 확인 3 | 처리량이 인스턴스 수에 비례해 증가하는가 |
| 주입 | 부하를 제거 |
| 확인 4 | 스케일 인이 발동하는가 |
| 확인 5 | 종료 대상 인스턴스가 배치를 실행 중이면 대기하는가 |
| 확인 6 | 강제 종료 시에도 데이터 손상이 0인가 |
| 주입 | 스케일 아웃 직후 배포 수행 |
| 확인 7 | 배포 절차가 늘어난 인스턴스 수에 대응하는가 |
| 주입 | 최대 인스턴스 수까지 증설 |
| 확인 8 | DB 커넥션이 한도 안에 머무는가 |

확인 6이 핵심이다. 수명주기 훅이 실패해도 조건부 UPDATE가 막아야 한다.

## 11. 도입 판단 기준

다음을 모두 만족할 때 도입한다.

| 조건 | 이유 |
|---|---|
| 부하 시험에서 앱이 병목으로 확인됨 | DB가 병목이면 효과 없음 |
| `max_connections`가 목표 인스턴스 수를 수용 | 상한 확인 |
| 조건부 UPDATE가 구현되고 검증됨 | 스케일 인 안전 |
| 수명주기 훅이 구현됨 | 배치 중단 방지 |
| 인스턴스 기동 시간이 대응 가능한 수준 | 5분이면 급증에 무력 |
| 최대 인스턴스 수 상한이 예산 안에 있음 | 비용 폭주 방지 |

하나라도 미충족이면 도입하지 않는다. **오토스케일링은 없는 것보다 잘못 설정된 것이 나쁘다.** 불필요한 증설로 비용을 쓰거나, 스케일 인이 배치를 끊거나, 정작 필요할 때 늦게 반응한다.
