# 배치 설계 (백엔드 공통)

주기 실행 배치를 전용 서버 한 대에서 돌린다. 그 구성과, 배치가 다시 돌아도 데이터가 깨지지 않게 하는 장치를 적는다.

원래 이 자리에는 분산 락 설계와 비교 실험 문서가 있었다.
배치 프로세스가 하나가 되어 락을 쓰지 않게 되면서 들어냈고, 락과 무관하게 유효한 부분만 남겼다.
락 구현이 다시 필요해지면 git 이력에서 꺼낸다.

## 2. 배치 서버를 분리한다

### 2.1 목적

주기 실행 스케줄러를 돌린다. 소비기한 경과 로트의 만료 전환, 쿠폰 만료, 미확정 업로드 정리,
일별 판매 집계, 정합성 검사가 전부 일정한 주기로 돌아야 하는 작업이다.

앱과 분리한 이유는 **스케줄러가 도는 프로세스를 하나로 고정하기 위해서**다.
Spring 의 `@Scheduled` 는 인스턴스마다 독립적으로 도므로, 앱 안에 두면 앱을 늘릴 때 배치도 함께 늘어난다.
스케줄러를 전용 인스턴스에만 두면 앱 대수와 무관하게 한 번만 돈다.

**현재 구성에서는 분산 락을 쓰지 않는다.** 배치 프로세스가 하나뿐이라 고를 대상이 없기 때문이다.
다만 이것은 아래 두 조건에 기대고 있다.

```
배치 인스턴스가 1 대다
무중단 배포를 하지 않는다 (2.3 절)
```

**둘 중 하나가 풀리면 락이 다시 필요하다.** 배치 서버를 이중화하거나 롤링 배포로 바꾸면
같은 시각에 배치 프로세스가 둘이 되고, 그때는 이 문서의 전제가 성립하지 않는다.

### 2.2 구성

| 항목 | 값 |
|---|---|
| 인스턴스 | `t4g.micro` x 1, 퍼블릭 서브넷 |
| 인바운드 | 없음. ALB 에 붙지 않는다 |
| 운영 접근 | SSM Session Manager |
| 산출물 | 앱과 같은 jar |
| 구분 | `--spring.profiles.active=prod,batch` |

스케줄러 설정을 프로필로 감싸 배치 프로필에서만 켠다.

```java
@Configuration
@EnableScheduling
@Profile("batch")
class SchedulerConfig { }
```

앱 인스턴스는 `prod` 만 쓰므로 스케줄러가 없다. **앱을 몇 대로 늘려도 배치는 배치 서버에서만 돈다.**

jar 를 나누지 않은 이유는 배치가 앱과 같은 엔티티와 리포지토리를 쓰기 때문이다.
`EXPIRE` 전환은 `stock_lot` 을, 쿠폰 만료는 `member_coupon` 을, 정합성 검사는 거의 모든 표를 건드린다.
산출물을 나누면 그 공유 코드를 라이브러리로 발행하거나 복제해야 하는데 둘 다 대가가 크다.

### 2.3 무중단 배포 대상이 아니다

배치 서버는 **중지 후 교체**한다. 롤링으로 바꾸면 구버전과 신버전 배치가 겹치는 구간이 생겨
"프로세스는 항상 하나" 라는 전제가 깨진다.

사용자 요청을 받지 않으므로 몇 분 멈춰도 된다. 멈춘 동안의 작업은 다음 주기가 따라잡고,
실행 중 종료된 배치는 4장의 조건부 UPDATE 멱등화가 받는다.

## 3. 배치 유형과 재실행 안전성

락을 쓰지 않아도 유형 분류는 그대로 필요하다.
**배치가 중간에 죽고 다시 도는 것은 락과 무관하게 일어나기 때문이다.** 배포, 인스턴스 교체, 예외가 전부 그 경로다.

### 2.2 배치 유형별 중복 실행 피해

연산의 성격에 따라 재실행 위험이 전혀 다르다. 무해한 것과 치명적인 것을 같은 방식으로 다루면 둘 다 잘못된다.

| 유형 | 연산 성격 | 다시 돌면 | 심각도 | 멱등화 필요 |
|------|-----------|--------------|--------|---------|
| 멱등 전이형 | 상태를 특정 값으로 덮어씀 | 같은 결과. 무해 | 낮음 | 불필요 |
| 재계산형 | 원본에서 값을 다시 계산해 덮어씀 | 같은 결과. 자원 낭비만 | 낮음 | 선택 |
| 누적 연산형 | 수량이나 잔액을 증감 | **오차가 누적되어 남음** | 치명적 | 필수 |
| 외부 부수효과형 | 알림 발송, 결제 요청, 파일 전송 | 외부에 이중 요청 | 높음 | **멱등화로 못 막는다** |
| 순번 발급형 | 시퀀스나 채번 | 번호 중복 또는 건너뜀 | 높음 | 필수 |

예시로 옮기면 이렇다.

| 배치 예시 | 유형 | 중복 시 결과 |
|---|---|---|
| 만료 상태 일괄 전이 (`status = EXPIRED`) | 멱등 전이형 | 무해 |
| 통계 집계 테이블 갱신 | 재계산형 | 무해, CPU 낭비 |
| 만료 처리 후 자원 반환 (수량, 좌석, 한도 복원) | 누적 연산형 | **반환이 두 번 일어나 값이 부풀려짐** |
| 확정 처리 후 적립금 지급 | 누적 연산형 | **이중 지급** |
| 미발송 알림 재시도 | 외부 부수효과형 | 중복 발송 |
| 정산 번호 채번 | 순번 발급형 | 번호 충돌 |

**핵심은 세 번째 행이다.** 상태 전이만 보면 두 번 다 같은 값이라 무해해 보이지만, 그 전이에 딸린 누적 연산은 두 번 실행되면 그만큼 값이 커진다.

이 오차는 **발생 시점에 아무 신호도 내지 않는다.** 예외도, 오류 로그도, 실패 응답도 없다. 증상은 며칠 뒤 무관해 보이는 다른 트랜잭션에서 나타난다.

```
14:00  배치 중복 실행으로 자원 수량이 +3 부풀려짐
14:00  오류 없음. 예외 없음. 로그 정상
       사용자 화면에는 3개가 더 있는 것으로 표시됨
       ... 며칠간 정상 거래 계속 ...
17:20  그 3개를 소비하려는 요청이 실패
17:20  "자원 부족" 오류  <- 원인을 가리키지 않는 증상
```

원인이 발생한 시점과 증상이 나타난 시점이 멀고, 증상의 형태가 원인과 달라 추적이 매우 어렵다. **이 시간차가 곧 복구 난이도다.** 사고 직후면 되돌릴 수 있지만, 며칠 지나면 그 사이 정상 거래가 쌓여 되돌릴 방법이 사실상 없어진다.

감지 수단은 백업과 복원 문서 8절의 정합성 검증 배치이며, 대응 절차는 알람과 알림 설계 문서 5.4절에 있다.

### 2.3 피해 시나리오 상세

만료 처리 후 자원을 반환하는 배치를 예로 든다. 흐름은 세 단계다.

1. 만료 조건에 해당하는 레코드를 찾는다
2. 상태를 `EXPIRED`로 바꾼다
3. 점유했던 자원(수량, 좌석, 한도 등)을 되돌린다

무엇이든 배치를 두 번 돌게 만들면 다음과 같이 흐른다. 프로필 설정 실수, 배포 겹침, 수동 기동이 그 경로다.

```
시각  인스턴스 A                       인스턴스 B
t0    레코드 1001 조회 (PENDING)       레코드 1001 조회 (PENDING)
t1    status = EXPIRED 로 갱신
t2                                      status = EXPIRED 로 갱신 (덮어쓰기, 무해해 보임)
t3    자원 풀에 수량 + 3
t4                                      자원 풀에 수량 + 3
```

자원 수량이 실제보다 3만큼 부풀려진다. 상태만 보면 이상이 없어 검증 쿼리로도 잡히지 않는다.

## 4. 최종 방어선: 조건부 UPDATE 멱등화

배치가 중복으로 돌거나 중간에 죽고 다시 돌아도 데이터가 깨지지 않게 하려면,
상태 전이를 원자적 조건부 UPDATE 로 수행하고 그 결과로 이후 동작을 분기해야 한다.

```java
@Transactional
public void expire(long recordId, Instant now) {
    // 상태 전이를 조건부 UPDATE 로 수행한다.
    // 이미 다른 인스턴스가 처리했다면 affected rows 는 0 이 된다.
    int transitioned = jdbcTemplate.update("""
            UPDATE reservation
               SET status = 'EXPIRED', updated_at = ?
             WHERE id = ? AND status = 'PENDING'
            """, Timestamp.from(now), recordId);

    if (transitioned == 0) {
        return;   // 누적 연산도 하지 않고 즉시 종료한다.
    }

    statusHistoryRepository.append(recordId, Status.EXPIRED, ChangedBy.BATCH);
    resourceService.release(recordId);   // 자원 반환은 전이에 성공한 쪽만 수행
}
```

핵심은 세 가지다.

1. **조회 후 판단하지 않는다.** `if (record.getStatus() == PENDING)` 형태로 먼저 확인하고 나중에 갱신하면 그 사이에 다른 인스턴스가 끼어든다. 갱신 손실 패턴 그대로다.
2. **누적 연산을 전이 성공 여부에 종속시킨다.** 전이가 원자적인 한, 누적 연산도 정확히 한 번 일어난다.
3. **전이와 누적 연산이 같은 트랜잭션 안에 있다.** 전이만 커밋되고 반환이 실패하면 자원이 영영 돌아오지 않는다.

외부 부수효과형 배치는 조건부 UPDATE로 먼저 처리 중 상태를 선점한 뒤 외부를 호출한다.

```java
// 발송 전에 상태를 선점한다. 선점에 실패하면 다른 인스턴스가 이미 집어 든 것이다.
int claimed = jdbcTemplate.update("""
        UPDATE notification
           SET status = 'SENDING', claimed_at = ?
         WHERE id = ? AND status IN ('PENDING', 'RETRY')
        """, Timestamp.from(now), notificationId);

if (claimed == 0) {
    return;
}
channel.send(notificationId);
```

발송 후에 상태를 바꾸면 그 사이에 다른 인스턴스가 같은 행을 집어 든다. 순서가 반대여야 한다.

## 5. 전제가 깨졌을 때

배치 프로세스가 하나라는 전제는 **런치 템플릿의 문자열 하나**에 걸려 있다.
앱 ASG 에 실수로 `batch` 프로필이 들어가면 앱 대수만큼 배치가 돈다. 락이 없으므로 아무것도 막지 않는다.

두 층으로 받는다.

### 5.1 예방: Terraform

런치 템플릿과 배치 인스턴스의 user-data 를 코드로 고정한다. 콘솔에서 손으로 바꾸는 경로를 없앤다.

**Terraform 코드 자체가 틀린 경우는 못 막는다.** 코드가 진실이므로 잘못 쓰면 그대로 배포된다.

### 5.2 탐지: 중복 실행 알람

원인을 가리지 않고 결과를 잡는다.

| 지표 | 정의 | 수집 방법 |
|------|------|-----------|
| 중복 실행 건수 | 동일 `scheduled_at` 에 대해 배치 시작 로그가 2건 이상 | 구조화 로그(`job_name`, `scheduled_at`, `instance_id`) |
| 배치 미실행 | 주기가 지났는데 실행 로그가 없음 | 로그 부재 감지 알람 |

`instance_id` 가 로그에 있으므로 **어느 인스턴스에서 잘못 돌았는지가 한 줄에 드러난다.**

탐지가 예방보다 중요한 이유가 있다. 조건부 UPDATE 멱등화가 데이터 손상은 막지만,
**외부 부수효과형은 못 막는다.** 이미 나간 알림은 되돌릴 수 없다. 그래서 났는지 아는 것이 먼저다.

`배치 미실행` 은 배치 서버가 한 대라서 생긴 새 위험이다.
앱 안에서 돌 때는 앱이 살아 있으면 배치도 돌았지만, 이제는 **배치 서버만 죽어도 아무도 모른다.**

## 6. 배치 목록

| 배치 | 유형 | 주기 | 비고 |
|---|---|---|---|
| 소비기한 경과 로트 만료 전환 | 멱등 전이형 | 미정 | `stock_lot.status = 'EXPIRED'`, `available_qty = 0` |
| 미확정 업로드 정리 | 외부 부수효과형 | 미정 | S3 객체를 먼저 지운다(`INF-11-13`) |
| 쿠폰 만료 전환 | 멱등 전이형 | 미정 | `member_coupon.status = 'EXPIRED'` |
| 정합성 검사 | 재계산형 | 미정 | 13건. 목록은 backend 의 `schema-design-rationale.md` 9장 |
| 일별 판매 집계 | 재계산형 | 일 1회 | `daily_sales` UPSERT |

주기와 실행 시각은 아직 정하지 않았다. 정할 때 3장의 유형을 함께 적는다.
