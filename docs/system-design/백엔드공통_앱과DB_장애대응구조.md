## 1. 문서 목적과 범위

요청 경로 위에 있는 세 구성요소의 장애를 다룬다.

1. Spring Boot 인스턴스가 죽거나 응답하지 않는 경우
2. MySQL이 죽거나 페일오버하는 경우
3. 로드밸런서에 문제가 생기는 경우

전체 장애 유형을 망라하는 FMEA는 이 문서의 범위가 아니다. 요청 경로의 구조를 먼저 확정하고, 필요해지면 그 위에 나머지를 얹는다.

로드밸런서는 관리형이라 대응이 불필요하다고 보기 쉬우나, 실제로 겪는 문제의 대부분은 AWS의 서비스 장애가 아니라 설정, 인증서, 삭제, 스케일링 같은 우리 쪽 사유다. 5절에서 AWS 소관과 우리 소관을 명시적으로 나눈다.

이 문서에서 반복해서 등장하는 원칙은 하나다. **한 구성요소의 장애가 다른 구성요소의 장애로 번지지 않게 경계를 만든다.** 대부분의 대형 장애는 단일 고장이 아니라, 작은 고장이 경계 없이 전파되어 커진 결과다.

### 1.1 이전 판단에 대한 정정

초기 설계에서 ALB 헬스체크가 참조하는 readiness 그룹에 `db`를 포함하도록 적었다. 이는 잘못이며, 본 문서 4.1절의 근거로 철회한다. **공유 의존성은 readiness에 넣지 않는다.**

## 2. 전제 구성

```
ALB (2 AZ)
 +--> app-1 (EC2, Docker)              <- 현재 1대. AZ 는 ASG 가 고른다
          |
          +--> RDS MySQL 8.4 Multi-AZ (writer 엔드포인트 하나)
```

| 항목 | 값 |
|---|---|
| 앱 인스턴스 수 | **1** (ASG 구성상 최대 2) |
| DB 구성 | Multi-AZ, 단일 writer 엔드포인트 |
| 목표 RTO (앱 컨테이너 급사) | 10초 |
| 목표 RTO (앱 인스턴스 소실) | 5분 |
| 목표 RTO (DB 페일오버) | 2분 |
| 목표 RPO | 0 (동기 복제) |

앱은 현재 1대로 운영한다. `desired_capacity`를 2로 올리면 이중화가 켜지며, 그때의 목표치는 아키텍처 결정 문서 4.3절에 있다. 본 문서는 **1대 기준**으로 서술하되, 2대가 되었을 때 달라지는 지점은 그때마다 명시한다.

## 3. 앱 인스턴스 장애 대응

### 3.1 방어 3층 구조

층마다 담당하는 고장이 다르고, 복구 속도도 다르다. 한 층으로 전부 처리하려 하면 반드시 구멍이 생긴다.

| 층 | 담당 고장 | 감지 수단 | 복구 시간 | 앱 1대일 때 |
|---|---|---|---|---|
| 컨테이너 | 프로세스 급사, OOM | Docker healthcheck, 종료 코드 | 5~15초 | **주된 복구 경로** |
| 인스턴스 | 응답 불가, 기동 실패 | ALB 헬스체크 | 20~30초 | 제외해도 갈 곳이 없음 |
| 용량 | EC2 소실, AZ 장애 | ASG 헬스체크 | 3~5분 | 유일한 최종 복구 |

앱이 1대인 현재 구성에서는 **2층의 완충 효과가 없다.** 대상 그룹에서 제외해도 트래픽을 넘길 다른 인스턴스가 없기 때문이다. 실질적 방어는 1층과 3층이며, 그 사이 구간은 그대로 다운타임이 된다.

따라서 `restart: unless-stopped` 설정이 이 구성에서 더 중요하다. 컨테이너 수준에서 회복되면 10초, 실패해 인스턴스 교체까지 가면 5분이다.

인스턴스를 2대로 늘리면 2층이 되살아나 RTO가 30초로 내려간다.

### 3.2 컨테이너 층 설정

```yaml
services:
  app:
    image: ghcr.io/${GITHUB_OWNER}/${APP_NAME}:${GIT_SHA}
    restart: unless-stopped
    stop_grace_period: 45s
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health/liveness"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 60s
    environment:
      JAVA_TOOL_OPTIONS: >-
        -XX:MaxRAMPercentage=70
        -Dnetworkaddress.cache.ttl=5
        -Dnetworkaddress.cache.negative.ttl=1
```

**`restart: always`가 아니라 `unless-stopped`인 이유**는 배포 중 의도적으로 내린 컨테이너를 Docker가 다시 살리지 않게 하기 위해서다. `always`로 두면 배포 절차와 재기동 정책이 충돌한다.

**`MaxRAMPercentage`를 명시하는 이유**는 컨테이너 메모리 한계를 JVM이 인식하게 하기 위해서다. 이 값이 없으면 힙이 컨테이너 한계를 넘어서 커지고, JVM이 OutOfMemoryError를 던지기 전에 커널이 프로세스를 죽인다. 후자는 힙 덤프도 남지 않아 원인 분석이 불가능하다.

**`start_period`가 60초인 이유**는 기동 중 healthcheck 실패를 재기동으로 오인하지 않게 하기 위해서다. 이 값이 짧으면 애플리케이션이 뜨는 도중에 계속 재기동되는 무한 루프에 빠진다.

### 3.3 헬스체크 설계

liveness와 readiness는 서로 다른 질문에 답한다. 이 구분이 무너지면 장애가 증폭된다.

| 종류 | 답하는 질문 | 소비자 | 포함 대상 | 실패 시 동작 |
|---|---|---|---|---|
| liveness | 이 프로세스를 죽이고 다시 띄워야 하는가 | Docker | JVM 생존 여부만 | 컨테이너 재기동 |
| readiness | 이 인스턴스에 트래픽을 보내도 되는가 | ALB | 인스턴스 로컬 상태만 | 대상 그룹에서 제외 |

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      show-details: never
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
```

Spring Boot의 기본 동작이 이미 올바르다. `probes.enabled: true`를 켜면 `/actuator/health/liveness`와 `/actuator/health/readiness`가 노출되며, readiness 그룹에는 `readinessState`만 포함되고 외부 의존성 인디케이터는 들어가지 않는다.

**여기에 임의로 인디케이터를 추가하지 않는다.** 판단 기준은 다음과 같다.

| 의존성 성격 | readiness 포함 | 이유 |
|---|---|---|
| 인스턴스 로컬 상태 (디스크, 기동 완료) | 포함 | 이 인스턴스만의 문제이므로 빼면 해결됨 |
| 공유 의존성 (DB, 캐시, 외부 API) | 제외 | 모든 인스턴스가 동시에 빠져 상황이 악화됨 |

### 3.4 ALB 대상 그룹 설정

| 항목 | 값 | 근거 |
|---|---|---|
| 헬스체크 경로 | `/actuator/health/readiness` | liveness가 아님 |
| 간격 | 10초 | |
| 타임아웃 | 5초 | |
| 정상 임계값 | 2 | |
| 비정상 임계값 | 2 | 20초 내 판정 |
| deregistration delay | 30초 | graceful shutdown과 정합 |

비정상 임계값을 1로 낮추면 감지가 빨라지지만, 일시적 지연으로 정상 인스턴스가 잘못 빠지는 위험이 커진다. 2가 균형점이다.

`/actuator/**` 경로는 ALB 리스너 규칙에서 외부 접근을 차단한다. 헬스체크는 ALB가 내부적으로 수행하므로 차단해도 동작한다.

### 3.5 인스턴스 급사 타임라인

```
t0     인스턴스 소실
t0     ALB 헬스체크 1차 실패
t10    ALB 헬스체크 2차 실패 -> unhealthy 판정
t10~   대상 그룹에 정상 대상이 없음 -> fail-open, 502 반환
t60    ASG가 desired 미달 감지
t240   신규 인스턴스 기동 및 readiness 통과, 대상 그룹 편입
```

**t0부터 t240까지가 그대로 다운타임이다.** 인스턴스가 1대이므로 ALB가 대상을 제외해도 트래픽을 넘길 곳이 없다. RTO 5분 목표는 t240 시점을 의미한다.

2대로 늘리면 t10에 나머지 인스턴스가 전체 트래픽을 받아 RTO가 30초가 된다. 이 차이가 이중화의 실질적 가치다.

**t10까지의 요청 실패는 서버가 막을 수 없다.** 이미 그 인스턴스로 라우팅된 요청은 갈 곳이 사라진 상태다. 따라서 클라이언트 재시도가 전제되어야 하며, 쓰기 요청이라면 멱등키가 필요하다. 1대 구성에서는 재시도해도 복구 전까지 실패하므로, 클라이언트의 백오프 정책이 더 중요해진다.

```java
// 쓰기 요청은 클라이언트가 보낸 요청 식별자로 중복 처리를 막는다.
@PostMapping("/v1/orders")
public OrderResponse create(@RequestHeader("Idempotency-Key") String key,
                            @RequestBody @Valid OrderRequest request) {
    return orderService.createIdempotent(key, request);
}
```

### 3.6 graceful shutdown 타임아웃 계층

안쪽에서 바깥쪽으로 갈수록 길어야 한다. 하나라도 역전되면 처리 중 요청이 잘린다.

| 계층 | 설정 | 값 |
|---|---|---|
| ALB 대상 그룹 | deregistration delay | 30초 |
| Spring Boot | `spring.lifecycle.timeout-per-shutdown-phase` | 30초 |
| Docker Compose | `stop_grace_period` | 45초 |
| systemd | `TimeoutStopSec` | 60초 |

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

## 4. 데이터베이스 장애 대응

### 4.1 핵심 전제: DB 장애를 앱 장애로 만들지 않는다

DB가 죽었을 때 가장 흔한 실패 양상은 DB 자체가 아니라 **앱이 함께 죽는 것**이다. 경로는 항상 같다.

```
요청 1   -> 커넥션 획득 시도 -> 무한 대기
요청 2   -> 커넥션 획득 시도 -> 무한 대기
...
요청 200 -> 톰캣 워커 스레드 전부 소진
결과: 헬스 엔드포인트조차 응답하지 못함 -> 인스턴스가 죽은 것으로 판정됨
```

이 경로를 끊는 것이 이 절의 전부다. **DB가 없어도 앱은 살아 있어야 하며, 명확한 오류를 빠르게 반환해야 한다.**

이것이 3.3절에서 공유 의존성을 readiness에서 제외한 이유이기도 하다. 두 경우를 비교하면 다음과 같다.

| readiness에 db 포함 | DB 장애 시 | 결과 |
|---|---|---|
| 포함함 | 인스턴스가 unhealthy | 대상 그룹이 비었다가 ALB fail-open으로 되돌아옴. 헬스 상태가 요동치고, 복구 후 재편입도 지연됨 |
| 포함 안 함 | 인스턴스가 healthy | 503을 안정적으로 반환. DB 복구 시 즉시 정상화 |

인스턴스가 1대인 현재 구성에서는 fail-open의 완충 효과가 없다. 갈 곳이 그 하나뿐이므로 죽은 대상으로 계속 요청이 간다. 감지에는 문제없으나, 앱 프로세스 자체가 죽었다면 503이 아니라 502가 나온다.

두 번째가 옳다. DB가 죽었을 때 앱이 할 일은 사라지는 것이 아니라, 살아서 명확한 오류를 반환하고 복구를 기다리는 것이다.

### 4.2 RDS Multi-AZ 페일오버의 동작

**대기 인스턴스는 읽기를 받지 못한다.** 가용성 전용이고 접속할 엔드포인트가 없다. 조회를 나눠 받아 주는 것이 아니므로 읽기와 쓰기가 모두 프라이머리 한 대로 간다. 읽기 경로를 분리하려면 별도의 읽기 복제본이 필요하며 4.9절에서 다룬다.

페일오버는 **엔드포인트 DNS 레코드가 대기 인스턴스를 가리키도록 바뀌는** 방식이다. 이 사실이 앱 설정을 결정한다.

```
t0     프라이머리 장애 발생
t0~60  RDS가 장애 판정 후 대기 인스턴스를 승격
t60    DNS 레코드 갱신
t60~   앱이 새 주소로 재연결       <- 여기서 설정에 따라 결과가 갈린다
t120   정상화
```

동기 복제이므로 커밋된 데이터의 손실은 없다(RPO 0). 문제는 t0부터 t60까지 앱이 무엇을 하느냐다.

#### RPO 0 의 대가는 쓰기 지연이다

**동기 복제는 공짜가 아니다.** 이 문서의 다른 곳에서 동기 복제는 항상 이득으로만 나오지만, 그 이득에는 상시 지불하는 비용이 붙는다.

프라이머리는 자기 스토리지에 쓰면서 동시에 다른 AZ 의 스탠바이 스토리지에도 쓴다. 커밋은 양쪽이 모두 내구성 있게 기록된 뒤에야 응답한다.

```
Single-AZ   commit -> 로컬 fsync -> 응답
Multi-AZ    commit -> 로컬 fsync + AZ 건너 스탠바이 fsync (둘 다 끝나야) -> 응답
                              ^^^^^^^^^^^^^^ 상시 추가분
```

같은 리전 안 AZ 간 왕복이 통상 1~2ms 라 커밋 한 번에 그만큼이 더 붙는다. 커밋이 잦은 워크로드에서 쓰기 지연이 1.5~2배로 관측되는 경우가 흔하다. **일반적인 관측치이며 이 프로젝트에서 실측한 값이 아니다.**

영향 범위가 균일하지 않다는 점이 중요하다.

| 대상 | 영향 |
|---|---|
| 조회(SELECT) | 없음. 복제 경로를 타지 않는다 |
| 대량 INSERT 처리량 | 작다. group commit 이 여러 트랜잭션의 로그 flush 를 묶는다 |
| 짧은 트랜잭션 다수의 커밋 지연 | **가장 크다.** 트랜잭션마다 왕복 비용을 낸다 |

대신 자동 백업을 스탠바이에서 뜨게 되어 백업 창 동안 프라이머리 I/O 부담은 줄어든다.

#### 조건부 UPDATE 와 겹칠 때 증폭된다

`INF-06` 의 조건부 UPDATE 는 행 잠금을 잡은 채 커밋까지 간다. **커밋이 2ms 늦어지면 잠금 보유 시간도 그만큼 늘어난다.**

절대 지연보다 `잠금 보유 시간 x 동시성` 이 문제다. 같은 상품 행에 요청이 몰리면 늘어난 보유 시간이 대기 큐로 증폭되고, 커넥션 풀 10 개가 먼저 마른다. 선착순 구매처럼 한 행에 집중되는 시나리오에서 드러난다.

`HikariPendingHigh`(대기 9 초과)가 이것을 잡는 알람이고, Grafana `03 앱과 JVM` 화면의 HikariCP 패널이 같은 값을 보여 준다.

**따라서 부하 시험은 Multi-AZ 를 켠 상태에서만 유효하다.** Single-AZ 에서 잰 숫자는 프로덕션 값이 아니다. `P99Slow` 의 기준선도 전환이 끝난 뒤에 읽어야 하며, 동기화가 진행 중인 구간의 값이 섞이면 안 된다.

`db.t4g.micro` 에서는 복제 지연보다 CPU 크레딧과 커넥션 풀이 먼저 병목일 가능성이 높다. 이 절은 그 둘을 배제한 뒤에도 쓰기가 느릴 때 의심할 자리를 남겨 두는 것이 목적이다.

### 4.3 설정 1: JVM DNS 캐시

페일오버가 DNS 변경이므로, JVM이 옛 주소를 캐시하고 있으면 승격이 끝난 뒤에도 계속 실패한다. JVM은 보안 관리자 설정에 따라 DNS 조회 결과를 장기간, 경우에 따라 영구히 캐시한다.

```
-Dnetworkaddress.cache.ttl=5
-Dnetworkaddress.cache.negative.ttl=1
```

이 설정이 빠지면 다른 모든 설정을 맞춰도 복구가 되지 않는다. **페일오버 검증에서 정상화가 60초를 크게 넘긴다면 가장 먼저 의심할 항목이다.**

### 4.4 설정 2: JDBC 타임아웃

이미 맺어진 커넥션은 상대가 사라져도 즉시 오류를 내지 않는다. 소켓 타임아웃이 없으면 OS의 TCP 타임아웃(수 분)까지 매달린다.

```
jdbc:mysql://{endpoint}:3306/{db}?connectTimeout=3000&socketTimeout=10000
```

| 파라미터 | 값 | 의미 |
|---|---|---|
| `connectTimeout` | 3000 | TCP 연결 수립 제한 |
| `socketTimeout` | 10000 | 쿼리 응답 대기 제한 |

`socketTimeout`은 **가장 오래 걸리는 정상 쿼리보다 길어야 한다.** 10초로 두면 그보다 느린 쿼리는 장애가 아닌 상황에서도 잘린다. 느린 쿼리가 있다면 타임아웃을 늘리기 전에 그 쿼리를 고치는 것이 순서다.

### 4.5 설정 3: 커넥션 풀

```yaml
spring:
  datasource:
    hikari:
      connection-timeout: 3000       # 풀에서 커넥션을 못 얻으면 3초 만에 포기
      validation-timeout: 1000
      keepalive-time: 120000
      max-lifetime: 1500000          # 25분
      maximum-pool-size: 10
      minimum-idle: 10
```

| 설정 | 역할 |
|---|---|
| `connection-timeout` | 스레드 고갈을 막는 핵심 장치 |
| `validation-timeout` | 죽은 커넥션 판별을 빠르게 |
| `keepalive-time` | 유휴 커넥션이 조용히 끊긴 것을 미리 발견 |
| `max-lifetime` | 커넥션을 주기적으로 교체해 오래된 연결 누적 방지 |

`connection-timeout` 3초가 3.1절의 전파 경로를 끊는다. 요청이 3초 만에 실패하고 스레드를 반환하므로, 200개 스레드가 잠기는 대신 200개가 계속 순환하며 빠르게 실패한다. 서비스의 증상이 "무한정 느려짐"에서 "명확한 오류"로 바뀐다.

`maximum-pool-size`와 `minimum-idle`을 같게 두면 풀 크기가 고정되어, 부하 급증 시 커넥션 생성 지연이 생기지 않는다. 현재 1대 기준 10개이며, 배포 중에는 신구 인스턴스가 함께 존재해 20개가 된다.

**DB에 붙는 것은 앱만이 아니다.** 배치 인스턴스가 앱과 같은 jar를 `prod,batch` 프로필로 띄우므로 같은 `application.yml`을 읽고 **풀도 똑같이 10개**다. 여기에 `mysqld_exporter`와 운영자 접속이 더해진다.

| 출처 | 평상시 | 배포 중 |
|---|---|---|
| 앱 1대 (현재) | 10 | 20 |
| 앱 2대 (이중화 후) | 20 | 30 |
| 배치 1대 | 10 | 10 |
| `mysqld_exporter` | 1~3 | 1~3 |
| 운영자 SSM 접속 | 1~2 | 1~2 |
| **합계 (앱 1대)** | **약 23** | **약 33** |
| **합계 (앱 2대)** | **약 33** | **약 45** |

배치는 무중단 배포를 하지 않으므로(배치 설계 2.3절) 배포 중에도 10개 그대로다.

#### `max_connections` 예측값

RDS는 기본 파라미터 그룹에서 이 값을 공식으로 정한다 (등급 B, AWS 문서).

```
max_connections = {DBInstanceClassMemory / 12582880}
```

상수 12,582,880은 MySQL 커넥션 하나당 대략적인 메모리 소비량(바이트)이다.
**`DBInstanceClassMemory`는 광고된 RAM이 아니다.** OS와 RDS 프로세스가 쓰는 몫을 뺀 값이며, **작은 클래스일수록 빼는 비율이 크다.**

```
단순 계산 (1 GiB)   1,073,741,824 / 12,582,880 = 85
db.t3.micro 실제                              약 60
db.t4g.micro                    같은 1 GiB 라 db.t3.micro 와 동급으로 본다
```

**약 60으로 예측한다.** 배포 중 최대치가 약 45이므로 수용은 되지만 **여유가 25%뿐이다.** 문서가 앱만 세었을 때는 30 대 60으로 두 배 여유처럼 보였으나 실제는 그렇지 않다.

**이 값은 예측이지 실측이 아니다.** 첫 기동 후 확인한다 (`OPS-1-11`).

```sql
SHOW VARIABLES LIKE 'max_connections';
```

**파라미터 그룹에서 직접 지정하지 않는다.** 1 GiB에서 커넥션당 12MB를 쓰므로 공식보다 높게 잡으면 OOM으로 간다. AWS가 메모리 비례 공식을 쓰는 이유가 그것이다.

### 4.6 설정 4: 트랜잭션 타임아웃

```java
@Transactional(timeout = 5)
public void placeOrder(OrderCommand command) { ... }
```

커넥션을 얻은 뒤 쿼리 도중 멈추는 경우를 대비한다. 쓰기 경로에 우선 적용하고, 조회 경로는 `socketTimeout`으로 충분한 경우가 많다.

트랜잭션 안에서 외부 API를 호출하지 않는다는 규칙도 여기에 함께 적용된다. 외부 호출이 느려지면 그동안 DB 커넥션이 점유되어, DB가 멀쩡한데도 풀이 고갈된다.

### 4.7 실패를 어떻게 보이게 할 것인가

빠르게 실패한 다음 무엇을 응답할지 정해야 한다.

```java
@RestControllerAdvice
public class DataAccessExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(DataAccessExceptionHandler.class);

    @ExceptionHandler(DataAccessResourceFailureException.class)
    public ResponseEntity<ErrorResponse> handleUnavailable(DataAccessResourceFailureException e) {
        log.error("database unavailable", e);
        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
                .header(HttpHeaders.RETRY_AFTER, "5")
                .body(ErrorResponse.of("SERVICE_UNAVAILABLE",
                        "일시적인 오류입니다. 잠시 후 다시 시도해 주세요."));
    }
}
```

500이 아니라 503에 `Retry-After`를 붙이는 이유는 클라이언트와 중간 계층에게 "코드 버그가 아니라 일시적 상태"임을 알리기 위해서다. 클라이언트는 이 신호로 재시도 여부를 판단할 수 있다.

오류 메시지에 내부 예외나 DB 정보를 노출하지 않는다. 상세 내용은 로그에만 남긴다.

### 4.8 복구는 자동이어야 한다

Hikari는 검증에 실패한 커넥션을 폐기하고 새로 생성한다. DNS TTL이 5초라면 페일오버 완료 후 수 초 안에 새 프라이머리로 연결된다.

**앱 재기동이 필요 없어야 한다.** 재기동해야만 복구된다면 4.3절의 DNS 캐시 설정이 적용되지 않은 것이다. 이것이 검증에서 확인할 가장 중요한 항목이다.

### 4.9 읽기 경로 분리는 선택지로 남긴다

읽기와 쓰기를 나누는 것은 **조건이 맞을 때 택하는 옵션**이지 예정된 일정이 아니다. 지금은 1단계로 간다.

| 단계 | 구성 | 인스턴스 | Multi-AZ | 읽기 분리 | 월 비용 |
|---|---|---|---|---|---|
| **1단계 (현재)** | primary + standby | 2대분 | 예 | 없음 | 29.20 USD |
| **2단계 (옵션)** | primary + standby + replica | 3대분 | 예 | 있음 | 43.80 USD |

**2단계는 1단계 위에 얹는 것이다.** 대기 인스턴스를 걷어내고 복제본으로 바꾸는 것이 아니다. 프라이머리를 건드리지 않고 복제본만 추가하므로 지우면 원상복구되고, RTO 2분과 RPO 0 도 그대로 유지된다.

#### 대기 인스턴스를 복제본으로 바꾸는 안은 기각한다

같은 2대분 비용으로 `primary + replica` 를 만들 수도 있다. 비용은 같지만 자동 페일오버를 잃는다. 다음 이유로 택하지 않는다.

- **복제본에는 자동 승격이 없다.** 승격은 `promote-read-replica` 를 사람이 호출하는 수동 작업이고, 복제를 끊는 단방향이며, 승격된 인스턴스는 새 엔드포인트를 가지므로 앱의 접속 대상도 바꿔야 한다
- **깨끗한 승격의 전제를 장애 때 못 지킨다.** AWS 절차는 프라이머리 쓰기를 멈추고 복제가 따라잡기를 기다리라고 하는데, 프라이머리가 이미 죽은 상황에서는 성립하지 않는다
- **비동기라 RPO 가 0이 아니다.** 미복제 커밋이 유실된다. 주문과 재고에서 이것은 지연이 아니라 정합성 문제다
- AWS 문서가 복제본 승격을 동기 복제와 자동 페일오버의 **보완**으로 규정한다. 대체재가 아니다

읽기를 덜어내려면 Multi-AZ 를 유지한 채 복제본을 붙이라는 것이 AWS 의 처방이기도 하다.

> you can't use the Multi-AZ secondary to serve read-only queries. Instead, you can create read replicas from high-traffic Multi-AZ DB instances to offload read-only queries.

#### 두 기능은 서로 방해하지 않는다

```
t0   primary(AZ-a) 장애
     |
     +-- standby(AZ-c) 가 자동으로 새 프라이머리     60~120초
     |
     +-- replica(AZ-b) 는 복제 원본만 자동 전환      승격 아님, 계속 읽기 전용
```

**복제본은 승격되는 것이 아니라 복제 원본을 바꾼다.** 프라이머리가 페일오버해도 복제본이 새 프라이머리를 자동으로 다시 물기 때문에 사람이 손댈 일이 없다. 복제본 승격이 필요해지는 것은 프라이머리와 대기 인스턴스를 동시에 잃는 경우뿐이고, 그때는 수동이다.

#### 2단계로 가는 조건

**부하 시험에서 읽기가 병목으로 확인될 때** 검토한다. 그 전에 밟을 것이 있다.

1. 조회 캐시를 제대로 태운다
2. 인덱스와 쿼리를 정리한다
3. 그래도 프라이머리가 못 버티면 복제본을 붙인다

순서를 건너뛰면 월 14.60 USD 를 더 내고도 병목이 안 풀린다. 병목이 쓰기 쪽이면 복제본은 답이 아니고 인스턴스 승급으로 간다.

#### 2단계에 따라오는 것

- 복제가 비동기라 복제 지연이 생긴다. 어떤 조회를 복제본으로 보낼지 도메인 단위로 판정해야 한다. 재고나 결제 확인처럼 최신성이 필요한 읽기는 프라이머리로 간다
- 데이터소스 라우팅이 추가되어 트랜잭션 경계 설계가 복잡해진다
- `ReplicaLag` 지표가 그때부터 유효해진다 (기술 스택 문서 2.4절)
- 복제본 자체를 Multi-AZ 로 만들 수도 있다. 조회 경로가 Critical 로 올라가면 그때 검토한다 (인스턴스 4대분)

## 5. 로드밸런서 장애 대응

### 5.1 대응 범위 구분

ALB는 단일 장비가 아니라 **가용영역마다 노드 집합을 두고 DNS로 앞단을 감싼 구조**다. 이 구조 때문에 어떤 고장은 AWS가 알아서 처리하고, 어떤 고장은 전적으로 우리 몫이다. 둘을 구분하지 않으면 "관리형이니 안전하다"는 잘못된 안심에 빠진다.

| 유형 | 원인 | 처리 주체 | 본 문서 대응 |
|---|---|---|---|
| 리스너 규칙 오설정 | 사람 실수 | 우리 | 5.4절 |
| 인증서 만료 | 검증 레코드 삭제로 자동 갱신 실패 | 우리 | 5.4절 |
| 실수로 삭제 | 잘못된 대상에 destroy 실행 | 우리 | 5.4절 |
| 보안 그룹 변경 사고 | 수동 변경 | 우리 | 5.4절 |
| 스케일링 지연 | 급격한 트래픽 증가 | 우리 | 5.4절 |
| 대상 전부 unhealthy | 앱 또는 DB 문제 | 공동 | 5.3절 |
| 클라이언트 DNS 캐시 | 클라이언트가 TTL 미준수 | 우리 | 5.6절 |
| AZ 단위 노드 이상 | AWS 인프라 | **AWS** | 5.2절, 대기 |
| ALB 서비스 전체 장애 | AWS | **AWS** | **범위 제외**, 5.8절 |

마지막 두 행만 AWS 소관이다. 나머지 일곱 개는 우리가 설계하지 않으면 아무도 하지 않는다.

### 5.2 AWS가 자동으로 처리하는 것

**노드 확장과 교체.** 트래픽이 변하면 ELB가 로드밸런서를 확장하고 DNS 항목을 갱신한다. DNS 항목의 TTL은 60초로 지정되어 있어 IP 주소가 빠르게 재매핑된다. 노드 하나가 고장 나면 AWS가 교체하고 해당 IP를 DNS에서 제거한다.

**AZ 단위 격리.** 어느 가용영역의 대상 그룹에 정상 대상이 없으면 해당 서브넷의 IP를 DNS에서 제거하고, 다른 가용영역의 노드는 계속 트래픽을 처리한다. Route 53이 특정 AZ의 로드밸런서 IP를 비정상으로 판단하면 그 IP를 FQDN 레코드에서 제거한다.

**우리가 할 일은 2개 가용영역을 활성화하고 각 AZ에 정상 대상을 두는 것뿐이다.** 이미 앱 인스턴스를 2 AZ에 분산했으므로 조건을 만족한다.

이 층의 장애가 발생하면 **기다린다.** 개입할 수단이 없고, 개입하려 들면 오히려 상황을 악화시킨다.

### 5.3 fail-open과 우리 설계의 관계

모든 가용영역에서 모든 대상이 동시에 헬스체크에 실패하면 로드밸런서는 fail-open으로 전환해, 상태와 무관하게 모든 대상으로 트래픽을 보낸다. 정상 대상이 임계값(기본값 1개)에 못 미치면 등록된 아무 대상에게나 정상인 것처럼 트래픽을 보내는 동작이 자동으로 발동한다.

**이 동작은 우리 설계에 유리하게 작동한다.** 4.1절에서 readiness에 공유 의존성을 넣지 않기로 한 결정과 맞물린다.

| 구성 | DB 장애 시 | ALB 동작 | 결과 |
|---|---|---|---|
| readiness에 db 포함 | 두 인스턴스 모두 unhealthy | 대상 그룹이 비었다가 fail-open | 헬스 상태 요동, 복구 후 재편입 지연 |
| readiness에 db 제외 | 두 인스턴스 모두 healthy | 정상 라우팅 | 503을 안정적으로 반환 |

두 번째가 옳다. ALB가 요청을 계속 보내 주어야 앱이 503과 `Retry-After`로 명확한 신호를 줄 수 있다.

**응답 코드 구분이 중요하다.** 비정상 대상이 TCP 연결을 거부하면 ALB가 502를 생성한다. 즉 앱이 죽어서 포트가 닫히면 502, 앱이 살아서 DB 장애를 알리면 503이다.

| 코드 | 의미 | 원인 위치 |
|---|---|---|
| 502 | ALB가 대상에 연결하지 못함 | 앱 프로세스 자체 문제 |
| 503 | 앱이 의도적으로 반환 | 하위 의존성 문제 |
| 504 | 대상 응답 시간 초과 | 앱 또는 DB 지연 |

알람과 대시보드에서 셋을 구분하지 않으면 원인 위치를 잘못 짚는다.

### 5.4 우리가 대응해야 하는 항목

| 유형 | 예방 | 감지 | 복구 |
|---|---|---|---|
| 리스너 규칙 오설정 | Terraform 단일 경로, PR 리뷰 | 배포 절차의 ALB 경유 스모크 테스트, 5xx 알람 | 이전 커밋으로 apply |
| 인증서 만료 | ACM DNS 검증, 검증 레코드를 Terraform이 관리 | 만료 잔여일 알람 (임계 30일) | 재발급 후 리스너 교체 |
| 실수로 삭제 | 삭제 방지 속성 + `prevent_destroy` | 외부 관점 감시 | Terraform으로 재생성, alias 레코드 갱신 |
| 보안 그룹 변경 사고 | Terraform 단일 경로 | 드리프트 점검, 5xx 알람 | 이전 상태로 apply |
| 스케일링 지연 | 부하 시험 램프업 완만화 | 502와 503 구분, LCU 지표 | 램프업 조정 또는 LCU 예약 |

**삭제 방지는 Terraform 도입으로 오히려 위험이 커진 항목이다.** 잘못된 변수 파일로 destroy를 돌리면 ALB가 사라지고 DNS 이름이 바뀐다. 두 겹으로 막는다.

```hcl
resource "aws_lb" "main" {
  name                       = "${var.project}-alb"
  load_balancer_type         = "application"
  enable_deletion_protection = true

  lifecycle {
    prevent_destroy = true
  }
}
```

**인증서 갱신은 조용히 실패한다.** ACM의 DNS 검증은 자동 갱신되지만, 검증용 CNAME 레코드가 삭제되면 갱신이 실패하고 만료 시점에야 드러난다. 검증 레코드를 Terraform 관리 대상에 포함시키고, 잔여일 알람을 함께 건다.

**LCU 예약은 선택 사항이다.** 용량은 리전 수준에서 예약되어 가용영역에 균등 분산되며, 요청은 선착순으로 처리되어 보통 몇 분 안에 이행되지만 최대 몇 시간이 걸릴 수 있다. 예약하거나 프로비저닝된 용량은 종료하거나 취소할 때까지 계속 과금된다. 부하 시험 구간에만 쓰고 반드시 해제한다.

### 5.5 감지 수단

**현재 설계의 사각지대를 먼저 짚는다.** 모니터링 인스턴스가 VPC 안에 있어 Prometheus는 앱 인스턴스를 직접 스크랩한다. 즉 **ALB가 죽어도 모든 앱 지표가 정상으로 보인다.** 앱은 살아 있고 헬스체크도 통과하는데 사용자만 접속하지 못하는 상태를 감지할 수단이 없다.

이를 메우려면 외부 관점 감시가 필요하다.

| 감지 수단 | 대상 | 비용 |
|---|---|---|
| Route 53 헬스체크 | 도메인 엔드포인트를 AWS 외부 위치에서 주기 점검 | 월 0.50 USD |
| CloudWatch `HTTPCode_ELB_5XX_Count` | ALB가 생성한 5xx | 무료 한도 |
| CloudWatch `HTTPCode_ELB_502_Count` | 대상 연결 실패 | 무료 한도 |
| CloudWatch `HealthyHostCount` | 대상 그룹 정상 호스트 수 | 무료 한도 |
| CloudWatch `TargetResponseTime` | 대상 응답 지연 | 무료 한도 |
| CloudWatch `ConsumedLCUs` | LCU 소모량 | 무료 한도 |
| ACM `DaysToExpiry` | 인증서 잔여일 | 무료 한도 |

**Route 53 헬스체크는 모니터링 인스턴스와 독립적이다.** 모니터링이 죽어도 동작하므로, 단일 장애점 보완책으로도 기능한다.

> **2026-08-28 현재 이 헬스체크는 존재하지 않는다.** 도메인이 없어 생성 조건을 만족하지 못한다 (`INF-38`).
> 이 절과 아래 롤백 판단은 근거 지표가 없는 상태로 읽어야 한다. 배경은 기술 스택 문서 5.6절에 있다.

알람의 심각도와 전달 채널은 [알람과 알림 설계 문서](./백엔드공통_알람과알림_설계.md) 5절에 정리했다. 본 절은 감지 수단만 다룬다.

| 알람 | 조건 | 심각도 |
|---|---|---|
| 외부 접속 실패 | Route 53 헬스체크 실패 2회 연속 | Critical |
| 정상 호스트 수 0 | 1분 지속 | Critical |
| 인증서 잔여일 | 30일 미만 | Critical |
| ALB 5xx 급증 | 배포 전 대비 2배, 3분 지속 | Critical |
| 502 발생 | (미정) 초과 | Critical |

### 5.6 AWS가 처리하지 않는 것: 클라이언트 DNS 캐시

클라이언트가 TTL을 지키지 않고 DNS에서 제거된 IP로 요청을 보내면 그 요청은 실패한다. 로컬 DNS 캐시가 TTL(60초)이 만료될 때까지 그 IP를 갖고 있을 수 있다.

**4.3절에서 JVM DNS 캐시를 5초로 낮춘 것과 같은 문제가 클라이언트 쪽에서도 발생한다.** 특히 부하 생성기가 ALB IP를 오래 캐시하면 AZ 페일오버 실험에서 실제보다 나쁜 결과가 나오고, 이를 서버 문제로 오진하게 된다.

| 항목 | 조치 |
|---|---|
| 부하 생성기 | IP가 아닌 도메인으로 접속. DNS 캐시 동작을 사전 확인 |
| 기존 TCP 연결 | DNS에서 IP가 빠져도 유지되므로 클라이언트 재시도 필요 |
| 쓰기 요청 | 재시도 시 중복 방지를 위해 멱등키 필수 |

### 5.7 검증 계획

| 항목 | 내용 |
|---|---|
| 주입 | 대상 그룹의 모든 인스턴스를 unhealthy로 만든다 |
| 확인 1 | fail-open이 발동해 트래픽이 계속 전달되는가 |
| 확인 2 | 502와 503이 의도대로 구분되어 나오는가 |
| 주입 | 인증서를 잘못된 것으로 교체한다 |
| 확인 3 | 클라이언트가 TLS 오류를 받고 알람이 발생하는가 |
| 주입 | 부하 램프업을 급격하게 건다 |
| 확인 4 | 스케일링 지연 구간의 5xx가 앱 지표와 무관함을 확인 |
| 사전 확인 | 부하 생성기의 DNS 캐시 TTL 준수 여부 |

ALB 삭제와 AZ 장애는 주입하지 않는다. 전자는 복구에 시간이 들고 얻는 정보가 적으며, 후자는 우리가 발생시킬 수 없다.

### 5.8 범위에서 제외하는 것

**리전 단위 ELB 서비스 장애는 대응 범위에서 제외한다.** 다중 리전 구성이 유일한 대안인데 예산과 검증 가능성 모두에서 불가능하다.

제외한다는 것이 아무것도 하지 않는다는 뜻은 아니다. 발생 시 취할 행동을 런북에 명시한다.

1. AWS Health Dashboard에서 서비스 상태 확인
2. Route 53 헬스체크와 CloudWatch 지표로 영향 범위 파악
3. 앱 인스턴스와 DB가 정상인지 확인 (복구 후 즉시 서비스 가능한 상태 유지)
4. 상황 공지, 복구 대기
5. 사후에 실제 소요 시간을 기록해 SLA와 대조

**무엇을 포기했는지 명시하고 그때 무엇을 할지 적어 두는 것 자체가 대응이다.** "대안 없음"으로 끝내면 실제 상황에서 판단할 근거가 없다.

## 6. 세 장애의 상호작용

현재 구성(앱 1대) 기준이다.

| 상황 | 앱의 상태 | ALB 판정 | 응답 코드 | 사용자 경험 |
|---|---|---|---|---|
| 앱 컨테이너 급사 | 재기동 중 | 대상 unhealthy, fail-open | 502 | 10초 내외 중단 |
| 앱 인스턴스 소실 | 없음 | 대상 없음, fail-open | 502 | ASG 교체까지 5분 중단 |
| DB 페일오버 | 살아 있음 | 정상 | 503 | 60초간 오류, 이후 자동 정상화 |
| AZ 소실 (앱이 있는 AZ) | 없음 | 대상 없음 | 502 | 다른 AZ에 재기동까지 5분 |
| AZ 소실 (앱이 없는 AZ) | 정상 | 정상 | 200 | DB 페일오버만 발생 |
| ALB 노드 이상 | 정상 | AWS가 노드 교체 | 200 | 영향 미미 |
| 배포 중 (혼재 구간) | 신구 2대 | 둘 다 정상 | 200 | 요청마다 다른 버전 |

세 번째 행이 중요하다. readiness에 DB를 넣지 않았기 때문에 두 장애가 겹쳐도 판정이 독립적으로 이루어진다. DB를 readiness에 넣었다면 이 상황에서 대상 그룹이 완전히 비어 fail-open으로 되돌아오며 헬스 상태가 요동친다. 인스턴스가 1대인 현재 구성에서는 이 위험이 더 크다.

**응답 코드가 원인 위치를 알려준다.** 502는 ALB가 대상에 연결하지 못한 것이므로 앱 프로세스 문제이고, 503은 앱이 살아서 의도적으로 반환한 것이므로 하위 의존성 문제다. 알람에서 둘을 구분해야 원인을 잘못 짚지 않는다.

## 7. 검증 계획

### 7.1 앱 인스턴스 장애

| 항목 | 내용 |
|---|---|
| 주입 | `docker kill app-1` |
| 전제 | k6로 지속 부하 인가 |
| 확인 1 | 오류 발생 구간이 30초 이내인가 |
| 확인 2 | 컨테이너가 자동 재기동되는가 |
| 확인 3 | 재기동 후 readiness 통과까지 몇 초인가 |
| 확인 4 | ASG가 인스턴스를 교체하는가 (인스턴스 자체를 종료한 경우) |

### 7.2 앱 응답 정지

| 항목 | 내용 |
|---|---|
| 주입 | `docker pause app-1` 60초 |
| 확인 1 | ALB가 unhealthy로 판정하는가 |
| 확인 2 | Docker healthcheck가 재기동을 유발하는가 |
| 확인 3 | unpause 후 정상 편입되는가 |

급사보다 정지가 위험하다. 프로세스는 살아 있어 TCP 연결은 수립되지만 응답이 없기 때문이다. 헬스체크 타임아웃이 없으면 감지되지 않는다.

### 7.3 DB 페일오버

| 항목 | 내용 |
|---|---|
| 주입 | RDS 콘솔에서 reboot with failover |
| 전제 | k6로 읽기와 쓰기 혼합 부하 인가 |
| 측정 1 | 페일오버 실제 소요 시간 |
| 측정 2 | 오류 구간의 응답 코드 분포 (503이어야 함) |
| 측정 3 | 정상화까지의 총 시간 |
| 확인 1 | 톰캣 스레드가 고갈되지 않는가 |
| 확인 2 | 헬스 엔드포인트가 계속 응답하는가 |
| 확인 3 | 앱 재기동 없이 자동 복구되는가 |
| 확인 4 | 커밋된 데이터가 손실되지 않는가 (RPO 0) |

측정 3이 60초를 크게 초과하면 4.3절의 DNS 캐시 설정을 확인한다.

확인 2가 실패하면 4.5절의 `connection-timeout`이 적용되지 않은 것이다.

### 7.5 관측 항목

검증 중 다음 지표를 함께 기록한다.

| 지표 | 출처 |
|---|---|
| HikariCP 활성 및 대기 커넥션 | `hikaricp_connections_active`, `hikaricp_connections_pending` |
| 톰캣 사용 중 스레드 | `tomcat_threads_busy_threads` |
| 대상 그룹 정상 호스트 수 | CloudWatch `HealthyHostCount` |
| 응답 코드 분포 | ALB 지표 또는 k6 결과 |
| DB 커넥션 오류 | 애플리케이션 로그 |
| 쓰기 경로 응답시간 | `http_server_requests_seconds_bucket` 의 쓰기 엔드포인트. 4.2절의 커밋 지연이 여기 실린다 |

`hikaricp_connections_pending`이 치솟는데 `tomcat_threads_busy_threads`가 상한에 붙어 있으면, 스레드 고갈이 진행 중이라는 신호다.

## 8. 설정 요약

한곳에 모은 최종 설정이다.

```yaml
# application.yml
server:
  shutdown: graceful
  tomcat:
    threads:
      max: 200

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
  datasource:
    url: jdbc:mysql://${DB_ENDPOINT}:3306/${DB_NAME}?connectTimeout=3000&socketTimeout=10000
    hikari:
      connection-timeout: 3000
      validation-timeout: 1000
      keepalive-time: 120000
      max-lifetime: 1500000
      maximum-pool-size: 10
      minimum-idle: 10

management:
  endpoint:
    health:
      probes:
        enabled: true
      show-details: never
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
```

```
# JVM 옵션
-XX:MaxRAMPercentage=70
-Dnetworkaddress.cache.ttl=5
-Dnetworkaddress.cache.negative.ttl=1
```

| 계층 | 항목 | 값 |
|---|---|---|
| ALB | 헬스체크 경로 | `/actuator/health/readiness` |
| ALB | 간격 / 타임아웃 | 10초 / 5초 |
| ALB | 정상 / 비정상 임계값 | 2 / 2 |
| ALB | deregistration delay | 30초 |
| Docker | restart | `unless-stopped` |
| Docker | stop_grace_period | 45초 |
| Docker | healthcheck 경로 | `/actuator/health/liveness` |
| Docker | start_period | 60초 |
| systemd | TimeoutStopSec | 60초 |

## 9. 값 조정이 필요한 항목

본 문서의 수치는 일반적인 출발점이다. 실제 부하 특성에 따라 다음을 조정한다.

| 항목 | 조정 기준 |
|---|---|
| `socketTimeout` | 가장 오래 걸리는 정상 쿼리의 p99보다 여유 있게 |
| `maximum-pool-size` | 동시 처리량과 DB `max_connections` 한계 |
| `@Transactional(timeout)` | 쓰기 경로의 정상 소요 시간 |
| 톰캣 `threads.max` | 인스턴스 메모리와 커넥션 풀 크기의 균형 |
| ALB 비정상 임계값 | 감지 속도와 오탐 사이의 균형 |
| 쓰기 커밋 지연 | 4.2절의 동기 복제 추가분. **실측한 적이 없다.** 부하 시험에서 읽는다 |

특히 커넥션 풀 크기는 "크게 잡으면 안전하다"가 성립하지 않는다. 풀이 크면 DB 쪽 커넥션 한계에 먼저 닿고, 커넥션당 메모리 소비도 늘어난다. 부하 시험으로 실측한 뒤 정한다.
