# 미결정 값

`docs/system-design/`에서 **아직 정해지지 않았거나 문서마다 다르게 적힌 값**을 모은다.

여기 있는 값은 판정 기준이 되지 못한다.
`code-guideline.md`의 항목이 "확정값과 일치하는가"를 묻는데, 확정값이 없거나 둘이면 판정할 수 없다.

두 부류가 섞이지 않게 나눈다.

| 부류 | 왜 못 정하는가 | 어떻게 정하는가 |
|------|----------------|-----------------|
| [1. 어긋난 값](#1-어긋난-값) | 문서마다 다르게 적혀 있다 | **읽고 고르면 된다.** 측정이 필요 없다 |
| [2. 비어 있는 값](#2-비어-있는-값) | 아직 측정하거나 실험하지 않았다 | 부하 시험, 스파이크, 리허설 |

1번은 지금 결정할 수 있고, 2번은 못 한다. 이 구분이 중요하다.

---

## 1. 어긋난 값

**네 건 모두 해소했고 게이트 반영까지 끝났다.** `fresh-market/.github` 의 `.github/llm-verify/known-conflicts.yml` 에서 네 건이 `resolved` 로 바뀌었다 (PR #5, `4ccbc2a`).

게이트는 아직 `unresolved` 인 모순만 `CONFLICTING_BASELINE` 으로 유보한다.
**한쪽을 골라 판정하지 않는다.** 그건 LLM이 팀의 결정을 대신 내리는 것이다.

새로 모순이 나오면 `known-conflicts.yml` 에 `unresolved` 로 넣고, 정해지면 `resolved` 로 바꾼다.

### 1.1 readiness 그룹에 `db`를 넣는가 (해소됨)

**넣지 않는 것으로 확정했다.** 기술 스택 확정 문서 4.2절을 `include: diskSpace` 로 고쳤다.

`INF-16`(공유 의존성을 readiness 에 넣지 않음)이 애초에 "되돌릴 수 없음"으로 등록된 결정이었고, 앱과DB 장애대응구조 1.1절이 초기 설계를 명시적으로 철회했는데, 확정값 문서만 옛 값을 **실행 가능한 yaml 형태로** 들고 있었다. 그래서 넷 중 가장 위험했다. 그대로 복사되면 그만이었다.

| 대상 | 포함 여부 | 근거 |
|------|-----------|------|
| 인스턴스 로컬 상태 (디스크, 기동 완료) | 포함 | 이 인스턴스만의 문제이므로 빼면 해결된다 |
| 공유 의존성 (DB, 캐시, 외부 API) | 제외 | 모든 인스턴스가 동시에 빠져 상황이 악화된다 |

DB가 잠시 흔들리면 전 인스턴스가 동시에 대상 그룹에서 빠져 서비스가 통째로 끊긴다. 등급이 Critical 이라서 넣는 것이 아니다. **공유 여부로 가른다.**

**게이트 반영 완료**: `known-conflicts.yml` 의 `readiness-include-db` 가 `resolved` 다. `REL-5-01`, `REL-5-02`, `INF-4-01` 은 `CONFLICTING_BASELINE` 에서 풀렸다.

### 1.2 ~ 1.4 배포 지표 세 건 (해소됨)

셋이 한 뿌리였다. **`장애 대응 목표` 7.1절과 `무중단 배포 롤링` 부록 A 가 채택하지 않은 롤링 변형을 서술하고 있었다.**

| 항목 | 옛 서술 (채택 안 함) | **확정** |
|------|------|-----|
| 전환 방식 | 대상 그룹에서 하나씩 빼고 교체 | **신규를 먼저 띄우고 검증 후 구 인스턴스 종료** |
| 배포 중 용량 | 50% | **100%** |
| 배포 소요 | 3~4분 | **6~8분** |
| 롤백 소요 | 3~4분 | **6~8분** |
| 혼재 구간 | 약 2분, 약 3분 | **약 1분** |
| 추가 인스턴스 | 불필요 | **배포 중 1대** |

실제 절차(`무중단 배포 롤링` 6절)가 `desired +1` 로 신규를 먼저 띄운다. 그래서 용량이 줄지 않고 그만큼 시간이 더 든다. `INF-29`("신규 기동 실패 시 구 인스턴스가 서비스 유지")가 이 방식을 가리킨다. 옛 값은 그 결정 이전의 서술이 남은 것이다.

**혼재 구간이 약 1분인 근거**는 절차에서 나온다. 신규가 대상 그룹에 등록된 뒤 스모크 테스트를 거치고, 구 인스턴스를 종료하면 드레이닝 30초가 걸린다.

**배치는 혼재 구간에 해당하지 않는다.** 전용 인스턴스에서 돌고 롤링 대상이 아니라 중지 후 교체한다(`INF-05`). 옛 서술의 "배치 주기가 혼재 구간보다 짧으면" 은 배치 분리 이전의 전제였다.

**함께 고친 것**: `시스템 디자인 종합` 7.3절이 "부하 시험 중 배포 금지" 의 근거를 "용량이 절반이 되므로" 로 적고 있었다. 용량은 100%다. 실제 근거는 혼재 구간이 측정을 오염시킨다는 것이다.

**게이트 반영 완료**: `known-conflicts.yml` 의 `deploy-capacity`, `deploy-duration`, `mixed-window` 가 모두 `resolved` 다.

## 2. 비어 있는 값

측정하거나 실험해야 나오는 값이다. **읽어서 정할 수 없다.**

이 값에 걸린 점검 항목은 근거 판정(기록이 있는가)만 가능하고 일치 판정(값이 같은가)은 불가능하다.
"측정 전에는 경보 없이 관측만"이라는 규율을 그대로 적용한다.

### 2.1 부하 시험이 있어야 나오는 것

오토스케일링 설계 297~305행. 전부 `(미정)`이다.

| 값 | 어떻게 구하는가 |
|------|-----------------|
| 인스턴스당 처리 가능 RPS | 단계적 부하 증가 중 p99가 목표를 넘는 지점 |
| `ALBRequestCountPerTarget` 목표값 | 위 값의 60~70% |
| 인스턴스 기동 시간 | 증설부터 healthy까지 |
| 인스턴스 워밍업 | 기동 시간 + 여유 |
| 최대 인스턴스 수 | 산출식에 실측값 대입 |
| 배치 최대 실행 시간 | 배치 로그 |
| 수명주기 훅 제한 시간 | 배치 최대 실행 시간 + 여유 |
| 병목 위치 | 부하 증가 시 먼저 포화되는 구성요소 |

**병목 위치가 먼저다.** DB가 병목이면 앱을 늘려도 효과가 없으므로 오토스케일링 자체를 도입하지 않는다(`OPS-1-01`).

알람과 알림 설계 5.1, 5.2절의 임계값 5곳도 같다.

```
백업 미생성        LatestRestorableTime 지연 (미정)분
502 발생          (미정) 초과
RDS 여유 메모리    (미정) 미만
톰캣 스레드 사용률  (미정)% 초과
ConsumedLCUs      (미정) 초과
```

**발동하지 않는 알람은 없는 것과 같고, 잘못된 임계값의 알람은 그보다 나쁘다.**

시스템 디자인 종합 593~602행의 설정값 5종(socketTimeout, 풀 크기, 트랜잭션 타임아웃, 톰캣 스레드, ALB 임계값)도 부하 시험 후 확정한다.

### 2.2 조회하면 바로 나오는 것 (해소됨)

**RDS `max_connections` 는 60 이다.** 2026-08-23 재구축 뒤 실측했고 공식에서 예측한 약 60 과 일치했다.

| 값 | 실측 | 잰 방법 |
|------|------|---------|
| `max_connections` | **60** | Prometheus `mysql_global_variables_max_connections` |
| `threads_connected` | 3 | 같은 익스포터. 앱이 뜨기 전 값이라 익스포터와 배치뿐이다 |
| `max_used_connections` | 3 | 같은 익스포터 |

`db.t4g.micro` 의 기본 공식 `{DBInstanceClassMemory/12582880}` 이 그대로 적용된 값이다. 파라미터 그룹에서 따로 지정하지 않았다.

이 값으로 커넥션 예산을 검산하면 이렇다.

```
app         maximum-pool-size 10 x 최대 2대  =  20
monitoring  mysqld_exporter                  =  1~2
batch       풀 크기 미확정
관리자, 마이그레이션 여유
─────────────────────────────────────────────
가용                                            60
```

앱만으로 3분의 1을 쓴다. `minimum-idle: 10` 이라 유휴여도 20개를 상시 점유한다. 여유는 있으나 넉넉하지 않고, ASG `max` 를 2보다 올리면 그때 빡빡해진다.

**앱이 뜬 상태에서 다시 재야 실사용량이 확정된다.** 위 `threads_connected` 3 은 앱 컨테이너가 없을 때의 값이다.

**측정 경로 주의**: RDS 가 프라이빗 서브넷이라 밖에서 직접 붙을 수 없고, 파라미터 그룹에는 공식만 있어 실제 값이 보이지 않는다. mysqld_exporter 가 유일한 관측 경로다. 그것이 죽어 있으면 이 값을 다시 잴 수 없다.

### 2.3 리허설이 있어야 나오는 것

| 값 | 현재 상태 |
|------|-----------|
| PITR 실측 RTO | 문서가 스스로 "근거 없는 목표치"라고 적고 있다 (60분) |
| PITR 실제 복원 지점 | RPO 5분은 AWS 구조에서 나오는 값이라 목표치가 아니다. 리허설에서 실제로 5분 안에 드는지만 본다 |

`OPS-1-12`가 이것을 점검한다.

### 2.4 스파이크로 해소된 것

둘 다 착수 전 스파이크 대상이었고 **지금은 확정이다.** 코드에 들어가 `./gradlew check` 가 도는 것으로 확인됐다.

| 값 | 결과 |
|------|-----------|
| springdoc-openapi 도입 | **확정. 3.0.3** (Boot 4.0.5 로 빌드된 버전). `build.gradle:79` |
| QueryDSL APT 동작 | **확정. 5.1.0** (BOM 관리). `build.gradle:85`, `ProductQueryRepository` 가 사용 중 |

**springdoc 만 계속 확인이 필요하다.** Boot 의 BOM 이 관리하지 않는 의존성이라 버전을 직접 박아야 하고, Boot 를 올릴 때마다 호환 버전을 다시 봐야 한다.

```
springdoc 3.0.3  ->  Boot 4.0.5   <- 채택
springdoc 3.1.0  ->  Boot 4.1.0
```

확인 방법은 springdoc 의 `pom.xml` 이 어떤 `spring-boot-starter-parent` 를 상속하는지 보는 것이다. Spring REST Docs 를 버린 근거는 [be 의 tech-stack.md](https://github.com/fresh-market/fm-backend/blob/main/docs/tech-stack.md) 4장에 있다.

### 2.5 아직 고르지 않은 것 (측정 불필요, 선택의 문제)

| 값 | 선택지 |
|------|--------|
| 추적(APM) 백엔드 | X-Ray 또는 Grafana Tempo |
| 알림 채널 | 이메일, Slack 등 |
| 개발 서버 유무 | 상시 가동 시 월 28~52 USD 추가 |
| 이중화 전환 시점 | `desired_capacity` 2로 상향. 월 22 USD 추가 |
| 배치 주기와 실행 시각 | 배치 목록 확정 후 |
| Terraform 마이너 버전 | 구축 시점 최신 안정 버전 |

이미지 조회 방식은 **CloudFront + OAC 로 확정**했다 (2026-08-08).
근거는 [백엔드공통_이미지저장소_설계.md](../system-design/백엔드공통_이미지저장소_설계.md), 점검 항목은 [code-guideline.md](./code-guideline.md) 11장에 있다.

다만 아래 둘은 아직 남았다.

| 값 | 정해야 할 때 |
|------|--------------|
| presigned URL 만료 시간 | 업로드 구현 시 |
| CloudFront 무효화 정책 | 이미지 교체 기능이 생길 때 |

## 다음에 할 일

우선순위는 **막고 있는 것의 크기**로 정한다.

| 순위 | 무엇 | 드는 시간 | 막고 있는 것 |
|------|------|-----------|--------------|
| 1 | 2.1 부하 시험 | 시험 1회 | 오토스케일링 도입 판단, 알람 임계값 5곳, 설정값 5종 |

**부하 시험만 남았고 인프라가 떠 있어야 한다.** 병목 위치를 먼저 본다. DB 가 병목이면 앱을 늘려도 효과가 없어 오토스케일링 자체를 도입하지 않는다 (`OPS-1-01`).

1장의 어긋난 값 네 건, 2.2 의 `max_connections`, 2.4 의 스파이크 두 건(springdoc, QueryDSL)이 모두 해소되어 목록에서 뺐다. `known-conflicts.yml` 반영도 끝나 게이트가 유보 중인 항목은 없다.
