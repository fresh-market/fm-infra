# 인프라 전제 코드 리뷰 가이드

이 문서는 `docs/system-design/`의 설계 결정 중 **애플리케이션 코드와 설정으로 지켜야 하는 것**을 코드 리뷰 점검 항목으로 정리한 가이드다.
배치 스케줄러, 애플리케이션 설정, 스키마 마이그레이션이 포함되거나 변경되는 PR에 적용한다.

판정 대상은 대부분 `fresh-market/fm-backend`의 코드다. 인프라 결정이 코드에 부과하는 제약이기 때문이다.
각 항목의 근거는 `docs/system-design/`의 해당 문서에 있으며, 항목마다 출처를 표기했다.

> **이 문서는 system-design 문서를 대체하지 않는다.**
> 저쪽이 근거와 확정값을 담고, 이 문서는 그중 PR 단위로 판정 가능한 것만 추출한다.
> 확정값이 바뀌면 저쪽을 고치고 이 문서를 따라 갱신한다.

## 1. 배치 재실행 안전성

배치는 전용 서버 한 대에서만 돈다. 그래서 중복 실행을 막는 락을 두지 않는다.
그럼에도 방어 장치가 필요한 이유는, **배치가 중간에 죽고 다시 도는 것은 락과 무관하게 일어나기 때문이다.**
배포로 인한 중지, 인스턴스 교체, 예외가 전부 그 경로다.

출처: 배치 설계 3장, 4장

점검 항목
* `INF-1-01` 배치 목록을 유형(멱등 전이형, 재계산형, 누적 연산형, 외부 부수효과형, 순번 발급형)으로 분류했는가
  누적 연산형은 멱등화가 필수이고, 외부 부수효과형은 멱등화로도 못 막아 선점이 필요하다.
* `INF-1-04` 상태 전이가 조건부 UPDATE인가
  조회 후 갱신 패턴이 남아 있으면 갱신 손실이 그대로 발생한다.
* `INF-1-05` 누적 연산이 전이 성공에 종속되는가
  `affected rows`가 0이면 즉시 종료해야 한다. 전이는 실패했는데 수량만 늘어나는 것을 막는다.
* `INF-1-06` 외부 호출 전에 상태를 선점하는가
  호출 후 상태를 바꾸면 그 사이에 다른 인스턴스가 같은 행을 집어 들어 중복 발송이 된다.
* `INF-1-09` 시각 기준을 애플리케이션 `Clock`으로 통일했는가
  `NOW()`와 `Instant.now()`를 섞으면 DB 시각과 인스턴스 시각 두 기준이 공존한다.
* `INF-1-10` 스케줄러 설정이 `batch` 프로필로 감싸여 있는가
  앱 인스턴스에서 스케줄러가 켜지면 앱 대수만큼 배치가 중복 실행된다. 락이 없으므로 아무것도 막지 못한다.
* `INF-1-11` 배치 시작 로그에 `job_name`, `scheduled_at`, `instance_id`를 남기는가
  중복 실행을 탐지하는 유일한 근거다. 이 로그가 없으면 중복이 났는지 알 수 없다.

`INF-1-02`, `INF-1-03`, `INF-1-07`, `INF-1-08`은 분산 락 전용 항목이라 폐기했다.
번호는 재사용하지 않는다. 검증 결과가 항목 번호로 기록되므로 뜻이 바뀌면 과거 기록이 거짓이 된다.

## 2. 스케일 인 안전장치

스케일 인은 인스턴스를 종료하는데, 그 인스턴스가 배치를 실행 중일 수 있다.
ASG는 어느 인스턴스가 배치를 돌리는지 알지 못한다.

출처: 오토스케일링 설계 5장

점검 항목
* `INF-2-01` 종료 신호를 받으면 새 배치를 시작하지 않는가
  수명주기 훅이 `Terminating:Wait`로 잡아 두는 동안 드레이닝 플래그를 세운다.
* `INF-2-02` 진행 중인 배치가 끝날 때까지 기다린 뒤 훅에 완료 신호를 보내는가
* `INF-2-03` 훅이 실패해도 조건부 UPDATE 방어가 남아 있는가
  훅은 최적화이고 정합성 보장은 조건부 UPDATE가 한다.

## 3. DB 장애 전파 차단 설정

DB가 죽었을 때 가장 흔한 실패 양상은 DB 자체가 아니라 **앱이 함께 죽는 것**이다.
커넥션 대기가 톰캣 워커를 전부 소진해 헬스 엔드포인트조차 응답하지 못하게 된다.

출처: 앱과 DB 장애 대응 구조 4장

확정값이므로 값까지 대조한다.

| 설정 | 확정값 | 막는 것 |
|---|---|---|
| `networkaddress.cache.ttl` | 5 | 옛 주소 고착으로 페일오버 후 복구 실패 |
| JDBC `connectTimeout` | 3000 | TCP 연결 수립 무한 대기 |
| JDBC `socketTimeout` | 10000 | 이미 맺은 커넥션의 무한 대기 |
| Hikari `connection-timeout` | 3000 | **톰캣 스레드 고갈** |
| `@Transactional(timeout)` | 5 | 쿼리 도중 정지 |

점검 항목
* `INF-3-01` JVM 옵션에 `networkaddress.cache.ttl`이 설정되어 있는가
  이 설정이 빠지면 다른 모든 설정을 맞춰도 페일오버 후 복구가 되지 않는다.
* `INF-3-02` JDBC URL에 `connectTimeout`과 `socketTimeout`이 있는가
* `INF-3-03` Hikari `connection-timeout`이 설정되어 있는가
* `INF-3-04` 쓰기 경로에 `@Transactional(timeout)`이 지정되어 있는가
* `INF-3-05` `socketTimeout`이 가장 오래 걸리는 정상 쿼리보다 긴가
  짧으면 장애가 아닌 상황에서도 정상 쿼리가 잘린다.
* `INF-3-06` `maximum-pool-size`와 `minimum-idle`이 같은 값인가
  풀 크기를 고정해 부하 급증 시 커넥션 생성 지연을 없앤다.
* `INF-3-07` `max-lifetime`이 DB `wait_timeout`보다 짧은가

## 4. 헬스체크

liveness와 readiness는 서로 다른 질문에 답한다. 이 구분이 무너지면 장애가 증폭된다.

출처: 앱과 DB 장애 대응 구조 3.3절

점검 항목
* `INF-4-01` readiness 그룹에 공유 의존성(DB, 캐시, 외부 API)을 넣지 않았는가
  넣으면 그 의존성 장애 시 모든 인스턴스가 동시에 대상 그룹에서 빠져 상황이 악화된다.
  Spring Boot 기본 동작이 이미 올바르므로 **그룹을 재정의하지 않는 것**이 정답이다.
* `INF-4-02` liveness가 프로세스 생존만 보는가
* `INF-4-03` `management.endpoint.health.probes.enabled`가 켜져 있는가
* `INF-4-04` `show-details`가 `never`인가

## 5. 컨테이너 설정

출처: 앱과 DB 장애 대응 구조 3.2절

점검 항목
* `INF-5-01` `restart` 정책이 `always`가 아니라 `unless-stopped`인가
  `always`면 배포 중 의도적으로 내린 컨테이너를 Docker가 다시 살려 배포 절차와 충돌한다.
* `INF-5-02` `JAVA_TOOL_OPTIONS`에 `MaxRAMPercentage`가 지정되어 있는가
  없으면 힙이 컨테이너 한계를 넘어 커널이 프로세스를 죽인다. 힙 덤프가 남지 않아 원인 분석이 불가능하다.
* `INF-5-03` healthcheck `start_period`가 기동 시간을 감당하는가
  짧으면 기동 도중 계속 재기동되는 무한 루프에 빠진다.
* `INF-5-04` 종료 타임아웃 4계층이 안에서 바깥으로 갈수록 긴가
  ALB deregistration 30초 <= Spring graceful 30초 <= Docker stop_grace 45초 <= systemd 60초.

## 6. 롤링 배포 혼재 구간

신규와 구 인스턴스가 약 1분간 함께 트래픽을 받는다. 배포가 중단되면 이 구간이 무기한 지속된다.

출처: 무중단 배포 롤링 8장

점검 항목
* `INF-6-01` 스키마 변경이 확장 후 축소(추가만)인가
  컬럼 삭제, 이름 변경, 기본값 없는 `NOT NULL` 추가, 타입 축소는 구 버전을 깨뜨려 롤백이 불가능해진다.
* `INF-6-02` API 응답 필드를 제거하거나 이름을 바꾸지 않았는가
  혼재 구간에는 클라이언트가 요청마다 다른 버전에 도달한다.
* `INF-6-03` 배치 상태 전이가 두 버전 모두에서 안전한가
  어느 버전이 락을 잡을지 알 수 없으므로 조건부 UPDATE가 유일한 방어선이다.
* `INF-6-04` CI에 파괴적 DDL 차단이 걸려 있는가

## 7. 식별자와 버전 외부화

ASG가 인스턴스를 교체할 때 시작 템플릿의 태그가 고정되어 있으면 **장애 복구가 곧 버전 롤백**이 된다.

출처: 무중단 배포 롤링 4장, 백업과 복원 설계 5.1절

점검 항목
* `INF-7-01` 현재 배포 버전을 SSM 파라미터로 읽는가
  user-data가 `/{project}/current-sha`를 조회해 컨테이너를 띄운다.
* `INF-7-02` DB 엔드포인트를 SSM 파라미터로 읽는가
  RDS 복원은 항상 새 인스턴스를 만들어 엔드포인트가 바뀐다.
* `INF-7-03` 배포 스크립트가 컨테이너 교체보다 **먼저** SSM 값을 갱신하는가
  나중에 갱신하면 그 사이 교체된 인스턴스가 구버전으로 올라온다.
* `INF-7-04` 롤백 시 SSM 값도 함께 되돌리는가

## 8. 정합성 감지

누적 값 오차는 발생 시점에 아무 신호도 내지 않는다. 증상은 며칠 뒤 무관해 보이는 트랜잭션에서 나타난다.

출처: 백업과 복원 설계 8장

점검 항목
* `INF-8-01` 누적 값 테이블에 변경 이력이 함께 남는가
  이력이 없으면 부분 복구가 불가능하고 정합성 검증 자체가 성립하지 않는다.
* `INF-8-02` 정합성 검증 배치가 이력에서 재계산한 값과 현재 값을 대조하는가
* `INF-8-03` 알람 메시지에 오차 건수, 최대 오차, 최근 변경 시각, 변경 주체가 포함되는가
  변경 주체가 전부 같은 시각의 `BATCH`라면 원인이 즉시 드러난다.

## 9. 관측 설정

출처: 기술 스택 확정 문서 4.2절, 4.3절

점검 항목
* `INF-9-01` 액추에이터가 `management.server.port` 로 8080 과 분리되어 있고 `/actuator/prometheus` 가 노출되는가
  같은 포트에 두면 밖에서 막을 규칙이 따로 필요하고, 그 규칙이 지워지면 그대로 열린다. 포트를 나누면 8080 에 그 경로가 존재하지 않는다.
* `INF-9-02` 메트릭 태그에 `application`과 `instance`가 있는가
* `INF-9-03` 로그가 stdout JSON이고 `traceId`가 MDC에 실리는가
  롤링 혼재 구간에서 구 버전과 신 버전의 로그를 구분해 따라가려면 이 값이 필요하다.
* `INF-9-04` Loki 레이블에 식별자처럼 값 종류가 무한한 항목을 넣지 않았는가
  카디널리티가 폭발해 Loki가 느려진다. 본문 JSON 필드로 두고 쿼리 시 파싱한다.
* `INF-9-05` 추적 샘플링 비율이 환경 변수로 주입되는가
  장애 주입 실험 직전에 100%로 올릴 수 있어야 한다.

## 10. 빌드 게이트

점검 항목과 근거를 **`fresh-market/fm-backend` 가 소유한다.** 판정 대상이 그 저장소의 `build.gradle` 이다.

[be 의 build-gate-guideline.md](https://github.com/fresh-market/fm-backend/blob/main/docs/code-architecture/build-gate-guideline.md)

커버리지(service 패키지 메서드 100%)와 정적 분석(신규 `Blocker` 0건)이 **병합을 차단한다.**
이 문서의 다른 항목과 달리 LLM 이 아니라 도구가 판정한다.

## 11. 이미지 저장소

출처: 이미지저장소 설계 문서 6.2절

버킷은 비공개이고 CloudFront + OAC 가 서빙한다. 업로드는 presigned PUT 으로 S3 에 직접 간다.

```
업로드   클라이언트  --presigned PUT-->  S3 (비공개)
조회     클라이언트  --GET-->  CloudFront  --OAC-->  S3
```

**이 절은 backend 코드가 판정 대상이다.** 버킷 정책과 OAC 설정 자체는 Terraform 이 생기면 별도 항목으로 다룬다.

점검 항목
* `INF-11-01` 응답에 넣는 이미지 URL 이 CloudFront 도메인인가
  S3 직접 URL(`*.s3.*.amazonaws.com`)을 노출하면 버킷을 비공개로 둔 의미가 없다. 접근은 거부되지만 버킷 이름과 키 구조가 드러난다.
  **presigned PUT URL 은 예외다.** 업로드는 오리진에 직접 서명하는 것이라 구조상 S3 호스트일 수밖에 없다. 이 항목은 조회용 URL 이 대상이다.
* `INF-11-02` presigned URL 발급 전에 요청자의 권한을 확인하는가
  서명은 그 자체로 접근 권한이다. 발급 조건을 확인하지 않으면 누구나 남의 경로에 쓸 수 있다.
* `INF-11-03` 업로드 키(저장 경로)를 서버가 정하는가
  클라이언트가 준 파일명을 그대로 쓰면 경로 조작과 덮어쓰기가 가능하다.
* `INF-11-04` 업로드 완료 통지에서 키를 클라이언트에게 받지 않는가
  서명은 **올리는 것**만 막지 **저장하는 것**은 막지 못한다.
  키를 돌려받아 저장하면 남의 키를 실어 보내 남의 이미지를 자기 리소스에 붙일 수 있다.
  발급 시점에 서버가 키를 저장해 두고 통지는 발급 식별자로만 받는다.
* `INF-11-05` 이미지 URL 을 통째로 저장하지 않고 키만 저장하는가
  도메인은 환경마다 다르므로 설정에서 붙인다. 전체 URL 을 저장하면 도메인이 바뀔 때 전 행을 고쳐야 하고,
  나중에 CloudFront 서명 URL 로 바꿀 수도 없다. 서명은 발급할 때마다 달라지는데 저장된 값은 고정이기 때문이다.
* `INF-11-06` 발급 때 크기 상한을 검사하고 `Content-Type` 과 크기를 서명 조건에 넣는가
  서명만 발급하고 조건을 안 걸면 클라이언트가 무엇이든 올릴 수 있다. 업로드가 앱을 거치지 않으므로 사전 방어는 이것뿐이다.
  presigned PUT 은 범위 조건을 걸 수 없어(`content-length-range` 는 POST policy 의 기능이다) 신고받은 정확값을 서명한다.
  그래서 상한 검사는 발급 요청을 받은 자리에서 따로 해야 한다. 크게 신고하면 여기서 걸리고, 작게 신고하고 큰 파일을 올리면 S3 가 거부한다.
  상한 값은 용도마다 다르며 `백엔드공통_이미지저장소_설계.md` 6.2절에 있다.
* `INF-11-07` S3 접근에 액세스 키가 아니라 IAM 역할을 쓰는가
  앱이 EC2에서 돌고 시크릿은 SSM을 쓰므로 액세스 키를 코드나 설정에 둘 이유가 없다.
* `INF-11-08` 이미지 삭제가 S3 객체 삭제까지 이어지고, 객체를 먼저 지우는가
  DB 레코드만 지우면 객체가 남아 저장 비용이 계속 나가고, 키를 아는 사람은 계속 볼 수 있다.
  순서도 본다. 행을 먼저 지우면 키를 잃어 그 객체를 다시 찾을 방법이 없어지고 고아가 확정된다.
  객체를 먼저 지우면 행 삭제가 실패해도 사용자가 다시 지워 해소된다. `DeleteObject` 는 없는 객체에도 성공하므로 재시도가 안전하다.
  되돌릴 수 없는 쪽을 피하는 것이며, `INF-11-13` 의 정리 배치와 같은 규칙이다.
* `INF-11-09` 이미지 조회 쿼리가 확정된 행만 고르는가
  `INF-11-04` 때문에 발급 시점에 행이 먼저 생기므로, 아직 올라오지 않은 행이 테이블에 남아 있다.
  조건을 빠뜨리면 업로드를 중간에 그만둔 이미지가 그대로 응답에 실려 깨진 이미지가 나간다.
  응답을 만든 뒤 걸러내지 말고 쿼리에서 걸러야 한다. 목록 조회가 특히 그렇다.
* `INF-11-10` 업로드 완료 통지에서 객체 존재와 서명 조건 일치를 S3 에 확인하는가
  업로드가 앱을 거치지 않으므로 서버는 `PUT` 이 실제로 일어났는지 모른다. 통지는 클라이언트의 주장일 뿐이다.
  통지만 믿고 확정하면 객체가 없는 키가 조회 응답에 실려 `INF-11-09` 를 지켜도 깨진 이미지가 나간다.
  `HeadObject` 로 존재를 확인하고, `Content-Length` 와 `Content-Type` 이 서명 조건과 같은지 대조한다.
  `INF-11-06` 의 조건은 올리는 것만 막으므로, 올라온 것이 조건과 같은지는 이 시점에서만 확인된다.
* `INF-11-11` 업로드 확정 요청에서 발급 건이 요청자와 대상 리소스에 속하는지 확인하는가
  `uploadId` 도 클라이언트가 보낸 식별자다. 그것으로 행을 찾은 것은 발급 건이 존재한다는 뜻일 뿐 요청자 것이라는 뜻이 아니다.
  경로의 리소스 식별자와 행의 FK 가 같은지, 그 리소스가 인증 주체의 것인지 둘 다 본다.
  확인하지 않으면 남의 발급 건 번호를 실어 보내 남의 이미지를 자기 리소스에 붙일 수 있어, `INF-11-04` 가 키를 안 받은 것이 무의미해진다.
  `INF-11-02` 는 발급 시점만 다룬다. 확정은 별개의 요청이고 그 사이에 권한이 바뀌었을 수도 있다.
  어긋날 때 `403` 이 아니라 `404` 를 주어야 번호를 훑어 남의 발급 건의 존재를 알아내지 못한다.
* `INF-11-12` 조회 시점 확정을 두었다면 유효 창과 단건 조회로 한정했는가
  확정 통지가 유실된 업로드를 조회할 때 `HeadObject` 로 되살리는 경우에만 해당한다. 두지 않았다면 이 항목은 대상 밖이다.
  발급한 지 오래된 행까지 시도하면 조회가 끝나지 않는 재시도가 된다. 확정될 수 없는 행은 계속 미확정이라 볼 때마다 다시 묻게 되고, 결과는 매번 같다.
  목록 조회에 넣으면 리소스 수 × 이미지 수만큼 동기 외부 호출이 되어 응답 시간이 S3 지연에 묶인다. 목록은 확정된 행만 걸러 내보낸다.
  확정 `UPDATE` 는 조회 트랜잭션 밖에서 조건부로 쓴다. 같은 리소스를 동시에 조회한 요청들이 같은 행을 확정하려 든다.
  서명 조건 대조에 실패하면 확정만 하지 않는다. 객체를 지우는 것은 배치 몫이며, 조회가 S3 객체를 삭제하는 구조는 만들지 않는다.
* `INF-11-13` 미확정 업로드를 정리하는 배치가 있고 S3 객체를 먼저 지우는가
  확정 통지가 유실되면 아무도 참조하지 않는 객체가 남는다. 조회에서 빠지므로 사용자 눈에 안 보이고, 그래서 어떤 삭제 경로에도 걸리지 않는다.
  `INF-11-08`은 사용자가 이미지를 지우는 경우만 다룬다. 확정된 적 없는 객체는 지울 대상으로 보이지도 않는다.
  행을 먼저 지우면 키를 잃어 객체를 영영 못 찾는다. S3 삭제가 먼저다.
  유예 시간이 `INF-11-12`의 유효 창보다 짧으면 아직 되살릴 수 있는 업로드를 배치가 지운다. 같은 값을 반대 방향으로 써야 한다.
  대상 조회가 상태와 생성 시각 복합 인덱스를 타는지 본다. 없으면 매 주기 풀스캔이다.
  `INF-1-01`의 외부 부수효과형이므로 1장의 락 항목이 모두 적용된다.

`INF-11-06`는 `fresh-market/.github`의 `SEC-3-04`(파일 업로드에서 확장자, MIME 타입, 크기, 저장 경로를 검증하는가)와 겹친다.
**업로드가 앱을 거치지 않는다는 이 인프라의 조건 때문에 검증 지점이 서명 시점으로 옮겨진 것이므로 여기가 더 구체적이다.**

`INF-11-11`은 `SEC-1-02`(검증을 클라이언트가 보낸 식별자가 아니라 인증 주체 기준으로 하는가)의 이미지 흐름 적용이다.
일반론만으로는 검사 지점이 어디인지 보이지 않는다. 업로드가 발급과 확정 두 요청으로 쪼개져 있어
발급 때 한 번 확인한 것으로 끝났다고 착각하기 쉬운 것이 이 흐름의 특성이므로 여기가 더 구체적이다.

세 이미지 테이블(`product_image`, `claim_attachment`, `shipment_photo`)이 각자 소유 리소스의 FK를 갖고 있어
이 확인이 조인 한 번으로 끝난다. 다형 테이블 하나로 합쳤다면 행마다 소유자를 찾는 경로가 달라졌을 것이다.

## 12. 인프라 코드

출처: 기술 스택 확정 문서 3.7절, 무중단 배포 롤링 5절, 알람과 알림 설계 3.3절

**이 절만 판정 대상이 이 저장소의 `.tf` 파일이다.** 나머지 장은 backend 코드를 본다.

인프라 결정의 상당수가 코드 한 줄에 걸려 있다. 배치 프로필 문자열 하나, `ignore_changes` 한 줄이 빠지면 락도 알람도 그것을 잡지 못한다. 그래서 파일을 읽어 판정할 수 있는 것만 여기 둔다. 런타임 상태를 조회해야 하는 것은 `preflight-guideline.md` 로 간다.

점검 항목
* `INF-12-01` `required_version` 과 AWS 프로바이더 버전이 고정되어 있는가
  코어는 `~> 1.15`, 프로바이더는 `~> 6.0` 이다. 프로바이더 고정이 코어보다 실질적으로 더 중요하다. 리소스 스키마가 거기서 바뀐다.
* `INF-12-02` 상태 백엔드가 S3 이고 `encrypt` 와 `use_lockfile` 이 켜져 있는가
  DynamoDB 잠금 테이블이 아니라 S3 네이티브 잠금을 쓴다. `backend "s3"` 블록 안에서는 변수 보간이 안 되므로 값은 `-backend-config` 로 넘긴다.
* `INF-12-03` SSM `current-sha` 파라미터에 `ignore_changes = [value]` 가 걸려 있는가
  값은 배포 스크립트가 갱신한다. 이 줄이 없으면 다음 `apply` 가 값을 `bootstrap` 으로 되돌려 전 인스턴스가 구버전으로 기동한다.
* `INF-12-04` 앱 ASG 에 `ignore_changes = [desired_capacity]` 가 걸려 있는가
  배포 중 desired 가 일시적으로 2가 된다. 이 줄이 없으면 `apply` 가 배포를 되돌린다.
* `INF-12-05` 앱 ASG 가 `min_size` 0, `desired_capacity` 1, `max_size` 2, `health_check_type` `ELB` 인가
  `max_size` 가 2여야 배포 절차가 성립한다. desired 를 2로 두면 신규를 띄울 자리가 없다.
* `INF-12-06` ALB 에 `enable_deletion_protection` 과 `prevent_destroy` 가 둘 다 있는가
  IaC 도입으로 오히려 커진 위험이다. 잘못된 변수 파일로 destroy 를 돌리면 ALB 가 사라지고 DNS 이름이 바뀐다. 두 겹으로 막는다.
* `INF-12-07` 앱 시작 템플릿의 user-data 에 `batch` 프로필이 없는가
  배치 프로세스가 하나라는 전제가 이 문자열 하나에 걸려 있다. 앱 ASG 에 들어가면 앱 대수만큼 배치가 돈다. 분산 락이 없으므로 아무것도 막지 못한다.
* `INF-12-08` 앱 시작 템플릿이 이미지 태그를 고정하지 않고 SSM 에서 읽는가
  고정하면 ASG 교체 시 최초 구축 시점 버전이 올라온다. 장애 복구가 곧 버전 롤백이 되고 혼재 구간이 무기한 지속된다.
* `INF-12-09` 모니터링 인스턴스가 ASG 밖에 있는가
  ASG 의 desired 0 은 EBS 까지 삭제한다. Prometheus 와 Loki 데이터가 사라진다.
* `INF-12-10` NAT Gateway 리소스가 없는가
  월 40 USD 이상으로 예산의 4분의 1을 차지한다. 앱을 퍼블릭 서브넷에 두는 설계 전체가 이 결정에서 나왔다.
* `INF-12-11` 22번 포트를 여는 인바운드 규칙이 없는가
  운영 접근은 SSM Session Manager 로 한다.
* `INF-12-12` 보안 그룹 인바운드가 CIDR 이 아니라 보안 그룹 참조인가
  앱이 퍼블릭 서브넷에 있으므로 보안은 서브넷이 아니라 보안 그룹이 확보한다. CIDR 로 열면 그 전제가 깨진다. 인터넷을 받는 ALB 만 예외다.
* `INF-12-13` 모든 CloudWatch 로그 그룹에 `retention_in_days` 가 있는가
  기본값이 무기한이라 생략하면 저장이 계속 누적된다.
* `INF-12-14` CloudWatch 알람이 6개 이하이고 전부 단일 지표인가
  무료 한도가 10개다. 이상 탐지, 복합 알람, 고해상도 알람, 커스텀 지표 전송, CloudWatch 대시보드는 쓰지 않는다. 각각 별도 과금이다.
* `INF-12-15` RDS 에 `multi_az`, `backup_retention_period` 7, `deletion_protection`, `skip_final_snapshot = false` 가 있는가
  자동 백업은 인스턴스를 지우면 함께 사라진다. 최종 스냅샷을 건너뛰면 되돌릴 수단이 없다.
* `INF-12-16` RDS 파라미터 그룹에 `max_connections` 를 지정하지 않았는가
  기본 파라미터 그룹의 공식을 그대로 쓴다. 1 GiB 에서 커넥션당 12MB 라 공식보다 높게 잡으면 OOM 이 난다.
* `INF-12-17` 캐시가 `aws_elasticache_cluster` 가 아니라 `aws_elasticache_replication_group` 인가
  복제본 추가는 replication group 에만 가능하다. 나중에 바꾸려면 이관이 필요하고 지금 정하면 비용 차이가 0 이다.
* `INF-12-18` ACM 검증용 DNS 레코드가 Terraform 관리 대상인가
  자동 갱신은 검증 레코드가 살아 있을 때만 된다. 레코드가 사라지면 갱신이 조용히 실패하고 만료 시점에야 드러난다.
* `INF-12-19` 대상 그룹이 트래픽 포트 8080 과 헬스체크 포트 8081 을 나눠 보는가
  액추에이터를 관리 포트로 뺐으므로 헬스체크도 그쪽을 봐야 한다. 8080 에는 그 경로가 없어 인증 실패로 떨어진다.
* `INF-12-21` 8081 을 여는 인바운드가 ALB 와 모니터링 보안 그룹뿐인가
  이 포트가 밖으로 열리면 관리 포트로 분리한 의미가 사라진다.
* `INF-12-22` 80 에서 443 으로의 리다이렉트가 있는가
  stateless JWT 가 헤더로 오가므로 평문 구간을 둘 수 없다 (INF-17).
* `INF-12-20` 오토스케일링 정책을 만들었다면 지표가 `ALBRequestCountPerTarget` 인가
  CPU 는 이 앱의 포화를 못 잡는다. 요청 스레드가 DB 응답이나 발급 큐의 future 를 기다리며 블록되므로,
  스레드가 다 잠긴 상태에서도 CPU 는 낮게 유지된다. 도착률은 병목이 어디든 부하를 그대로 반영한다.
  크레딧 때문이 아니다. 인스턴스가 전부 unlimited 모드라 크레딧은 애초에 스로틀 요인이 아니다 (INF-33).
